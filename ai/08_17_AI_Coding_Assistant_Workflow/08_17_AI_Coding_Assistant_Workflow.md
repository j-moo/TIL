# AI 코딩 도구와 협업하는 방법: 범위, 맥락, 권한, 검증

- 🎯 글의 목표: AI 코딩 도구에 긴 요청을 한 번 전달하는 데서 벗어나, 확인 가능한 입력·작은 작업 단위·명확한 권한·검증 절차로 결과 품질을 관리한다.
- 🧩 핵심 키워드: AI Coding Agent, Prompt, Context, Scope, Tool, Connector, CLI, Authentication, Read-only, Write Permission, Hallucination, Verification, Acceptance Criteria
- ⭐ 중요도: ★★★★★ — AI가 코드를 생성하는 능력보다 어떤 파일과 도구를 사용하고 무엇으로 완료를 판단할지 통제하는 능력이 실제 프로젝트 품질을 좌우하기 때문이다.
- 📝 한눈에 보는 내용: 좋은 요청은 목적, 근거 자료, 수정 범위, 금지 범위, 완료 조건을 분리한다. 큰 작업은 분석·설계·구현·검증으로 나누고 각 단계의 산출물을 확인한다. 플러그인, CLI, 브라우저는 인증과 권한이 서로 다를 수 있으며, 조회 성공이 수정 권한을 의미하지 않는다. 최종 결과는 보고가 아니라 파일·테스트·화면·원격 상태로 다시 확인한다.
- 🔗 관련 주제: 프롬프트 엔지니어링, Git, 코드 리뷰, 테스트, Figma, 브라우저 자동화, MCP
- 🧱 선수 지식: 파일과 폴더, Git 변경 사항, 테스트의 기본 목적

## 1. 들어가며

AI 코딩 도구에 자세한 설명을 많이 입력하면 항상 더 좋은 결과가 나올 것처럼 보인다. 하지만 한 대화에서 서로 다른 목표와 반복 수정이 계속 쌓이면, 최신 요구와 오래된 요구가 충돌하거나 이미 취소한 작업을 다시 수행할 수 있다.

또한 “GitHub가 연결되어 있다”, “Figma를 열 수 있다”, “Notion 페이지가 보인다”는 사실만으로 수정 권한까지 있다고 판단할 수 없다. 같은 계정처럼 보여도 플러그인, 로컬 CLI, 브라우저 로그인은 서로 다른 인증 경로와 권한을 가질 수 있다.

따라서 AI 도구와의 협업은 다음 세 축으로 관리한다.

```text
무엇을 할 것인가?      → 목표와 범위
무엇을 근거로 할 것인가? → 파일, 문서, 현재 상태
어떻게 완료를 증명할까?  → 테스트, diff, 화면, 원격 재조회
```

## 2. 핵심 개념 정리

AI 작업의 안정적인 흐름은 다음과 같다.

```text
목표 정의
  ↓
현재 상태와 근거 자료 확인
  ↓
수정 범위·금지 범위 확정
  ↓
작은 작업 단위로 실행
  ↓
각 단계 결과 검증
  ↓
최종 diff·테스트·외부 상태 확인
  ↓
남은 불확실성 기록
```

프롬프트는 결과물을 대신 만드는 마법 주문이 아니다. AI가 판단할 수 있는 경계를 정하고, 잘못된 판단을 빨리 발견할 수 있도록 검사 지점을 만드는 작업 명세다.

## 3. 본문 정리

### 3.1 좋은 요청의 다섯 요소

실행형 요청에는 최소한 다음 요소가 필요하다.

| 요소 | 설명 | 예시 |
| --- | --- | --- |
| 목표 | 최종적으로 바뀌어야 하는 상태 | 역할별 상단 내비게이션 구현 |
| 근거 | 판단에 사용할 자료 | 현재 라우터, 역할 정의, API 문서 |
| 범위 | 수정해도 되는 대상 | `frontend/` 내부 |
| 금지 범위 | 건드리면 안 되는 대상 | backend, 다른 담당자 파일 |
| 완료 조건 | 결과를 판단할 검사 | build 통과, 역할별 메뉴 확인, 변경 파일 목록 |

다음처럼 모호한 요청은 판단 공간이 너무 넓다.

```text
전체적으로 더 좋게 수정해 주세요.
```

다음처럼 바꾸면 판단 기준이 생긴다.

```text
목표: 사용자 역할에 따라 상단 내비게이션 항목을 다르게 표시한다.
근거: 현재 router 설정과 role 타입을 사용한다.
수정 범위: frontend/src 내부만 수정한다.
보존: 기존 URL과 API 요청 형식은 바꾸지 않는다.
완료 조건:
- fan, creator, manager 역할별 메뉴가 요구사항과 일치한다.
- 직접 URL 진입과 새로고침이 동작한다.
- TypeScript 검사와 build가 통과한다.
- 변경 파일과 확인하지 못한 사항을 보고한다.
```

### 3.2 긴 프롬프트보다 충돌 없는 프롬프트

긴 프롬프트가 필요한 작업도 있지만, 같은 지시를 여러 표현으로 반복하면 우선순위가 흐려질 수 있다. 현재 OpenAI 모델 지침도 각 지시를 한 번씩 명확히 쓰고, 필요한 도구와 예시만 노출하는 간결한 프롬프트를 권장한다.

프롬프트를 줄일 때는 중요한 제약까지 지우는 것이 아니라 다음 중복을 제거한다.

- 같은 목표를 표현만 바꾸어 여러 번 반복
- 이미 파일에 있는 긴 내용을 프롬프트에 다시 복사
- 이번 작업에 사용하지 않는 역할·도구 설명
- 완료 기준과 관계없는 스타일 문장

반대로 다음 내용은 짧게라도 남긴다.

- 정확한 대상 경로와 브랜치
- 수정·읽기 권한의 범위
- 보존해야 하는 동작
- 판단 기준의 우선순위
- 실행할 검증 명령
- 실패했을 때 보고할 정보

### 3.3 자료 우선순위를 정한다

여러 문서와 화면이 서로 다르면 AI가 임의로 섞을 수 있다. 작업 전에 근거의 우선순위를 정한다.

```text
1. 현재 실행되는 코드와 테스트
2. 승인된 최신 요구사항
3. 최신 화면 설계와 API 명세
4. 이전 보고서
5. 일반적인 관례
```

프로젝트에 따라 순서는 달라질 수 있다. 중요한 것은 충돌을 숨기지 않고 어떤 자료를 우선할지 명시하는 것이다.

```markdown
문서가 충돌하면 다음 순서로 판단한다.

1. 최신 API 명세
2. 현재 승인된 화면 설계
3. 기존 코드

충돌이 해결되지 않으면 구현으로 임의 확정하지 말고 `확인 필요`로 보고한다.
```

### 3.4 분석과 변경 권한을 분리한다

“분석해 주세요”는 보통 읽기 작업이고, “수정해 주세요”는 쓰기 작업이다. 외부 서비스에서는 클릭 한 번이 파일, 권한, 게시물에 실제 변경을 만들 수 있다.

작업 지시에서 다음을 분명히 한다.

| 모드 | 허용 예 | 금지 예 |
| --- | --- | --- |
| 읽기 전용 분석 | 파일 열기, 레이어 확인, 스크린샷, 보고서 작성 | 노드 이동, 텍스트 수정, 권한 변경 |
| 제한된 수정 | 지정한 Frame의 내부 UI 수정 | 다른 페이지·레이어 삭제 |
| 코드 구현 | 지정 디렉터리 수정, 테스트 실행 | 담당 외 코드 대규모 재구성 |

읽기 작업과 쓰기 작업을 한 문장에 섞으면, 분석만 원했는데 외부 상태가 바뀌거나 반대로 수정 요청인데 보고서만 생성되는 일이 생길 수 있다.

### 3.5 도구가 연결되었다는 말의 정확한 의미

AI 도구는 같은 서비스에 여러 방식으로 접근할 수 있다.

```text
GitHub Connector / Plugin
  └─ 앱에 부여된 OAuth 또는 설치 권한

로컬 gh CLI
  └─ 현재 컴퓨터의 gh 로그인 정보

브라우저
  └─ 해당 브라우저 프로필의 웹 로그인 세션

로컬 git
  └─ Git credential helper, SSH key, 토큰 등의 인증
```

이 인증 경로는 서로 자동 공유되지 않는다. 예를 들어 Connector로 저장소 README를 읽을 수 있어도 파일 쓰기 API가 `403 Forbidden`을 반환할 수 있다. 동시에 로컬 `gh auth status`는 로그인되지 않았지만 브라우저에는 로그인되어 있을 수도 있다.

📌 핵심: “연결됨”을 한 단계로 보지 말고 대상 서비스, 인증 주체, 허용 동작, 실제 검사 결과로 나눈다.

### 3.6 조회 성공은 쓰기 권한의 증거가 아니다

외부 서비스 권한은 보통 동작별로 분리된다.

| 확인된 동작 | 아직 확인되지 않은 동작 |
| --- | --- |
| 저장소 목록 조회 | 파일 커밋 |
| Figma 파일 열기 | 노드 수정 |
| Notion 페이지 읽기 | 페이지 편집 |
| 브랜치 조회 | push |

안전한 확인 순서는 다음과 같다.

1. 현재 사용자와 대상 리소스를 조회한다.
2. 대상 브랜치·파일·페이지를 정확히 식별한다.
3. 권한 메타데이터가 있다면 읽는다.
4. 사용자가 요청한 쓰기 동작을 실행한다.
5. 실패 시 HTTP 상태와 권한 범위를 구분한다.
6. 다른 인증 경로를 쓸 때는 다시 현재 계정과 대상을 확인한다.

### 3.7 `401`, `403`, `404`를 구분한다

외부 API에서 자주 만나는 상태를 단순히 “연결 안 됨”으로 묶으면 원인 분석이 틀릴 수 있다.

| 상태 | 일반적인 의미 | 확인할 것 |
| --- | --- | --- |
| `401 Unauthorized` | 인증 정보가 없거나 유효하지 않음 | 로그인, 토큰 만료, 인증 헤더 |
| `403 Forbidden` | 신원은 알지만 해당 동작 권한이 없음 | 앱 권한, 저장소 설치 범위, 조직 정책 |
| `404 Not Found` | 리소스가 없거나 권한 때문에 감춰짐 | 경로·브랜치·소유자 오타, 비공개 접근 |

실제 서비스는 보안을 위해 권한 부족을 `404`처럼 보이게 할 수도 있으므로 상태 코드만으로 확정하지 않고 계정·경로·권한을 함께 확인한다.

### 3.8 큰 작업을 단계로 나누는 이유

Notion 전체 분석, Figma 30개 화면 수정, React 구현, API 연결, 테스트를 한 번에 요청하면 중간 판단 오류가 마지막 결과까지 전파된다.

다음처럼 단계별 승인 지점을 만든다.

```text
1단계: 자료 목록과 접근 실패 항목 확인
2단계: 역할·요구사항·화면 목록 작성
3단계: 화면 순서와 상태 설계
4단계: 대표 화면 1~2개 구현
5단계: 결과 기준 합의
6단계: 나머지 화면에 패턴 확장
7단계: 전체 검증
```

이 방식은 단지 AI를 천천히 일하게 만드는 것이 아니다. 잘못된 가정을 적은 비용으로 발견하고, 좋은 패턴을 확인한 뒤 반복 적용하는 품질 관리 방식이다.

### 3.9 반복 작업에서 맥락이 나빠지는 이유

한 대화에서 다음 상황이 반복되면 결과가 흔들릴 수 있다.

- 이전 요구와 새 요구가 충돌한다.
- 사용자가 취소한 결과도 대화 기록에 남아 있다.
- 파일의 현재 상태가 대화 속 설명과 달라졌다.
- 긴 로그와 결과 보고서가 핵심 제약보다 더 많은 문맥을 차지한다.
- “이전처럼”이 어느 시점을 가리키는지 모호하다.

이를 줄이는 방법은 새 대화를 무조건 만드는 것이 아니라 현재 상태를 짧은 기준 문서로 다시 고정하는 것이다.

```markdown
# 현재 작업 기준

- 기준 커밋: abc1234
- 수정 대상: frontend/src/routes, frontend/src/layouts
- 폐기된 시도: 새 Figma 페이지 생성 방식
- 유지할 결과: COM-001 대표 화면 구조
- 이번 목표: MAN 화면 3개에 동일 품질 기준 적용
- 완료 검사: 화면 겹침 없음, 번호 일치, build 통과
```

### 3.10 “자체 프롬프팅”보다 명시적 검사표

AI에게 “스스로 최적의 프롬프트를 만든 뒤 작업하라”고 요청하면 내부 사고 과정이 품질을 자동 보장할 것처럼 느껴질 수 있다. 더 재현 가능한 방법은 작업 전후에 확인할 외부 기준을 제공하는 것이다.

```text
작업 전
- 대상 파일과 현재 상태를 읽었는가?
- 중복·누락·충돌을 기록했는가?
- 수정 범위 밖 파일을 식별했는가?

작업 후
- 요구사항별 구현 위치를 확인했는가?
- 테스트와 build가 통과했는가?
- 화면과 실제 데이터 상태를 확인했는가?
- 변경하지 못한 항목을 숨기지 않았는가?
```

품질은 보이지 않는 생각의 길이보다 검증 가능한 결과와 피드백 반복에서 나온다.

### 3.11 대표 샘플로 품질을 먼저 맞춘다

화면 30개를 일괄 생성하기 전에 한 개의 대표 화면을 완성한다.

대표 화면에서 확인할 항목은 다음과 같다.

- 정보 계층
- 컴포넌트 스타일
- 번호와 설명의 연결
- 기본·로딩·빈 상태·오류
- 이전·다음 화면 이동
- 실제 구현 가능성

대표 샘플이 승인된 뒤 그 패턴을 다른 화면에 확장하면 “전체가 만들어졌지만 모두 원하는 수준과 다름”이라는 위험을 줄일 수 있다.

### 3.12 보고서와 실제 변경을 구분한다

AI가 “수정 완료”라고 설명했더라도 다음을 별도로 확인해야 한다.

```text
보고서에 수정했다고 적힘 ≠ 실제 파일이 수정됨
편집 화면에 내용이 보임 ≠ 원격 저장이 완료됨
코드가 생성됨 ≠ build와 테스트가 통과함
테스트 통과 ≠ 사용자 흐름이 올바름
```

외부 상태 변경은 다시 읽어서 검증한다.

- GitHub: 원격 파일과 최신 커밋 재조회
- Git: `git status`, `git diff`, 필요하면 원격 브랜치 확인
- 코드: 타입 검사, 단위 테스트, build
- 웹 UI: 주요 역할과 경로를 실제 클릭
- Figma: 저장 후 레이어와 화면을 다시 확인

### 3.13 코드 작업의 완료 조건 예시

```markdown
## 완료 조건

- 지정된 역할의 화면만 수정한다.
- 기존 API 요청 형식을 유지한다.
- TypeScript 타입 오류가 없다.
- unit test와 build를 실행한다.
- 데이터 로딩·빈 상태·오류 상태를 확인한다.
- `git diff --check`에 공백 오류가 없다.
- 변경 파일, 테스트 결과, 미확인 항목을 최종 보고한다.
```

테스트 명령을 모르면 AI가 저장소 설정을 먼저 확인하도록 한다. 존재하지 않는 명령을 만들어 실행하게 해서는 안 된다.

### 3.14 작업 지시 템플릿

```markdown
# 목표
[최종적으로 달라져야 하는 상태]

# 현재 상태와 근거
- 기준 브랜치·커밋:
- 관련 파일:
- 요구사항·API·디자인 문서:
- 충돌 시 우선순위:

# 수정 범위
- 수정 허용:
- 읽기만 허용:
- 수정 금지:

# 구현 요구사항
1. [기능 또는 화면]
2. [상태와 예외]
3. [보존해야 할 동작]

# 작업 순서
1. 현재 구조를 확인한다.
2. 변경 계획과 영향 파일을 짧게 정리한다.
3. 구현한다.
4. 테스트한다.
5. diff와 결과를 검토한다.

# 완료 조건
- [테스트 또는 build]
- [화면 흐름]
- [외부 저장 확인]
- [남은 제한 보고]
```

이 템플릿을 매번 전부 채울 필요는 없다. 작업이 작다면 목표, 범위, 완료 조건 세 가지로 줄일 수 있다.

## 4. 적용 관점에서 다시 보기

### 상황 1: 특정 담당자의 파일만 수정

1. 담당자 정보가 있는 CSV·이슈·코드 소유 범위를 읽는다.
2. 수정 허용 파일 목록을 먼저 만든다.
3. 공유 컴포넌트 변경이 필요하면 즉시 범위를 넓히지 않고 영향만 보고한다.
4. 허용 범위 안에서 구현과 테스트를 진행한다.
5. `git diff --name-only`로 다른 파일이 바뀌지 않았는지 확인한다.

### 상황 2: 플러그인으로 외부 파일 수정

1. 인증된 계정과 대상 리소스를 확인한다.
2. 조회 기능으로 현재 파일과 버전 식별자를 읽는다.
3. 쓰기 권한이 있는지 확인한다.
4. 변경 직전에 정확한 대상과 내용을 다시 확인한다.
5. 저장 후 같은 파일을 재조회한다.
6. API가 권한을 거부하면 “플러그인 미연결”로 단정하지 않고 읽기·쓰기 권한 차이를 보고한다.

### 상황 3: 반복할수록 결과가 나빠짐

1. 현재 코드·문서를 다시 읽어 실제 상태를 기준으로 삼는다.
2. 유지할 결과와 폐기할 결과를 짧게 명시한다.
3. 다음 한 단계만 수행하도록 범위를 줄인다.
4. 대표 샘플의 완료 기준을 먼저 맞춘다.
5. 결과가 맞으면 같은 패턴을 확장한다.

### 상황 4: UI가 백지로 보임

AI에게 “고쳐 달라”고만 하기보다 다음 증거를 모은다.

- 브라우저 콘솔 오류
- 네트워크 요청 상태와 응답
- 현재 URL과 라우터 매칭
- root 렌더링 여부
- import 경로와 export 방식
- 로딩·오류 상태가 화면에 표시되는지

증거가 있으면 문법, 라우팅, API, CSS 중 어느 계층의 문제인지 좁힐 수 있다.

## 5. 배운 점 / 확장 포인트

### 5.1 새로 이해한 것

- 같은 서비스라도 Connector, CLI, 브라우저는 인증과 권한이 다를 수 있다.
- 조회 성공은 수정 권한의 증거가 아니다.
- 긴 대화는 최신 파일 상태를 대신할 수 없다.
- “스스로 잘 검토하라”보다 검사 가능한 완료 조건이 재현성이 높다.
- 대표 샘플을 먼저 승인하면 대규모 일괄 수정 위험을 줄일 수 있다.

### 5.2 이전·다음 학습과의 연결

이 내용은 Git 브랜치 전략, PR 리뷰, CI, 테스트 피라미드, 요구사항 관리, 디자인 시스템과 연결된다. AI 도구를 사용하더라도 좋은 소프트웨어 개발의 기본인 작은 변경, 자동 검증, 변경 이력, 책임 분리는 그대로 중요하다.

### 5.3 더 확인할 주제

- 저장소의 `AGENTS.md`와 프로젝트 규칙 관리
- 테스트 가능한 acceptance criteria 작성법
- AI 작업을 평가하는 반복 가능한 eval
- 최소 권한 원칙과 OAuth scope
- 컨텍스트가 긴 작업의 체크포인트 문서화

## 6. 요약 정리

1. 실행형 요청은 목표, 근거, 범위, 금지 범위, 완료 조건을 포함한다.
2. 지시는 반복해서 길게 쓰기보다 충돌 없이 한 번씩 명확하게 쓴다.
3. 여러 자료가 있으면 판단 우선순위를 정한다.
4. 읽기 전용 분석과 외부 쓰기 작업을 구분한다.
5. 플러그인, CLI, 브라우저, 로컬 Git은 서로 다른 인증 경로다.
6. 조회 권한과 수정 권한은 별개다.
7. 큰 작업은 분석·대표 샘플·확장·검증 단계로 나눈다.
8. 긴 대화보다 현재 파일과 기준 문서가 우선한다.
9. 완료 보고를 믿는 데서 끝내지 않고 파일·테스트·원격 상태를 다시 확인한다.
10. 보이지 않는 자체 사고보다 외부에서 확인 가능한 검사표가 재현성이 높다.

🧠 기억할 것: AI에게 더 많이 말하는 것보다, 현재 상태와 수정 경계와 완료 증거를 더 분명하게 제공한다.

## 7. 미니 퀴즈 또는 체크리스트

1. GitHub Connector에서 파일 조회가 성공했는데 수정이 `403`인 상황은 무엇을 뜻할 수 있는가?
2. 로컬 `gh` CLI 로그인이 없더라도 브라우저에서 GitHub 편집이 가능한 이유는 무엇인가?
3. 화면 30개를 한 번에 만들기 전에 대표 화면을 먼저 만드는 이유는 무엇인가?
4. “작업 전 자체 프롬프팅”보다 완료 검사표가 재현성이 높은 이유는 무엇인가?
5. AI가 수정 완료라고 보고한 뒤 무엇을 다시 확인해야 하는가?
6. 오래 이어진 작업에서 최신 요구가 흔들릴 때 어떤 기준을 다시 고정해야 하는가?

<summary>정답과 해설</summary>

1. Connector는 연결되어 있고 읽기 권한도 있지만 해당 리소스의 파일 쓰기 권한이 없을 수 있다.
2. CLI와 브라우저는 서로 다른 인증 저장소와 로그인 세션을 사용하기 때문이다.
3. 품질 기준을 작은 범위에서 검증하고 잘못된 패턴이 전체로 퍼지는 것을 막기 위해서다.

5. 실제 diff, 테스트·build, 화면 동작, 원격 파일 또는 커밋 상태를 다시 확인한다.
6. 기준 커밋, 현재 파일, 유지할 결과, 폐기할 시도, 이번 작업 범위와 완료 조건을 고정한다.
