# PEFT·QLoRA·Quantization·TTP 강의노트 통합정리

- 🎯 글의 목표: 대형 언어모델을 **적은 자원으로 학습하고**, 또 **적은 자원으로 추론하는 방법**을 하나의 흐름으로 이해한다.
- 🧩 핵심 키워드: PEFT, LoRA, QLoRA, Unsloth, Quantization, FP16, INT4, BitsAndBytesConfig, double quant, TTP
- ⭐ 중요도: 매우 높음 — 실제로 로컬 GPU나 제한된 VRAM 환경에서 LLM을 다룰 때 바로 써먹는 개념들이다.
- 📝 한눈에 보는 내용: 이 강의는 먼저 **왜 Full Fine-tuning이 부담스러운지**를 짚고, 이를 줄이기 위한 **PEFT와 LoRA**를 설명한다. 그 다음 **양자화된 모델 위에 LoRA를 얹는 QLoRA**로 넘어가고, Unsloth를 이용해 실제 추론과 파인튜닝 과정을 따라간다. 이어서 학습 비용뿐 아니라 **추론 비용을 줄이는 양자화(FP16, INT4)**를 살펴보고, 양자화로 생길 수 있는 품질 저하를 **TTP(Test-Time Prompting)** 로 보완하는 전략까지 연결한다.
- 🔗 관련 문제 / 주제(있다면): 저사양 GPU에서 LLM 학습하기, QLoRA 실습, bitsandbytes 기반 INT4 추론, 환경 변화 입력 대응, 도메인별 프롬프트 설계

## 1. 들어가며

대형 언어모델을 다루다 보면 금방 부딪히는 현실적인 문제가 있다.  
모델은 똑똑하지만, 그대로 학습하거나 그대로 올려서 추론하기에는 너무 크다.  
특히 개인 PC, Colab, 실습용 GPU처럼 자원이 제한된 환경에서는 이 문제가 더 선명하게 드러난다.

여기서 중요한 점은, 비용을 줄이는 방법이 하나만 있는 것이 아니라는 점이다.  
**학습 비용을 줄이는 방법**과 **추론 비용을 줄이는 방법**은 닮아 있으면서도 다르다.

- 학습 비용을 줄일 때는 모든 파라미터를 다 바꾸지 않고, 정말 필요한 작은 부분만 학습시키는 쪽으로 간다.
- 추론 비용을 줄일 때는 이미 있는 모델을 더 낮은 정밀도로 저장하고 계산해서 메모리와 연산량을 줄이는 쪽으로 간다.

이번 자료는 바로 이 두 흐름을 함께 다룬다.  
앞쪽에서는 **PEFT, LoRA, QLoRA** 로 학습 비용을 줄이는 방식을 이해하고, 뒤쪽에서는 **Quantization, FP16, INT4, TTP** 로 추론 비용과 품질 균형을 맞추는 방법을 정리한다.

이 흐름을 한 번에 잡아두면, 이후에 파인튜닝 실습을 하든 배포 환경을 고민하든 판단 기준이 훨씬 분명해진다.  
쉽게 말하면 이 강의는 “모델을 더 작고, 더 싸고, 더 실용적으로 다루는 법”을 단계별로 익히는 과정이라고 볼 수 있다.

## 2. 핵심 개념 정리

이번 강의의 큰 그림은 아래 순서로 이해하면 가장 자연스럽다.

### 2-1. 왜 Full Fine-tuning이 부담스러운가

Foundation Model은 파라미터 수가 너무 크기 때문에, 전체를 다 업데이트하는 Full Fine-tuning은 많은 GPU 메모리와 시간, 데이터를 요구한다.  
그래서 “전부 바꾸지 말고, 필요한 변화만 더하자”는 생각이 나온다.

### 2-2. PEFT와 LoRA는 무엇을 줄이는가

PEFT(Parameter-Efficient Fine-Tuning)는 말 그대로 **적은 파라미터만 학습**하는 방식이다.  
그중 LoRA는 원래 가중치 전체를 다시 배우는 대신, 변화량을 작은 저랭크 행렬로 근사해서 학습한다.

### 2-3. QLoRA는 왜 중요한가

LoRA만 써도 학습 부담이 줄어들지만, 베이스 모델 자체가 크면 여전히 메모리가 부담된다.  
그래서 **베이스 모델을 4비트로 양자화**하고, 그 위에 **LoRA 어댑터만 학습**하는 방식이 QLoRA다.  
이 조합이 실전에서 매우 자주 쓰인다.

### 2-4. Unsloth는 무엇을 도와주는가

Unsloth는 저사양 환경에서도 LoRA/QLoRA 기반 학습과 추론을 더 쉽게 할 수 있도록 돕는 라이브러리다.  
모델 로딩, LoRA 어댑터 부착, 학습 설정, 추론 흐름을 비교적 간단한 코드로 묶어 준다.

### 2-5. 양자화는 학습이 아니라 추론 비용을 줄이는 데도 쓰인다

양자화는 가중치를 FP32, FP16 같은 부동소수점 대신 더 적은 비트 수로 저장해 메모리를 절약하는 방식이다.  
예를 들어 FP16은 FP32보다 절반, INT4는 FP16보다도 훨씬 더 적은 메모리만 사용한다.

### 2-6. 하지만 양자화는 품질과 맞바꾸는 기술이기도 하다

비트 수가 줄어들면 표현 가능한 값의 수가 줄어든다.  
그래서 메모리는 아끼지만, 입력이 조금 흔들리거나 문장이 지저분할 때 응답 품질이 민감해질 수 있다.

### 2-7. TTP는 추론 시점에서 품질을 보완하는 전략이다

모델을 다시 학습하지 않고도, 프롬프트를 더 정교하게 설계하면 응답 품질을 끌어올릴 수 있다.  
특히 양자화 모델처럼 표현력이 조금 줄어든 환경에서는 **규칙 명시, few-shot 예시, 출력 형식 제약**이 꽤 큰 도움이 된다.

이제부터는 이 큰 흐름을 개념별로 차근차근 묶어서 본다.

## 3. 본문 정리

### 3.1 PEFT: 왜 모든 파라미터를 다 학습하지 않는가

**PEFT는 모델 전체를 다시 학습하지 않고, 적은 수의 파라미터만 업데이트해 추가 학습 비용을 줄이는 방법**이다.

대형 모델을 Full Fine-tuning 하면 가장 먼저 드는 생각은 단순하다.  
“좋긴 한데, 너무 무겁다.”  
메모리도 많이 들고, 속도도 느리고, 학습 데이터가 충분하지 않으면 오히려 성능이 흔들릴 수도 있다.

그래서 PEFT는 질문을 바꾼다.

> 정말 모델 전체를 다 바꿔야만 원하는 성능이 나올까?

여기서 핵심은 **모델 전체를 새로 배우는 대신, 필요한 변화만 얹는 것**이다.  
이 발상이 뒤에서 나오는 LoRA와 QLoRA의 출발점이 된다.

💡 포인트: PEFT는 “성능을 조금 포기하는 대신 훨씬 싸게 학습한다”는 개념이 아니라,  
대부분의 실전 상황에서 **충분히 좋은 성능을 훨씬 현실적인 비용으로 얻기 위한 전략**에 가깝다.

⚠️ 주의: PEFT를 단순히 “작은 모델만 쓰는 방법”으로 이해하면 흐름이 틀어진다.  
모델 자체를 줄이는 것은 양자화나 프루닝의 영역이고, PEFT는 **학습되는 파라미터 수를 줄이는 것**에 더 가깝다.

📌 핵심: PEFT의 출발점은 “전체를 다시 배우지 말고, 필요한 변화만 학습하자”이다.

---

### 3.2 LoRA: 큰 가중치 변화량을 작은 행렬 두 개로 근사하기

**LoRA는 원래 가중치 \(W\) 자체를 직접 업데이트하는 대신, 변화량 \(\Delta W\)를 저랭크 행렬 \(A, B\)의 곱으로 근사해 학습하는 방식**이다.

이 개념이 처음에는 추상적으로 느껴질 수 있다.  
막히는 지점은 보통 여기다.

- 왜 굳이 \(\Delta W\)를 따로 생각하는가?
- 왜 작은 행렬 두 개로 근사할 수 있는가?
- 그러면 원래 모델 성능이 많이 깎이지는 않는가?

쉽게 말하면, Full Fine-tuning은 “커다란 표 전체를 다시 쓰는 것”에 가깝고,  
LoRA는 “원래 표는 두고, 수정이 필요한 패턴만 압축해서 적는 것”에 가깝다.

원래의 거대한 가중치 행렬을 전부 바꾸는 대신,  
그 변화량이 갖는 핵심 방향만 작은 차원의 행렬 곱으로 표현하면,  
학습해야 할 파라미터 수를 크게 줄일 수 있다.

예를 들어 매우 큰 \(\Delta W\)가 있다고 해도,  
그 전체를 다 저장하고 학습하는 대신 더 작은 차원의 \(A, B\)만 학습하면 메모리와 계산량이 크게 감소한다.  
강의에서 이 부분을 선형대수 관점으로 풀어주는 이유가 바로 여기에 있다.

#### LoRA를 코드 관점에서 보면

실습에서는 Unsloth의 `get_peft_model()` 로 LoRA 어댑터를 붙였다.  
아래 코드는 강의에서 나온 흐름을 이해하기 좋게 주석을 보강한 형태다.

```python
from unsloth import FastLanguageModel

# 1) 먼저 베이스 모델을 로드합니다.
#    여기서는 4bit 로딩을 켜 두어 QLoRA 형태로 이어질 수 있게 준비합니다.
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen3-4B-Instruct-2507",
    max_seq_length=2048,
    load_in_4bit=True,     # 베이스 모델을 4비트로 로드
    load_in_8bit=False,
    full_finetuning=False, # 전체 파라미터 학습은 하지 않음
)

# 2) LoRA 어댑터를 베이스 모델 위에 추가합니다.
#    실제로 학습되는 것은 이 LoRA 관련 파라미터들입니다.
model = FastLanguageModel.get_peft_model(
    model,
    r=32,                  # 저랭크 차원. 클수록 표현력은 늘지만 비용도 증가
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj",
    ],
    lora_alpha=32,         # LoRA 출력 스케일 조절
    lora_dropout=0,        # 드롭아웃. 실습에서는 0으로 둠
    bias="none",           # bias는 학습하지 않음
    use_gradient_checkpointing="unsloth",  # 긴 문맥에서 메모리 절약
    random_state=3407,
    use_rslora=False,
    loftq_config=None,
)
```

여기서 중요한 점은 `target_modules`다.  
LoRA는 모델 전체 아무 데나 붙이는 것이 아니라, 주로 attention/MLP 내부의 핵심 선형층에 붙여서 변화를 학습한다.

#### 왜 필요한가 / 어디서 막히는가

LoRA를 처음 배울 때 자주 생기는 오해는 “작게 학습하면 당연히 성능도 크게 손해 보지 않을까?” 하는 것이다.  
하지만 실제로는 많은 태스크에서 **전체를 다시 학습하지 않아도 충분히 좋은 적응 성능**이 나온다.  
특히 도메인 적응, 스타일 변환, 특정 포맷 응답처럼 “모델의 성격을 조금 조정하는 문제”에서는 LoRA가 매우 강력하다.

⚠️ 주의: `r` 값을 무조건 크게 잡는다고 항상 좋은 것은 아니다.  
표현력은 늘 수 있지만, VRAM 사용량과 학습 시간도 함께 늘어난다.  
실습용 환경에서는 먼저 작은 값으로 시작하고, 성능이 부족할 때 점진적으로 늘리는 쪽이 안전하다.

📌 핵심: LoRA는 “모델 전체를 다시 배우는 것”이 아니라, “필요한 변화량만 작은 저랭크 구조로 학습하는 것”이다.

### 3.3 QLoRA: 양자화된 베이스 모델 위에 LoRA를 얹는 방식

**QLoRA는 4비트로 양자화된 베이스 모델을 사용하고, 그 위에 LoRA 어댑터만 학습하는 방식**이다.

LoRA를 이해한 다음 자연스럽게 생기는 질문은 이것이다.

> LoRA는 학습 파라미터 수를 줄여 주는데, 베이스 모델 자체가 너무 크면 그건 어떻게 하나?

바로 여기서 QLoRA가 나온다.  
베이스 모델을 16비트나 32비트로 그대로 두지 않고, **4비트로 양자화해서 메모리 부담을 먼저 줄인 다음**,  
추가 학습은 LoRA 어댑터에만 걸어 준다.

쉽게 말하면 다음과 같다.

- **LoRA**: 바꾸는 파라미터 수를 줄인다.
- **QLoRA**: 바꾸는 파라미터 수도 줄이고, 베이스 모델을 들고 있는 비용도 줄인다.

이 조합이 강력한 이유는 아주 현실적이다.  
개인 GPU나 Colab T4 같은 환경에서도 “생각보다 큰 모델”을 다룰 수 있게 해 주기 때문이다.

#### QLoRA의 감각을 코드에서 확인하기

실습에서 모델 로딩은 아래처럼 진행됐다.

```python
from unsloth import FastLanguageModel

# QLoRA의 출발점: 베이스 모델을 4bit로 로드
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen3-4B-Instruct-2507",
    max_seq_length=2048,
    load_in_4bit=True,     # 핵심: 베이스 모델을 4비트 양자화 상태로 로드
    load_in_8bit=False,
    full_finetuning=False,
)
```

여기서 `load_in_4bit=True` 가 QLoRA의 핵심 단서다.  
이후 LoRA 어댑터를 부착하면,  
“4비트 양자화된 베이스 모델 + 학습 가능한 LoRA 어댑터” 구조가 된다.

#### 왜 중요한가

강의에서 “LoRA가 파인튜닝을 대중화했다”는 표현이 나오는 이유가 여기에 있다.  
예전에는 대형 모델의 추가 학습이 사실상 대규모 서버 자원을 가진 환경에 더 가까웠다면,  
이제는 QLoRA 덕분에 개인도 훨씬 현실적인 비용으로 실험할 수 있게 되었다.

⚠️ 주의: QLoRA는 “4비트 모델 전체를 마음대로 다시 학습하는 것”이 아니다.  
보통은 양자화된 베이스는 고정하고, **LoRA 파라미터만 학습**한다는 구조를 함께 이해해야 한다.

📌 핵심: QLoRA는 “양자화로 베이스 모델 비용을 낮추고, LoRA로 학습 비용까지 줄이는 조합”이다.

### 3.4 Unsloth로 파인튜닝 흐름 잡기: 모델, 데이터, 템플릿, 트레이너

**실전 파인튜닝은 모델을 불러오는 것만으로 끝나지 않고, 데이터 형식과 학습 포맷을 모델이 기대하는 구조에 맞게 정리하는 과정까지 포함한다.**

강의의 실습 예시는 “제주도 사투리 번역기 만들기”였다.  
이 예제가 좋은 이유는, 단순한 분류 문제가 아니라 **대화형 LLM의 입력/출력 구조**를 그대로 다루기 때문이다.

여기서 중요한 흐름은 네 단계다.

1. 데이터셋 로드
2. 대화 형식(`conversations`)으로 변환
3. 모델 전용 chat template에 맞게 문자열화
4. SFTTrainer로 학습

이 흐름을 놓치면 “모델은 로드됐는데 왜 학습이 이상하지?” 같은 문제가 생기기 쉽다.

#### 데이터 포맷을 대화형 구조로 바꾸기

```python
from datasets import load_dataset

# 1) 원본 데이터셋 로드
#    실습에서는 제주도 사투리 번역 데이터를 사용했습니다.
dataset_origin = load_dataset(
    "junyeong-nero/jeju-dialect-to-standard",
    split="train[:10000]"   # 데모를 위해 일부만 사용
)

# 2) 원본 컬럼을 대화형 학습 포맷으로 바꿉니다.
#    user는 표준어 문장을 주고, assistant는 제주도 사투리 번역을 답하게 합니다.
def format_jeju_data(example):
    return {
        "conversations": [
            {
                "role": "user",
                "content": f"다음 문장을 제주도 사투리로 번역해줘:\n\n{example['standard']}"
            },
            {
                "role": "assistant",
                "content": example["dialect"]
            },
        ]
    }

dataset = dataset_origin.map(
    format_jeju_data,
    remove_columns=list(dataset_origin.features)
)
```

이 코드에서 중요한 점은, 데이터를 그냥 입력-정답 쌍으로만 보지 않고  
**모델이 실제로 대화하듯 읽을 수 있는 구조로 바꾼다**는 것이다.

#### chat template에 맞게 최종 텍스트 만들기

모델마다 자신이 학습할 때 쓰던 대화 형식이 조금씩 다르다.  
그래서 같은 내용이라도 템플릿이 맞지 않으면 성능이 흔들릴 수 있다.

```python
from unsloth.chat_templates import get_chat_template

# 3) 모델이 기대하는 대화 템플릿을 토크나이저에 연결합니다.
tokenizer = get_chat_template(
    tokenizer,
    chat_template="qwen3-instruct",
)

# 4) conversations 구조를 실제 학습용 텍스트로 변환합니다.
def formatting_prompts_func(examples):
    convos = examples["conversations"]
    texts = [
        tokenizer.apply_chat_template(
            convo,
            tokenize=False,
            add_generation_prompt=False
        )
        for convo in convos
    ]
    return {"text": texts}

dataset = dataset.map(formatting_prompts_func, batched=True)
```

여기서 자주 막히는 지점은 `conversations` 를 만들고 끝내 버리는 경우다.  
하지만 실제 학습에서는 모델이 읽을 **최종 문자열 포맷**이 필요하다.  
즉, “대화 구조를 만들었다”와 “모델이 읽는 텍스트가 준비됐다”는 서로 다른 단계다.

#### SFTTrainer로 학습 연결하기

```python
from trl import SFTTrainer, SFTConfig
from unsloth.chat_templates import train_on_responses_only

# 5) 학습 설정
trainer = SFTTrainer(
    model=model,
    tokenizer=tokenizer,
    train_dataset=dataset,
    eval_dataset=None,
    args=SFTConfig(
        dataset_text_field="text",
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,  # 작은 GPU에서도 큰 배치 효과를 흉내냄
        warmup_steps=5,
        max_steps=60,
        learning_rate=2e-4,
        logging_steps=1,
        optim="adamw_8bit",
        weight_decay=0.01,
        lr_scheduler_type="linear",
        seed=3407,
        report_to="none",
    ),
)

# 6) 질문 부분은 맞추라고 시키는 대상이 아니므로,
#    assistant 응답 부분만 학습 대상으로 삼게 만듭니다.
trainer = train_on_responses_only(
    trainer,
    instruction_part="<|im_start|>user\n",
    response_part="<|im_start|>assistant\n",
)

# 7) 학습 시작
trainer_stats = trainer.train()
```

이 부분은 실전 감각에서 특히 중요하다.  
LLM은 “질문과 답변이 함께 있는 텍스트”를 읽지만,  
우리가 정말 예측하게 만들고 싶은 것은 **답변 부분**이다.  
그래서 `train_on_responses_only()` 같은 처리가 들어간다.

#### 자주 하는 실수 / 디버깅 포인트

- 데이터 컬럼은 맞는데 chat template가 안 맞는 경우  
- `add_generation_prompt` 옵션을 학습/추론에서 뒤섞어 쓰는 경우  
- 질문 부분까지 같이 학습 손실에 포함되어 결과가 이상해지는 경우  
- 배치 크기를 너무 크게 잡아 VRAM이 터지는 경우  
- loss가 잘 줄지 않는데 데이터 품질 문제인지 템플릿 문제인지 구분하지 않는 경우

⚠️ 주의: loss가 줄지 않는다고 무조건 모델 문제가 아니다.  
대부분은 **데이터 포맷, 템플릿, 응답 전용 학습 처리** 중 하나가 어긋난 경우가 많다.

📌 핵심: 파인튜닝 성패는 모델 선택만이 아니라, **데이터를 모델이 기대하는 대화 구조로 정확히 바꾸는 과정**에 크게 달려 있다.

### 3.5 양자화: 숫자 표현을 줄여 메모리와 연산량을 낮추기

**양자화는 모델 가중치를 더 적은 비트 수의 숫자로 표현해 메모리 사용량과 연산 부담을 줄이는 기술**이다.

PEFT와 QLoRA가 “학습 비용 줄이기” 쪽의 이야기였다면,  
이제부터는 “추론 비용 줄이기” 쪽의 이야기다.

강의에서 먼저 FP32, FP16, INT8, INT4를 비교한 이유는 단순하다.  
양자화는 결국 “숫자를 어떻게 저장하느냐”의 문제이기 때문이다.

### 비트 정밀도 감각 잡기

| 형식 | 비트 수 | 파라미터 1개당 대략 메모리 | 특징 |
|---|---:|---:|---|
| FP32 | 32비트 | 4바이트 | 기준이 되는 고정밀 형식 |
| FP16 | 16비트 | 2바이트 | 메모리 절반, 추론에서 자주 사용 |
| INT8 | 8비트 | 1바이트 | 더 큰 절감, 비교적 품질 안정적 |
| INT4 | 4비트 | 0.5바이트 | 매우 큰 절감, 대신 정밀도 손실 가능 |

예를 들어 1B 파라미터 모델이라면 대략 아래 감각으로 보면 된다.

- FP32: 약 4GB
- FP16: 약 2GB
- INT8: 약 1GB
- INT4: 약 0.5GB

강의에서는 7B 모델 예시도 다뤘는데, 이 경우 FP32로는 너무 무겁고, FP16만 가도 절반으로 줄어든다.  
즉, 양자화는 단순 최적화가 아니라 **아예 모델을 올릴 수 있느냐 없느냐를 갈라 주는 기술**이 되기도 한다.

#### 메모리 계산 예시 코드

```python
# 70억(7B) 파라미터 기준 대략적인 메모리 계산
params = 7e9

fp32_gb = params * 4 / 1e9    # FP32: 파라미터당 4바이트
fp16_gb = params * 2 / 1e9    # FP16: 파라미터당 2바이트
int8_gb = params * 1 / 1e9    # INT8: 파라미터당 1바이트
int4_gb = params * 0.5 / 1e9  # INT4: 파라미터당 0.5바이트

print(f"FP32: {fp32_gb:.1f} GB")
print(f"FP16: {fp16_gb:.1f} GB")
print(f"INT8: {int8_gb:.1f} GB")
print(f"INT4: {int4_gb:.1f} GB")
```

이 계산은 아주 단순화된 감각용 계산이지만,  
실무 판단에서는 이 정도 감각만 있어도 “지금 환경에서 어떤 정밀도를 써야 할지” 빠르게 감을 잡을 수 있다.

#### 왜 필요한지 / 어디서 막히는지

양자화는 “모델을 작게 만드는 기술”로만 이해하면 절반만 이해한 것이다.  
핵심은 **작게 만들기 위해 표현 가능한 숫자 레벨을 줄이는 것**이다.  
그래서 메모리는 줄지만, 세밀한 수치 표현이 덜 가능해질 수 있다.

⚠️ 주의: FP16은 흔히 “양자화”라고 넓게 묶어 설명되기도 하지만,  
실무 맥락에서는 보통 **저정밀 부동소수점 사용**과 **정수 기반 양자화(INT8, INT4)** 를 구분해서 생각하는 편이 더 명확하다.

📌 핵심: 양자화는 숫자 표현 비트를 줄여 비용을 낮추는 기술이며, 그 대가로 일부 정밀도를 포기한다.

### 3.6 FP16과 INT4: 어디까지 줄일 것인가

**FP16은 비교적 안전하게 메모리를 절반으로 줄이는 선택이고, INT4는 훨씬 과감하게 메모리를 줄이는 대신 더 민감한 품질 손실 가능성을 감수하는 선택**이다.

강의에서는 FP16 모델을 먼저 로드해서 “문제가 얼마나 큰지”를 체감하고,  
그 다음 INT4 모델을 로드해 실제 차이를 비교하도록 구성되어 있었다.  
이 순서가 중요한 이유는, INT4의 장점을 이해하려면 먼저 FP16도 여전히 꽤 무겁다는 사실을 느껴야 하기 때문이다.

#### FP16 추론 측정 흐름

```python
import time
import torch

def measure_inference(model, tokenizer, prompt, max_new_tokens=128):
    """단일 프롬프트에 대해 응답, 지연 시간, 피크 메모리를 측정합니다."""

    # 추론 직전 상태를 맞춥니다.
    torch.cuda.synchronize()
    torch.cuda.reset_peak_memory_stats()

    # 채팅 입력을 모델 포맷에 맞게 토큰화합니다.
    messages = [{"role": "user", "content": prompt}]
    inputs = tokenizer.apply_chat_template(
        messages,
        return_tensors="pt",
        return_dict=True,
        add_generation_prompt=True,
    )

    # 입력을 모델이 올라가 있는 디바이스로 옮깁니다.
    input_ids = inputs["input_ids"].to(model.device)
    input_length = input_ids.shape[1]

    # 샘플링 기반 생성 설정
    torch.manual_seed(42)
    start_time = time.time()

    with torch.no_grad():
        outputs = model.generate(
            input_ids,
            max_new_tokens=max_new_tokens,
            do_sample=True,
            temperature=0.7,
            top_p=0.95,
            pad_token_id=tokenizer.eos_token_id,
        )

    torch.cuda.synchronize()
    end_time = time.time()

    # 피크 메모리는 "추론 중 가장 많이 쓴 순간"을 보여줍니다.
    peak_memory_gb = torch.cuda.max_memory_allocated() / 1024**3

    # 입력 이후 생성된 부분만 잘라 응답으로 디코딩합니다.
    response = tokenizer.decode(
        outputs[0][input_length:],
        skip_special_tokens=True,
    )

    latency = end_time - start_time
    return response, latency, peak_memory_gb
```

이 함수는 이후 INT4 비교, 환경 변화 입력 테스트, TTP 적용까지 계속 재사용된다.  
즉, 이 실습의 중심축은 “모델을 바꿔 가며 같은 방식으로 측정한다”는 점에 있다.

#### INT4 양자화 모델 로딩

```python
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
import torch

model_name = "Qwen/Qwen2.5-1.5B-Instruct"

# 4비트 양자화 설정
quantization_config = BitsAndBytesConfig(
    load_in_4bit=True,                    # 4비트 양자화 활성화
    bnb_4bit_quant_type="nf4",            # NF4: 가중치 분포에 잘 맞는 4비트 방식
    bnb_4bit_compute_dtype=torch.float16, # 계산은 FP16으로 수행
    bnb_4bit_use_double_quant=True,       # 양자화 상수도 다시 양자화
)

tokenizer = AutoTokenizer.from_pretrained(model_name)

# 양자화된 모델 로딩
model_int4 = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=quantization_config,
    device_map="auto",
)
```

여기서 가장 자주 나오는 설정이 바로 아래 네 가지다.

- `load_in_4bit=True`
- `bnb_4bit_quant_type="nf4"`
- `bnb_4bit_compute_dtype=torch.float16`
- `bnb_4bit_use_double_quant=True`

#### 각 설정이 의미하는 것

- **load_in_4bit**: 가중치를 4비트로 저장
- **bnb_4bit_quant_type="nf4"**: 정규분포에 가까운 가중치 분포에 적합한 4비트 양자화 방식
- **bnb_4bit_compute_dtype=torch.float16**: 저장은 4비트지만 실제 계산은 FP16으로 수행
- **double_quant=True**: 양자화할 때 필요한 스케일 정보도 다시 양자화하여 추가 메모리 절감

이 설정은 처음 보면 낯설지만, 결국 질문은 하나다.  
**“어디까지 저장 비용을 줄이되, 계산 품질은 어느 정도 지킬 것인가?”**

#### 실수 포인트

- 저장 비트와 계산 비트를 같은 개념으로 이해하는 경우  
- `device_map="auto"` 없이 메모리 분산을 제대로 못 시키는 경우  
- INT4만 켜면 모든 문제가 자동 해결된다고 생각하는 경우  
- 모델 메모리와 추론 피크 메모리를 구분하지 않는 경우

⚠️ 주의: 모델이 차지하는 메모리와, 생성 중 일시적으로 치솟는 피크 메모리는 다르다.  
실전에서 OOM이 나는 이유는 종종 “모델 로딩은 됐는데 생성 도중 피크가 터져서” 이기도 하다.

📌 핵심: INT4는 저장 비용을 크게 낮추는 강력한 수단이지만, 계산 정밀도와 응답 안정성까지 함께 고려해야 한다.

### 3.7 양자화를 행렬 수준에서 이해하기: 왜 오차가 생기는가

**양자화의 본질은 실수값을 더 적은 정수 격자에 맞춰 반올림하는 과정이며, 이때 생기는 근사 오차가 결국 모델 품질 변화로 이어진다.**

초보자 실습에서는 행렬곱으로 양자화를 직접 체험하게 했다.  
이 부분이 좋은 이유는, 거대한 LLM 내부에서도 결국 많은 계산이 “입력 행렬 × 가중치 행렬” 형태로 일어난다는 감각을 주기 때문이다.

#### 대칭 양자화의 기본 아이디어

```python
import numpy as np

def quantize_symmetric(x, num_bits=8):
    """
    대칭 양자화:
    - 절댓값 최대치를 기준으로 스케일을 정합니다.
    - float 값을 정수 범위로 반올림합니다.
    """
    qmax = 2 ** (num_bits - 1) - 1
    qmin = -qmax
    scale = np.max(np.abs(x)) / qmax if np.max(np.abs(x)) != 0 else 1.0
    x_q = np.round(x / scale).clip(qmin, qmax).astype(np.int32)
    return x_q, scale

def dequantize(x_q, scale):
    """정수 격자 값을 다시 float 값으로 복원합니다."""
    return x_q.astype(np.float32) * scale
```

이 코드의 흐름은 단순하다.

1. 원래 실수 행렬의 최대 절댓값을 본다.
2. 정수 범위(INT8이면 대략 -127~127)에 맞는 `scale`을 만든다.
3. 실수값을 `scale`로 나눠 정수칸에 맞게 반올림한다.
4. 필요하면 다시 곱해서 float 근사값으로 복원한다.

#### 왜 INT4가 INT8보다 더 거칠어지는가

INT8은 표현 가능한 정수 칸 수가 더 많고,  
INT4는 그보다 훨씬 적다.  
즉, 같은 실수값을 저장할 때 INT4는 더 거친 칸에 반올림할 수밖에 없다.

쉽게 말하면,

- INT8은 더 촘촘한 바둑판
- INT4는 더 성긴 바둑판

위에 좌표를 찍는 것과 비슷하다.

그래서 행렬곱 결과를 비교해 보면, 대체로 다음 흐름이 나온다.

- 원래 float 결과
- 가중치만 INT8로 양자화한 결과 → 약간 차이
- 입력과 가중치를 둘 다 INT8로 양자화한 결과 → 차이가 더 커짐
- INT4로 낮추면 → 차이가 더 커질 가능성

⚠️ 주의: “오차가 생긴다 = 무조건 못 쓴다”는 뜻은 아니다.  
실전에서는 **얼마나 줄였는지 대비 실제 성능 저하가 감당 가능한지**를 본다.

📌 핵심: 양자화 품질 저하는 추상적인 현상이 아니라, 결국 “실수값을 더 거친 정수칸에 맞춰 저장할 때 생기는 근사 오차”에서 온다.

---

### 3.8 double quant와 INT8 vs INT4 비교: 메모리와 품질의 균형

**INT8과 INT4의 비교는 결국 “얼마나 더 줄일 것인가”와 “그 대가로 품질을 얼마나 감수할 것인가”의 균형 문제**다.

강의 과제에서는 FP16 vs INT4에서 한 단계 더 나아가, **INT8 vs INT4** 비교까지 다뤘다.  
그리고 추가로 `double_quant=True/False` 도 비교했다.

#### INT8과 INT4의 감각적 비교

| 항목 | INT8 | INT4 |
|---|---|---|
| 메모리 절감 | 큼 | 매우 큼 |
| 품질 손실 가능성 | 비교적 낮음 | 더 큼 |
| 실전 안정성 | 높음 | 입력 흔들림에 더 민감할 수 있음 |
| 추천 상황 | 품질이 더 중요한 서비스 | 비용/메모리 최적화가 더 중요한 서비스 |

INT8은 “좀 더 안전한 절충안”에 가깝고,  
INT4는 “더 과감한 절감”에 가깝다.

#### double quant는 무엇을 더 줄이는가

보통 양자화하면 가중치만 줄인다고 생각하기 쉽다.  
하지만 실제로는 양자화 과정에서 필요한 스케일 같은 부가 정보도 메모리를 먹는다.  
`double_quant=True` 는 이 **양자화 상수들까지 다시 양자화** 해서 오버헤드를 줄이는 방식이다.

쉽게 말하면 “압축을 위한 메타데이터도 다시 압축하는 느낌”에 가깝다.

```python
from transformers import BitsAndBytesConfig
import torch

# double quant 비활성화
int4_no_double_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.float16,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=False,
)

# double quant 활성화
int4_double_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.float16,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
)
```

#### 어디서 막히는가

초반에는 `double_quant=True` 가 “정확도도 두 번 양자화해서 더 나빠지는 것 아닌가?”처럼 보일 수 있다.  
하지만 여기서의 핵심은 **가중치 본체뿐 아니라 양자화에 필요한 정보까지 더 효율적으로 저장**한다는 점이다.

⚠️ 주의: 양자화 설정은 항상 “낮을수록 좋다”가 아니다.  
서비스 성격이 다르면 선택도 달라진다.

- 품질이 민감하면 INT8 쪽이 낫다.
- 메모리가 가장 빡빡하면 INT4가 필요할 수 있다.
- 같은 INT4라도 `double_quant=True` 가 유리한 경우가 많다.

📌 핵심: INT8과 INT4는 우열 관계가 아니라 트레이드오프 관계이며, `double_quant` 는 INT4를 좀 더 실용적으로 만드는 보조 장치다.

---

### 3.9 양자화 모델이 환경 변화 입력에 취약한 이유

**양자화 모델은 숫자 표현이 거칠어지는 만큼, 입력이 깔끔하지 않을 때 내부 표현이 흔들릴 가능성이 더 커진다.**

강의에서 특히 인상적인 지점은, 단순히 “메모리가 줄었다”에서 끝나지 않고  
**환경 변화 입력**을 넣어 본다는 점이었다.

환경 변화 입력은 예를 들어 이런 것들이다.

- 오타가 포함된 문장
- 노이즈가 섞인 문장
- 모호한 표현
- 불완전한 질문
- 평소와 다른 입력 형식

예를 들어 교통 도메인에서는 아래 같은 테스트 샘플이 들어간다.

- 정상 문장
- 오타가 섞인 질문
- 노이즈가 많은 문장
- 모호한 질문

그리고 의료 도메인 과제에서는 다음처럼 확장된다.

- “두통이 3일째 계속되고 있습니다. 어떻게 해야 하나요?”  
- “두통이 3일쩨 게속되고 잇습니다. 어떠게 해야 하나요?”  
- “머리가 좀 그래요. 어떻게 해야 해요?”  
- “음... 그러니까... 두통이 있는데요... 뭐랄까... 어떻게 하죠?”

이 실험이 중요한 이유는, 실서비스 입력은 항상 깔끔하지 않기 때문이다.

#### 왜 더 취약해질까

양자화는 원래 float 공간의 세밀한 차이를 더 거친 표현으로 바꾸는 과정이다.  
그래서 정상 입력에서는 큰 문제 없이 버티더라도,  
입력이 애매하거나 흔들리면 그 미세한 차이를 더 잘 잃어버릴 수 있다.

쉽게 말하면,  
해상도가 조금 낮아진 지도에서 깨끗한 길은 잘 보이지만  
흐릿한 길은 더 잘 놓치게 되는 것과 비슷하다.

#### 환경 변화 테스트 흐름

```python
# 환경 변화 입력 샘플을 순회하며 응답 품질을 비교합니다.
env_change_results = []

for sample in test_samples:
    response, latency, _ = measure_inference(
        model_int4,
        tokenizer,
        sample["prompt"],
        max_new_tokens=100,
    )

    env_change_results.append({
        "type": sample["type"],
        "prompt": sample["prompt"],
        "response": response,
        "latency": latency,
    })
```

이 코드는 특별히 복잡하지 않지만, 실험 설계 관점에서 중요하다.  
**같은 모델에 입력만 바꿔 넣어 본다**는 점에서,  
양자화가 실제 사용자 환경에서 어떤 한계를 가질 수 있는지 확인하게 해 주기 때문이다.

⚠️ 주의: 응답이 이상하다고 해서 무조건 모델이 나쁘다고 결론내리면 안 된다.  
입력이 흔들렸을 때, **모델이 그 흔들림을 얼마나 견디는지**를 보는 것이 핵심이다.

📌 핵심: 양자화는 비용을 줄여 주지만, 입력이 지저분할수록 그 대가가 더 눈에 띄게 나타날 수 있다.

---

### 3.10 TTP(Test-Time Prompting): 학습 없이 추론 품질을 보완하기

**TTP는 모델을 다시 학습하지 않고, 추론 시점의 프롬프트 설계를 바꿔 응답 품질을 높이는 전략**이다.

양자화로 비용을 줄였는데 입력이 흔들릴 때 응답이 불안정해진다면,  
가장 먼저 떠올릴 수 있는 대응은 모델 재학습일 수 있다.  
하지만 그건 비용이 크다.

그래서 더 빠른 대응으로 등장하는 것이 TTP다.  
질문을 그대로 던지는 대신, 모델이 더 잘 답할 수 있도록 **규칙, 예시, 출력 형식**을 함께 제공한다.

#### 규칙 명시형 TTP

```python
TTP_A_TEMPLATE = """다음 질문에 답해주세요.

규칙:
1. 오타나 불명확한 표현이 있어도 의도를 파악하세요.
2. 교통 관련 질문은 대략적인 소요 시간(시간 단위)으로 답하세요.
3. 맥락이 부족하면 일반적인 상황을 가정하여 답하세요.
4. 간결하게 핵심만 답하세요.

질문: {question}

답변:"""
```

이 방식의 핵심은 “어떻게 답해야 하는지”를 명확히 고정하는 데 있다.  
특히 오타, 모호함, 노이즈가 있는 입력에서는 이런 규칙형 프롬프트가 꽤 큰 도움이 된다.

#### few-shot 기반 TTP

```python
TTP_B_TEMPLATE = """다음은 교통 관련 질문과 답변의 예시입니다.

예시:
Q: 서울역에서 대전역까지 KTX로 얼마나 걸려요?
A: 서울역에서 대전역까지 KTX로 약 50분~1시간 정도 소요됩니다.

이제 아래 질문에 동일한 형식으로 답해주세요.

질문: {question}

답변:"""
```

few-shot 방식은 모델에게 “이런 패턴으로 답하라”는 예시를 직접 보여 준다.  
규칙형이 추상적인 제약을 준다면, few-shot은 **구체적인 답변 스타일**을 보여 준다고 보면 된다.

#### TTP 적용 함수

```python
def apply_ttp(template, question):
    """프롬프트 템플릿의 자리 표시자에 실제 질문을 삽입합니다."""
    return template.format(question=question)
```

이 함수 자체는 단순하지만,  
강의에서 굳이 `str.format()` 을 짚어 준 이유는 템플릿 기반 추론 실험이 반복되기 때문이다.  
즉, 모델을 바꾸지 않고도 프롬프트만 바꿔 비교 실험을 돌릴 수 있게 해 준다.

#### 의료 도메인처럼 민감한 영역에서는 더 중요하다

과제에서는 의료 도메인용 TTP를 직접 설계하게 했다.  
이런 도메인에서는 규칙이 더 중요해진다.

예를 들면 아래 같은 규칙을 넣을 수 있다.

- 증상이 불명확하면 추가 확인이 필요하다고 말할 것
- 응급 신호가 보이면 즉시 병원 방문을 권할 것
- 단정적 진단은 피할 것
- 한국어로, 간결하게 답할 것

즉, TTP는 단순히 말투를 예쁘게 만드는 기술이 아니라  
**모델이 어떤 안전 규칙과 응답 형식을 따라야 하는지 명시하는 장치**가 될 수 있다.

#### 자주 하는 실수

- 템플릿은 길게 만들었는데 규칙이 모호한 경우  
- few-shot 예시가 실제 태스크와 맞지 않는 경우  
- 출력 형식 제약이 없어 응답 패턴이 흔들리는 경우  
- 민감한 도메인인데 안전 문구나 불확실성 처리가 없는 경우

⚠️ 주의: TTP는 만능이 아니다.  
하지만 “재학습 없이 지금 당장 응답 품질을 올리는 가장 싼 방법”이라는 점에서 실무 가치가 높다.

📌 핵심: TTP는 양자화나 저비용 추론 환경에서 떨어질 수 있는 품질을, 프롬프트 설계만으로 빠르게 보완하는 전략이다.

## 4. 적용 관점에서 다시 보기

앞의 내용을 실전 판단 기준으로 다시 묶어 보면, 결국 질문은 세 가지다.

1. 지금 내가 줄이고 싶은 비용은 **학습 비용**인가, **추론 비용**인가?
2. 현재 환경에서 가장 먼저 부족한 것은 **VRAM**, **속도**, **품질 안정성** 중 무엇인가?
3. 모델을 다시 학습시킬 여유가 있는가, 아니면 **프롬프트 수준 대응**이 필요한가?

### 4-1. 어떤 상황에서 LoRA / QLoRA를 떠올리면 되는가

아래 같은 신호가 보이면 LoRA나 QLoRA를 먼저 떠올리면 된다.

- 특정 태스크나 도메인에 모델을 맞추고 싶다.
- Full Fine-tuning은 너무 무겁다.
- 작은 GPU로도 실험 가능한 수준에서 학습하고 싶다.
- 베이스 모델 전체를 바꾸기보다 적응만 시키고 싶다.

구현 순서는 대체로 아래처럼 잡으면 안정적이다.

1. 베이스 모델 선정
2. 4bit 로딩 가능 여부 확인
3. LoRA target modules 결정
4. 데이터셋을 대화형 포맷으로 변환
5. chat template 적용
6. 응답 부분만 학습하도록 설정
7. 짧은 스텝으로 먼저 검증
8. loss, 샘플 생성 결과, 저장 전략 점검

### 4-2. 어떤 상황에서 FP16 / INT8 / INT4를 떠올리면 되는가

#### FP16
- 비교적 안전하게 메모리를 절반 수준으로 줄이고 싶을 때
- 품질 손실은 최소화하고 싶을 때
- GPU 메모리가 아주 타이트하지는 않을 때

#### INT8
- 품질과 메모리 사이에서 균형을 잡고 싶을 때
- INT4까지 내리기에는 응답 안정성이 걱정될 때
- 서비스 품질이 꽤 중요한 편일 때

#### INT4
- 메모리 제약이 매우 심할 때
- 더 큰 모델을 어떻게든 올려야 할 때
- 약간의 품질 손실을 감수할 수 있을 때
- 가능하면 `double_quant=True` 까지 함께 고려할 때

### 4-3. 어떤 상황에서 TTP를 먼저 써 보면 좋은가

- 입력에 오타, 노이즈, 모호함이 자주 섞인다.
- 재학습까지 가기 전에 빠른 개선이 필요하다.
- 도메인별 안전 규칙이나 출력 형식을 강하게 요구한다.
- 같은 모델이라도 서비스 상황에 맞는 응답 패턴이 필요하다.

구현 순서를 짧게 정리하면 이렇다.

1. 흔들리는 입력 유형을 먼저 분류한다.
2. 규칙형 템플릿과 few-shot 템플릿을 각각 만들어 본다.
3. 정상 입력 / 오타 / 모호함 / 노이즈 입력으로 비교한다.
4. 품질과 응답 길이, 일관성을 함께 본다.
5. 효과가 확인되면 도메인별 템플릿으로 확장한다.

### 4-4. 실전에서 자주 틀리는 패턴

- QLoRA와 일반 양자화 추론을 같은 것으로 이해하는 경우  
- 저장 비트와 계산 비트를 구분하지 않는 경우  
- 데이터 포맷보다 모델 선택만 신경 쓰는 경우  
- 양자화만 하면 모든 비용 문제가 해결된다고 생각하는 경우  
- TTP를 너무 길게 써서 오히려 출력이 산만해지는 경우  
- 민감한 도메인인데 few-shot 예시 없이 막연한 규칙만 넣는 경우

🧠 기억할 것:  
학습 비용 문제에는 **PEFT/LoRA/QLoRA**,  
추론 비용 문제에는 **FP16/INT8/INT4**,  
입력 흔들림 대응에는 **TTP** 를 먼저 떠올리면 전체 구조가 정리된다.

## 5. 배운 점 / 느낀 점 / 확장 포인트

이번 강의의 가장 큰 장점은, 파인튜닝과 양자화를 따로 떼어 설명하지 않고  
“자원 제약이 있는 환경에서 모델을 어떻게 운용할 것인가”라는 하나의 문제로 묶어 보여 준다는 점이다.

특히 배운 점은 세 가지다.

첫째, LLM 실습에서 가장 중요한 것은 단순히 좋은 모델을 고르는 것이 아니라,  
**내 자원 한도 안에서 어떤 조합이 가능한지 판단하는 능력**이라는 점이다.  
LoRA, QLoRA, INT4, TTP는 모두 그 판단을 위한 도구들이다.

둘째, 파인튜닝 성능은 모델 자체만이 아니라  
**데이터 포맷, chat template, 학습 대상 구간 분리**에 크게 좌우된다는 점이 선명하다.  
LLM은 입력 형식에 민감하기 때문에, 데이터 전처리와 학습 구조 설정이 매우 중요하다.

셋째, 양자화는 단순한 속도 최적화가 아니라  
**실제 서비스 품질과 안정성에 영향을 주는 선택**이라는 점이다.  
그래서 환경 변화 입력 테스트나 TTP 설계가 함께 따라와야 한다.

### 더 확장해서 공부해볼 만한 포인트

- LoRA의 rank \(r\) 값에 따른 품질 변화
- NF4와 다른 양자화 방식의 비교
- QLoRA와 일반 LoRA의 실제 VRAM 차이 측정
- 도메인별 TTP 템플릿 설계 원칙
- 의료/법률처럼 민감한 태스크에서 안전 규칙형 프롬프트 구성
- 멀티모달 모델에서의 LoRA/QLoRA 확장
- Unsloth와 Hugging Face 기본 Trainer의 속도 및 메모리 비교

## 6. 요약 정리

📌 핵심

- PEFT는 모델 전체를 다시 학습하지 않고, 적은 파라미터만 학습하는 방법이다.
- LoRA는 가중치 변화량을 저랭크 행렬로 근사해 학습 비용을 크게 줄인다.
- QLoRA는 4비트 양자화된 베이스 모델 위에 LoRA를 얹어, 학습 비용과 메모리 부담을 함께 낮춘다.
- Unsloth는 이런 흐름을 저사양 환경에서도 비교적 쉽게 실습할 수 있게 돕는 도구다.
- 양자화는 FP16, INT8, INT4처럼 숫자 표현 비트를 줄여 추론 비용을 낮춘다.
- INT4는 메모리를 크게 줄이지만, 입력이 흔들릴수록 품질 저하가 더 눈에 띌 수 있다.
- `double_quant=True` 는 INT4를 더 효율적으로 쓰게 돕는 설정이다.
- TTP는 재학습 없이 프롬프트 설계만으로 추론 품질을 보완하는 전략이다.

🧠 기억할 것

- 학습이 무거우면 → **LoRA / QLoRA**
- 추론이 무거우면 → **FP16 / INT8 / INT4**
- 입력이 흔들리면 → **TTP**
- 결과가 이상하면 → 먼저 **데이터 포맷, 템플릿, 응답 구간 학습 여부**를 점검

## 7. 미니 퀴즈 또는 체크리스트

1. Full Fine-tuning 대신 LoRA를 쓰는 이유를 “학습해야 하는 파라미터 수” 관점에서 설명해보자.
2. QLoRA가 일반 LoRA보다 더 실용적인 이유를 “베이스 모델 메모리” 관점에서 설명해보자.
3. `load_in_4bit=True` 와 `bnb_4bit_compute_dtype=torch.float16` 는 각각 무엇을 줄이고 무엇을 유지하려는 설정인가?
4. INT8과 INT4 중 하나를 고를 때, 어떤 상황에서는 INT8을, 어떤 상황에서는 INT4를 선택하는 것이 더 합리적인가?
5. 양자화 모델이 오타나 모호한 표현에 더 취약해질 수 있는 이유를 행렬 양자화의 관점에서 설명해보자.
6. TTP의 규칙형 템플릿과 few-shot 템플릿은 어떤 차이가 있으며, 각각 어떤 상황에서 더 잘 작동할지 생각해보자.
