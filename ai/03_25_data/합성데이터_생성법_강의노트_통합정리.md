## 1. 들어가며

데이터가 부족한 프로젝트를 하다 보면 비슷한 고민이 반복된다.  
실제 데이터를 모으기에는 시간이 오래 걸리고, 라벨링까지 하려면 비용도 커진다. 게다가 개인정보가 섞여 있으면 마음대로 쓰기도 어렵다. 이때 많은 사람이 먼저 떠올리는 방법이 바로 “AI에게 데이터를 만들어 달라고 하자”는 접근이다.

하지만 여기서 곧바로 실전 문제가 생긴다.  
API 키는 어디에 보관해야 안전한지, 프롬프트는 어떻게 써야 원하는 형식이 나오는지, 생성된 데이터가 정말 쓸 만한지, 대량으로 만들 때는 비용과 품질을 어떻게 같이 잡아야 하는지 같은 질문들이다.

이번 강의는 이 질문들을 따로따로 다루지 않는다.  
오히려 하나의 파이프라인으로 연결한다.

1. 먼저 **환경변수로 API 키를 안전하게 관리**한다.
2. 그다음 **프롬프팅 기법**으로 모델의 출력을 조절한다.
3. 이어서 **합성 데이터와 구조화된 출력**으로 실제로 쓸 수 있는 데이터를 만든다.
4. 마지막으로 **LLM as a Judge**로 생성 결과를 자동 평가하고 필터링한다.
5. 여기에 더해, 대량 생성 상황에서는 **소형 모델 + 대형 평가 모델** 조합과 **데이터 증강**까지 고려한다.

쉽게 말하면, 이 강의는 “LLM을 한 번 써보는 법”이 아니라  
**LLM으로 데이터를 만들고, 고르고, 파이프라인으로 연결하는 법**을 배우는 시간이다.

## 2. 핵심 개념 정리

이 장의 큰 흐름은 아래처럼 잡을 수 있다.

| 단계 | 핵심 질문 | 배울 내용 |
|---|---|---|
| 1 | 모델을 어떻게 안전하게 호출할까? | 환경변수, `.env`, `python-dotenv`, OpenAI 호환 API |
| 2 | 같은 모델인데 왜 답이 달라질까? | Zero-shot, Few-shot, CoT, generation parameter |
| 3 | 사람이 바로 쓸 수 있는 데이터로 만들려면? | JSON 출력, 파싱, `response_format`, 스키마 설계 |
| 4 | 데이터를 많이 만들 때 무엇을 조절해야 할까? | persona, temperature, top_p, sLLM 활용 |
| 5 | 생성된 데이터가 좋은지 어떻게 알까? | LLM as a Judge, rubric, 자동 평가, filtering |
| 6 | 합성 데이터와 데이터 증강은 어떻게 다를까? | 텍스트/이미지 관점에서의 생성 전략 |

이 흐름에서 중요한 점은, 각 개념이 따로 떨어져 있지 않다는 것이다.  
예를 들어 `response_format`은 단순히 JSON을 예쁘게 받기 위한 기능이 아니다. 이 기능이 있어야 나중에 평가 파이프라인에서 데이터를 자동으로 순회하고, 점수를 저장하고, 기준 이하 샘플을 걸러낼 수 있다.

또 `temperature`와 `top_p`는 단순한 옵션 조절이 아니다.  
이 값들은 합성 데이터의 **다양성**과 **안정성** 사이의 균형을 정하는 손잡이 역할을 한다. 너무 낮으면 뻔한 문장만 반복되고, 너무 높으면 말이 안 되는 문장이 섞인다.

결국 이 장은 다음 한 문장으로 정리할 수 있다.

> **LLM 기반 데이터 생성은 “호출 → 유도 → 구조화 → 평가 → 선별”의 흐름으로 이해해야 한다.**

## 3. 본문 정리

## 3.1 환경변수와 API 호출 기초

환경변수는 운영체제가 프로그램 실행 시 넘겨주는 설정값이다.  
이 개념이 중요한 이유는, API 키를 코드 안에 직접 적는 순간 보안 문제가 바로 생기기 때문이다. GitHub에 실수로 올라가거나, 노트북 파일을 공유하는 순간 키가 노출될 수 있다.

쉽게 말하면, 환경변수는 **비밀번호를 코드 밖에 두는 방법**이다.  
코드는 그대로 두고, 실행 환경만 바꿔도 다른 키를 쓸 수 있다는 점도 실무에서 아주 중요하다.

### 왜 필요한가

- 키를 코드에 하드코딩하면 유출 위험이 크다.
- 개발 환경과 배포 환경에서 서로 다른 키를 써야 할 때 코드 수정이 불필요하다.
- OpenAI SDK처럼 표준 인터페이스를 쓰면 `base_url`만 바꿔 다른 서비스에도 붙을 수 있다.

### 기본 예시: `.env` 로드와 클라이언트 생성

~~~python
# .env 파일을 읽어 환경변수를 현재 프로세스에 로드한다.
from dotenv import load_dotenv

# 운영체제 환경변수에서 값을 읽기 위해 os를 불러온다.
import os

# OpenAI 호환 API 클라이언트를 사용한다.
from openai import OpenAI

# 프로젝트 루트의 .env 파일을 불러온다.
# 파일 안에는 UPSTAGE_API_KEY="..." 형태로 키가 들어 있다고 가정한다.
load_dotenv(".env")

# 환경변수에서 API 키를 꺼낸다.
# 키 이름이 다르면 여기서 None이 나오므로 가장 먼저 확인해야 한다.
UPSTAGE_API_KEY = os.getenv("UPSTAGE_API_KEY")

# 키가 잘 읽혔는지 간단히 점검한다.
if UPSTAGE_API_KEY:
    print("Success API Key Setting!")
else:
    print("Failed to load API Key. Please check your .env file.")

# OpenAI 호환 API 클라이언트를 만든다.
# base_url만 바꾸면 같은 SDK로 다른 제공업체 API에도 연결할 수 있다.
client = OpenAI(
    api_key=UPSTAGE_API_KEY,
    base_url="https://api.upstage.ai/v1"
)
~~~

### 코드 흐름 해설

이 코드는 겉보기엔 짧지만, 이후 모든 실습의 출발점이 된다.

1. `load_dotenv(".env")`가 `.env` 파일을 읽는다.
2. `os.getenv("UPSTAGE_API_KEY")`가 실제 실행 환경에 들어간 값을 꺼낸다.
3. 그 값을 `OpenAI` 클라이언트에 넣어 API 요청을 보낼 준비를 한다.

여기서 중요한 점은,  
`load_dotenv()`는 키를 “직접 쓰는” 함수라기보다 **환경에 주입하는 함수**라는 점이다. 그래서 이후엔 항상 `os.getenv()`로 읽게 된다.

### 재사용 가능한 호출 함수

실습이 길어질수록 `client.chat.completions.create(...)`를 매번 길게 쓰는 것은 불편하다. 그래서 호출 함수를 하나 만들어두면 프롬프트 실험이 훨씬 쉬워진다.

~~~python
def chat_completion(prompt: str,
                    system_prompt: str = None,
                    model: str = "solar-pro3") -> str:
    """
    사용자 프롬프트와 선택적 시스템 프롬프트를 받아
    LLM 응답 텍스트를 반환하는 함수
    """
    # 최종적으로 API에 전달할 messages 리스트를 만든다.
    messages = []

    # 시스템 프롬프트가 있으면 먼저 넣는다.
    # 시스템 프롬프트는 모델의 역할, 말투, 출력 형식 같은 상위 규칙을 정한다.
    if system_prompt:
        messages.append({"role": "system", "content": system_prompt})

    # 사용자의 실제 질문이나 요청은 user 역할로 추가한다.
    messages.append({"role": "user", "content": prompt})

    # LLM에게 요청을 보낸다.
    response = client.chat.completions.create(
        model=model,
        messages=messages
    )

    # 응답 객체에서 실제 텍스트만 꺼내 반환한다.
    return response.choices[0].message.content
~~~

### 자주 하는 실수 / 디버깅 포인트

⚠️ `.env` 파일은 만들었는데 키가 안 읽히는 경우  
- 파일 경로가 현재 작업 디렉터리와 다를 수 있다.
- 키 이름을 `OPENAI_API_KEY`로 저장해놓고 `UPSTAGE_API_KEY`를 읽는 경우가 많다.

⚠️ `.env`를 Git에 올려버리는 경우  
- `.gitignore`에 `.env`를 추가하지 않으면 그대로 업로드된다.

⚠️ `base_url`을 빼먹는 경우  
- OpenAI SDK는 같아도, 실제 호출 대상이 다르면 엔드포인트도 달라진다.

📌 핵심: **환경변수 설정은 부가 작업이 아니라, 이후 모든 실습을 안정적으로 수행하기 위한 기반이다.**

## 3.2 프롬프팅 기법: 같은 모델인데 왜 답이 달라질까

프롬프팅은 LLM에게 원하는 출력을 이끌어내기 위해 입력을 설계하는 방법이다.  
같은 모델에 같은 질문을 해도, 프롬프트를 어떻게 쓰느냐에 따라 결과의 형식, 정확도, 논리성이 크게 달라진다.

쉽게 말하면, 프롬프트는 모델을 바꾸는 것이 아니라  
**모델이 가진 능력을 어느 방향으로 끌어내느냐를 바꾸는 장치**다.

### 세 가지 대표 기법

| 기법 | 한 줄 정의 | 강점 | 약점 | 잘 맞는 상황 |
|---|---|---|---|---|
| Zero-shot | 예시 없이 바로 지시 | 간단하고 빠름 | 형식 불안정 가능 | 단순 분류, 명확한 작업 |
| Few-shot | 예시를 몇 개 보여줌 | 형식과 패턴 유도에 강함 | 토큰 증가 | 원하는 답변 스타일이 있을 때 |
| CoT | 단계별 추론을 유도 | 복잡한 문제에서 정확도 향상 | 응답 길이 증가 | 계산, 분석, 논리 추론 |

### 예시: 영화 추천 작업 비교

같은 요청인 `"스릴러 영화를 추천해줘"`를 세 가지 방식으로 처리해보자.

#### Zero-shot

~~~python
# 시스템 프롬프트는 모델의 역할과 출력 요구사항을 정한다.
SYSTEM_PROMPT = """당신은 세상의 모든 영화를 꿰뚫고 있는 영화 전문가 '시네마스터'입니다.
사용자의 요청에 맞춰 영화를 추천하는 역할을 맡고 있습니다.
추천할 때는 반드시 영화 제목, 개봉 연도, 그리고 추천 이유를 포함해야 합니다."""

# 사용자의 실제 요청이다.
user_query = "스릴러 영화를 추천해줘"

# Zero-shot은 예시 없이 바로 요청한다.
zero_shot_prompt = f"{user_query}"

# 응답을 받아 출력한다.
zero_shot_result = chat_completion(zero_shot_prompt, SYSTEM_PROMPT)
print(zero_shot_result)
~~~

Zero-shot의 장점은 빠르고 단순하다는 점이다.  
다만, “제목-연도-이유” 형식이 어느 정도 지켜질 가능성은 있어도, 항상 일정하다고 보기는 어렵다.

#### Few-shot

~~~python
few_shot_prompt = f"""다음은 영화 추천 예시입니다:

질문: 로맨스 영화를 추천해줘
답변: 영화 제목: 노트북 (The Notebook)
개봉 연도: 2004년
추천 이유: 시대를 초월한 순수한 사랑 이야기로, 감동적인 스토리와 아름다운 영상미가 돋보이는 클래식 로맨스 영화입니다.

질문: 코미디 영화를 추천해줘
답변: 영화 제목: 행오버 (The Hangover)
개봉 연도: 2009년
추천 이유: 총각파티 후 기억을 잃은 친구들의 황당한 모험을 그린 코미디로, 예측 불가능한 전개와 유쾌한 유머가 가득합니다.

질문: {user_query}
답변:"""

few_shot_result = chat_completion(few_shot_prompt, SYSTEM_PROMPT)
print(few_shot_result)
~~~

Few-shot의 핵심은 모델에게 “정답 형식의 감”을 먼저 보여준다는 점이다.  
그래서 출력 형식이나 말투를 맞추고 싶을 때 특히 강하다.

#### Chain-of-Thought (CoT)

~~~python
cot_prompt = f"""{user_query}

영화를 추천하기 전에 다음 단계를 따라 생각해주세요:

1단계: 스릴러 장르의 핵심 요소가 무엇인지 정의합니다.
2단계: 이 요소들을 잘 갖춘 대표적인 스릴러 영화들을 떠올립니다.
3단계: 그 중에서 가장 추천할 만한 영화 1개를 선택하고 이유를 설명합니다.

위 단계를 따라 추론 과정을 보여주고, 최종 추천을 해주세요."""

cot_result = chat_completion(cot_prompt, SYSTEM_PROMPT)
print(cot_result)
~~~

CoT는 특히 “왜 이 답이 나왔는지”가 중요한 작업에서 강하다.  
영화 추천처럼 단순해 보이는 문제에서도 논리 구조를 더 뚜렷하게 만들 수 있고, 계산·분석 문제에서는 효과가 더 커진다.

### 쉬운 해설

- Zero-shot은 “바로 시키기”
- Few-shot은 “예시를 보여주고 따라 하게 만들기”
- CoT는 “생각하는 순서를 먼저 깔아주기”

이 세 방식은 서로 경쟁 관계가 아니라,  
**작업의 성격에 따라 꺼내 쓰는 도구 상자**에 가깝다.

### 자주 하는 실수 / 디버깅 포인트

⚠️ Few-shot 예시가 너무 많을 때  
- 도움이 되기보다 토큰만 늘고, 오히려 모델이 불필요한 패턴을 따라갈 수 있다.

⚠️ Few-shot 예시가 한쪽으로 치우칠 때  
- 예시가 너무 비슷하면 다양성이 줄고 특정 형식에 과도하게 고정될 수 있다.

⚠️ CoT를 모든 작업에 남용할 때  
- 단순 분류나 짧은 추출 작업에선 오히려 응답만 길어질 수 있다.

📌 핵심: **프롬프팅 기법의 선택은 “무슨 모델을 쓰느냐” 못지않게 “무슨 작업을 하느냐”에 따라 달라진다.**

## 3.3 생성 파라미터: 다양성과 안정성을 조절하는 손잡이

프롬프트가 “어떤 방향으로 답하게 할지”를 정한다면,  
생성 파라미터는 “얼마나 보수적으로 또는 얼마나 다양하게 답할지”를 조절한다.

이 부분은 처음엔 추상적으로 느껴지기 쉽다.  
하지만 합성 데이터 생성에서는 아주 직접적으로 체감된다. 같은 프롬프트를 반복 호출했을 때 문장이 너무 똑같이 나오거나, 반대로 지나치게 엉뚱한 결과가 나오는 이유가 여기에 걸려 있기 때문이다.

### 주요 파라미터

| 파라미터 | 역할 | 직관적 해석 |
|---|---|---|
| `temperature` | 확률 분포를 얼마나 평평하게 만들지 | 낮을수록 보수적, 높을수록 창의적 |
| `top_p` | 누적 확률 상위 토큰만 후보로 사용 | 작을수록 안전, 클수록 다양한 후보 허용 |
| `max_tokens` | 최대 출력 길이 제한 | 너무 작으면 중간에 잘리고, 너무 크면 비용 증가 |

### OpenAI 호환 API에서의 사용 예시

~~~python
response = client.chat.completions.create(
    model="solar-pro3",
    messages=[{"role": "user", "content": "AI의 미래를 한 문장으로"}],
    temperature=0.0,   # 가능한 한 일관된 답을 원할 때
    max_tokens=500     # 답변 길이 상한선
)

print(response.choices[0].message.content)
~~~

### 로컬 sLLM 추론 코드에서의 사용 예시

대량 생성 관점에서는 허깅페이스 모델을 직접 돌리는 실습도 함께 등장했다. 여기서 `temperature`와 `top_p`는 더 직접적으로 보인다.

~~~python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

# GPU가 있으면 GPU를, 없으면 CPU를 사용한다.
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")

# 실습에서는 Qwen 계열의 소형 모델을 사용했다.
model_name = "Qwen/Qwen3-0.6B"

# 토크나이저와 모델을 불러온다.
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype="auto",
    device_map="auto"
)

prompt = """
원본 데이터를 기반으로 새로운 데이터들을 만들어줘
같은 의미를 가지고 있지만, 다양한 표현으로 바꾸어줘

원본 데이터 : "안녕, 난 철수야. KFC를 좋아하지"
만들고 싶은 데이터 예시는 다음과 같아
1. 안녕하세요, 철수입니다. 오늘은 KFC의 인기 비결에 대해 알아보겠습니다.
2. 안녕~, 철수예요. KFC의 로고 컬러는 언제 봐도 강렬하죠.
3. 여러분 안녕하세요. 저는 철수랍니다. 수업 후엔 KFC 치킨을 즐긴답니다.

새로운 문장 1개로만 대답해줘
"""

# 채팅 형식 프롬프트를 모델 입력 형태로 바꾼다.
messages = [{"role": "user", "content": prompt}]
text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
    enable_thinking=False
)

# 토큰 텐서로 변환하고 모델이 있는 장치로 보낸다.
model_inputs = tokenizer([text], return_tensors="pt").to(model.device)

# 실제 생성 단계다.
generated_ids = model.generate(
    **model_inputs,
    max_new_tokens=500,
    temperature=0.7,  # 너무 낮으면 반복이 늘고, 너무 높으면 품질이 흔들릴 수 있다.
    top_p=0.8         # 누적 확률 상위 후보만 사용해 다양성과 안정성을 함께 잡는다.
)

# 새로 생성된 부분만 잘라 디코딩한다.
output_ids = generated_ids[0][len(model_inputs.input_ids[0]):]
content = tokenizer.decode(output_ids, skip_special_tokens=True)

print(content)
~~~

### 어떻게 이해하면 좋은가

- `temperature`가 낮으면 자주 선택되는 단어가 더 자주 선택된다.
- `temperature`가 높으면 덜 유력한 단어도 후보가 되어 문장이 다양해진다.
- `top_p`는 “후보 단어 풀”의 크기를 제한하는 역할에 가깝다.

즉, 이 둘은 따로 놀지 않는다.  
실전에서는 보통 **둘을 같이 조정하면서 반복성 ↔ 다양성**의 균형을 맞춘다.

### 어떤 상황에서 어떻게 조절할까

| 상황 | 조절 방향 |
|---|---|
| 결과가 지나치게 반복된다 | `temperature` ↑, `top_p` ↑ |
| 문장이 어색하거나 말이 안 된다 | `temperature` ↓, `top_p` ↓ |
| 분류/평가처럼 일관성이 중요하다 | `temperature=0` 또는 매우 낮게 |
| 합성 문장 다양성이 중요하다 | 중간 수준으로 열어두고 반복 호출 |

⚠️ 주의: 다양성을 올린다고 해서 무조건 좋은 데이터가 늘어나는 것은 아니다.  
다양성이 커질수록 **저품질 샘플도 함께 늘어날 가능성**이 생기기 때문에, 뒤에서 다룰 Judge 단계가 함께 필요하다.

📌 핵심: **생성 파라미터는 답을 “잘 나오게” 만드는 버튼이 아니라, 다양성과 안정성의 균형을 조정하는 손잡이다.**

## 3.4 합성 데이터 생성: 사람이 쓸 수 있는 형태로 만들기

합성 데이터는 실제 세상에서 수집한 데이터가 아니라,  
모델이 인공적으로 만들어낸 데이터다. 이 개념이 중요한 이유는, 프로젝트에서 정말 부족한 것은 단순한 텍스트 한 줄이 아니라 **학습에 바로 넣을 수 있는 구조화된 샘플**인 경우가 많기 때문이다.

예를 들어 영화 추천 챗봇을 학습시키고 싶다면, “스릴러 영화 추천해줘” 같은 요청과 함께  
제목, 연도, 장르, 추천 이유가 정리된 구조화 데이터가 필요할 수 있다.

### 합성 데이터가 필요한 이유

- 실제 데이터가 부족하다.
- 개인정보를 그대로 쓰기 어렵다.
- 특정 장르, 특정 감성, 특정 페르소나처럼 **희소한 케이스를 의도적으로 늘리고 싶다**.
- 테스트셋, 평가셋, 시뮬레이션 입력처럼 사람이 매번 만들기 번거로운 데이터를 빠르게 만들고 싶다.

### 3.4.1 페르소나 기반 생성

페르소나는 “누가 말하는가”를 정하는 장치다.  
같은 의미를 유지하면서도 문체와 분위기를 바꾸고 싶을 때 특히 효과적이다.

#### 리뷰 생성 예시

~~~python
# 특정 인물의 배경과 말투를 먼저 정해놓고 리뷰를 생성한다.
prompt = """당신은 30대 직장인 여성 '김미래'입니다.
온라인 쇼핑을 자주 하며 가격 대비 품질을 중시합니다.

다음 상품에 대한 리뷰를 작성해주세요:
상품: 무선 블루투스 이어폰
별점: 4점

리뷰:"""

response = chat_completion(prompt)
print(response)
~~~

이 방식의 장점은,  
단순히 “리뷰 1개 써줘”라고 하는 것보다 훨씬 현실적인 표현이 나오기 쉽다는 점이다.

#### Text-to-SQL 번역 증강에서의 페르소나 확장

실습·과제에서는 번역 데이터도 페르소나 기반으로 증강했다.  
이때 핵심은 **의미는 유지하되 톤만 바꾸는 것**이다.

~~~python
personas = [
    "Friendly Adult - Kind and polite tone, like an older sibling giving advice.",
    "Elementary Student - Simple, cheerful, and naive tone, like a 10-year-old child.",
    "Formal Business - Polite, professional tone suitable for documents or work emails.",
    "Casual Friend - Relaxed, informal tone, as if chatting with a close friend.",
    "Elderly Person - Gentle, old-fashioned, and wise tone, like a kind grandparent.",
]

PERSONA_PROMPT_TEMPLATE = """You are a translation assistant.
Your task is to translate English sentences into Korean.
You must keep the meaning accurate, but adapt the tone and style according to the requested persona.

Persona: {persona}

Translate the given English sentence into Korean with the specified persona's tone and style.
"""
~~~

이 코드에서 중요한 점은,  
페르소나가 “새 내용을 추가하는 장치”가 아니라 **표현 방식만 흔들어 다양성을 만드는 장치**라는 것이다. 이 차이를 놓치면, 나중에 Judge 단계에서 의미 왜곡이 많이 발생한다.

### 3.4.2 프롬프트 기반 JSON 생성과 파싱

합성 데이터가 진짜 쓸모 있으려면 텍스트 덩어리가 아니라,  
코드로 읽을 수 있는 형식이어야 한다. 가장 흔한 방식이 JSON이다.

#### JSON 파싱 유틸리티

~~~python
import json

def json_parsing(output_text: str) -> dict:
    """
    LLM 응답 텍스트에서 JSON 부분만 추출해 dict로 변환한다.
    마크다운 코드 블록(```json ... ```) 안에 JSON이 들어온 경우까지 처리한다.
    """
    try:
        # 응답이 ```json ... ``` 형태라면 JSON 본문만 잘라낸다.
        if "```json" in output_text:
            output_text = output_text[output_text.index("```json") + len("```json"):].strip()
            output_text = output_text[:output_text.index("```")].strip()

        # 잘라낸 텍스트를 실제 딕셔너리로 바꾼다.
        return json.loads(output_text)

    # JSON이 깨졌거나 닫는 백틱을 못 찾는 경우를 대비한다.
    except (json.JSONDecodeError, ValueError) as e:
        print(f"JSON 파싱 오류: {e}")
        return None
~~~

이 함수가 필요한 이유는,  
LLM이 “JSON으로 답해줘”라고 했을 때도 꼭 순수 JSON만 주지는 않기 때문이다. 설명 문장을 붙이거나, 코드 블록 안에 감싸거나, 쉼표 하나를 빠뜨리는 경우가 생긴다.

#### 영화 추천 합성 데이터 생성 예시

~~~python
STRUCTURED_GENERATOR_SYSTEM_PROMPT = """당신은 세상의 모든 영화를 꿰뚫고 있는 영화 전문가 '시네마스터'입니다.
사용자의 요청에 맞춰 영화를 추천하는 역할을 맡고 있습니다. 영화는 반드시 하나만 추천합니다.

## 1. 입력 형식
[추천받고자 하는 영화 장르]

## 2. 작업 지시
- 요청된 장르에 가장 적합한 영화 1개를 추천합니다.
- 추천 이유는 구체적이고 설득력 있게 작성합니다.
- 친근하고 유머러스한 말투로 설명합니다.

## 3. 출력 형식
```json
{
    "movie_name": [영화 이름],
    "year": [개봉 연도],
    "genre": [장르],
    "reason": [추천 이유]
}
```
"""

def generate_movie_recommendation(genre: str, temperature: float = 1.0) -> dict:
    """
    특정 장르에 대한 영화 추천 데이터를 생성하고,
    결과를 JSON으로 파싱해 dict 형태로 반환한다.
    """
    response = client.chat.completions.create(
        model="solar-pro3",
        messages=[
            {"role": "system", "content": STRUCTURED_GENERATOR_SYSTEM_PROMPT},
            {"role": "user", "content": f"{genre} 영화를 추천해줘"}
        ],
        temperature=temperature
    )

    output = response.choices[0].message.content
    return json_parsing(output)
~~~

### 코드 흐름 해설

1. 시스템 프롬프트에서 모델의 역할을 고정한다.
2. 출력 형식을 JSON으로 구체적으로 지정한다.
3. 사용자 입력으로 장르만 바꿔가며 반복 호출한다.
4. 응답 텍스트를 `json_parsing()`으로 딕셔너리로 변환한다.

이 구조가 좋은 이유는,  
같은 틀을 유지한 채 입력만 바꾸면 데이터셋이 계속 쌓인다는 점이다.

### 자주 하는 실수 / 디버깅 포인트

⚠️ “JSON으로 답해줘”만 쓰고 스키마를 안 주는 경우  
- 키 이름이 제각각 달라질 수 있다. 예: `movie`, `title`, `movie_name`

⚠️ 파싱 함수 없이 바로 `json.loads()`를 쓰는 경우  
- 코드 블록이 붙거나 설명 문장이 섞이면 바로 에러가 난다.

⚠️ 페르소나를 넣었는데 의미까지 바뀌는 경우  
- 다양성을 주되 사실 정보는 유지해야 한다. 이 때문에 뒤에서 평가가 필요하다.

📌 핵심: **합성 데이터는 “텍스트를 하나 생성했다”에서 끝나는 것이 아니라, 프로그램이 바로 다룰 수 있는 구조로 만들어질 때 비로소 파이프라인에 들어간다.**

## 3.5 Structured Output: JSON을 요청하는 것과 강제하는 것은 다르다

프롬프트에 “JSON 형식으로 답해줘”라고 쓰는 것만으로도 어느 정도 구조화는 된다.  
하지만 반복 생성이 많아질수록 이 방식은 흔들린다. 어떤 응답은 키가 빠지고, 어떤 응답은 설명 문장이 섞이고, 어떤 응답은 타입이 달라진다.

이때 필요한 것이 `response_format` 기반 Structured Output이다.

### 왜 필요한가

프롬프트 기반 JSON은 말 그대로 “부탁”에 가깝다.  
반면 `response_format`은 API 레벨에서 스키마를 검증하는 방향에 가깝다.

즉, 이 기능은 단순한 편의성이 아니라  
**파이프라인 자동화를 가능하게 만드는 안정성 장치**다.

### 비교 표

| 비교 항목 | 프롬프트 기반 JSON | `response_format` 기반 |
|---|---|---|
| JSON 보장 | 보장 안 됨 | API 레벨에서 강제 |
| 필드 누락 | 발생 가능 | `required`로 방지 가능 |
| 파싱 에러 | 자주 발생 가능 | 크게 줄어듦 |
| 후처리 난이도 | 예외 처리 많이 필요 | 단순해짐 |

### 리뷰 데이터 스키마 예시

~~~python
review_response_format = {
    "type": "json_schema",
    "json_schema": {
        "name": "customer_reviews",
        "strict": True,
        "schema": {
            "type": "object",
            "properties": {
                "reviews": {
                    "type": "array",
                    "description": "고객 리뷰 목록",
                    "items": {
                        "type": "object",
                        "properties": {
                            "customer_name": {
                                "type": "string",
                                "description": "고객 이름"
                            },
                            "rating": {
                                "type": "integer",
                                "description": "별점 (1-5)"
                            },
                            "category": {
                                "type": "string",
                                "description": "감성 분류 (긍정/부정/중립)"
                            },
                            "text": {
                                "type": "string",
                                "description": "리뷰 본문"
                            }
                        },
                        "required": ["customer_name", "rating", "category", "text"],
                        "additionalProperties": False
                    }
                }
            },
            "required": ["reviews"],
            "additionalProperties": False
        }
    }
}
~~~

### 실제 호출 예시

~~~python
prompt = "무선 블루투스 이어폰에 대한 고객 리뷰 3개를 생성하세요. 긍정, 부정, 중립 각 1개씩 포함하세요."

response = client.chat.completions.create(
    model="solar-pro3",
    messages=[{"role": "user", "content": prompt}],
    response_format=review_response_format
)

result = json.loads(response.choices[0].message.content)

for r in result["reviews"]:
    print(f"[{r['category']}] {r['customer_name']} ({r['rating']}점): {r['text']}")
~~~

### 쉬운 해설

- 프롬프트 기반 JSON은 “형식 좀 맞춰줘”
- `response_format`은 “이 형식 아니면 안 돼”

합성 데이터가 3개일 땐 큰 차이가 없어 보일 수 있다.  
하지만 300개, 3,000개로 넘어가면 이 차이는 바로 작업량 차이로 바뀐다.

### Text-to-SQL 번역 과제의 구조화 예시

과제에서는 영어 질문을 한국어로 번역한 결과를 아래처럼 단일 필드 스키마로 받았다.

~~~python
translation_response_format = {
    "type": "json_schema",
    "json_schema": {
        "name": "translation",
        "strict": True,
        "schema": {
            "type": "object",
            "properties": {
                "korean": {
                    "type": "string",
                    "description": "한국어로 번역된 문장"
                }
            },
            "required": ["korean"],
            "additionalProperties": False
        }
    }
}
~~~

이 구조 덕분에 프롬프팅 기법별 결과 비교도 훨씬 쉬워진다.  
예를 들어 Zero-shot, Few-shot, CoT 각각의 응답에서 `"korean"` 필드만 바로 꺼내 비교할 수 있기 때문이다.

⚠️ 주의: `response_format`이 있다고 해서 품질 자체가 보장되는 것은 아니다.  
형식은 안정화되지만, 내용의 자연스러움이나 의미 보존 여부는 별도의 평가가 필요하다.

📌 핵심: **Structured Output은 응답 형식을 예쁘게 만드는 기능이 아니라, 반복 생성 파이프라인의 실패율을 낮추는 핵심 장치다.**

## 3.6 대량 생성 전략: ChatGPT에 한 번에 많이 시키면 왜 안 될까

초반 Easy 자료에서는 아주 직관적인 출발점을 보여줬다.  
소량 데이터는 ChatGPT에게 예시를 주고 바로 만들어도 된다. 실제로 `"안녕, 난 철수야. KFC를 좋아하지"` 같은 문장을 여러 직업/말투 버전으로 바꾸는 작업은 이런 식으로 빠르게 처리할 수 있다.

하지만 여기서 바로 대량 생성으로 넘어가면 문제가 생긴다.

### 소량 생성과 대량 생성의 차이

- 소량 생성: 사람 눈으로 확인 가능, ChatGPT로 빠르게 가능
- 대량 생성: 비용, 토큰, 반복성, 품질 편차 문제가 크게 드러남

강의에서는 대량 텍스트 생성 시 다음 전략을 제안한다.

1. **생성은 경량 모델(sLLM)** 로
2. **평가는 더 강한 모델** 로
3. 필요하면 temperature/top_p를 조정해 다양성을 늘리되,
4. 최종 채택은 Judge 단계에서 걸러낸다.

이 구조가 중요한 이유는,  
생성과 평가의 비용 구조가 다르기 때문이다. 생성은 보통 출력 토큰이 많이 들고, 평가는 입력 위주라 상대적으로 저렴할 수 있다.

### 로컬 모델을 쓰는 이유

대량 데이터를 계속 만들 때는 클라우드 호출 비용이 부담될 수 있다.  
그래서 허깅페이스 모델을 코랩이나 추론 서버에서 돌리는 방식이 등장한다.

쉽게 말하면:

- **많이 찍어내는 쪽**은 싸게
- **거르는 쪽**은 더 정확하게

이 분업 구조가 대량 생성에서 꽤 실용적이다.

### 대량 생성 루프 예시

~~~python
# 여러 페르소나와 여러 상품 조합을 순회하며 리뷰를 만든다.
personas = ["20대 대학생", "40대 주부", "60대 은퇴자"]
products = ["노트북", "운동화"]

results = []

for persona in personas:
    for product in products:
        # 입력만 바꾸고 같은 패턴으로 계속 생성한다.
        prompt = f"{persona}의 관점에서 {product} 리뷰를 작성하세요."

        # 리뷰 텍스트를 생성한다.
        review = chat_completion(prompt)

        # 나중에 평가하거나 저장할 수 있도록 메타정보와 함께 담아둔다.
        results.append({
            "persona": persona,
            "product": product,
            "review": review
        })

print(f"생성된 리뷰 수: {len(results)}개")
~~~

이 코드는 단순해 보여도 실제 합성 데이터 파이프라인의 기본 골격이다.  
**입력 조합을 설계하고, 반복 생성하고, 구조화해서 저장한다**는 점이 핵심이다.

### 데이터 증강과 합성 데이터의 차이

강의 후반부에서는 이 둘을 명확히 구분한다.

| 구분 | 의미 | 예시 |
|---|---|---|
| 데이터 증강 | 기존 데이터를 살짝 변형해 양을 늘림 | 문장 패러프레이징, 이미지 회전/좌우반전 |
| 합성 데이터 | 예시나 규칙을 바탕으로 새 데이터를 대량 생성 | AI가 새로운 리뷰/추천 데이터 생성 |

이 차이를 이해해야 하는 이유는,  
실무에서는 보통 **원본 품질을 보존하는 데이터 증강이 먼저**이고, 그다음이 합성 데이터이기 때문이다. 특히 텍스트는 합성 데이터가 빠르지만 품질 통제가 어렵고, 이미지는 오히려 증강이 더 경제적인 경우가 많다.

📌 핵심: **대량 생성에서는 “많이 만드는 것”보다 “어떻게 싸고 안정적으로 만들고, 어떻게 걸러낼 것인가”가 더 중요하다.**

## 3.7 LLM as a Judge: 생성만큼 중요한 것은 평가다

합성 데이터를 만들고 나면 자연스럽게 다음 질문이 생긴다.  
“그래서 이 데이터, 믿고 써도 되나?”

이 질문이 중요해지는 이유는,  
생성 모델은 그럴듯한 문장을 만들 수는 있어도 항상 정확하거나 자연스러운 것은 아니기 때문이다. 특히 temperature를 올려 다양성을 확보하면 저품질 샘플이 섞일 가능성도 커진다.

그래서 필요한 것이 **LLM as a Judge**다.  
말 그대로 LLM을 “평가자”로 써서, 다른 모델의 출력 품질을 자동으로 점수화하는 방식이다.

### 개념 한 줄 정의

> **LLM as a Judge는 생성 결과를 사람 대신 모델이 일정한 기준으로 평가하도록 만드는 자동 품질 관리 방식이다.**

### 왜 필요한가

- 사람이 수백, 수천 개 샘플을 일일이 읽기 어렵다.
- 같은 기준으로 반복 평가하기 쉽다.
- 점수와 이유를 함께 받아 필터링 근거를 남길 수 있다.
- 합성 데이터뿐 아니라 RAG 답변 평가, 챗봇 응답 비교에도 적용 가능하다.

### 예시 1: 리뷰 품질 평가 프롬프트

~~~python
eval_prompt = """다음 리뷰의 품질을 1-5점으로 평가하세요.

평가 기준:
1. 구체성 (1-5): 제품의 구체적인 특징을 언급하는가?
2. 자연스러움 (1-5): 실제 고객이 쓴 것처럼 자연스러운가?
3. 유용성 (1-5): 다른 구매자에게 도움이 되는 정보가 있는가?

리뷰: {review_text}

JSON 형식으로 답변:
{{"specificity": N, "naturalness": N, "usefulness": N, "total": N, "reason": "..."}}"""
~~~

여기서 중요한 점은,  
“좋은 리뷰인가요?”처럼 두루뭉술하게 묻지 않았다는 것이다. 어떤 기준으로 점수를 줄지 먼저 정의했기 때문에, 모델도 평가 방향을 잡기 쉬워진다.

### 예시 2: 일반화된 Judge 함수

실습 정답 노트에서는 좀 더 범용적인 평가 함수를 만들었다.

~~~python
JUDGE_SYSTEM_PROMPT = """당신의 역할은 모델 답변 자동 평가자입니다. 입력 프롬프트와 모델 답변을 보고, 평가 기준에 따라 모델 답변을 평가합니다.

## 1. 입력 형식
- 입력 프롬프트: [instruction]
- 모델 답변: [output]
- 평가 기준: [criteria]

## 2. 작업 지시
- [instruction]에 따른 모델 결과물인 [output]을 평가합니다.
- [output]이 [criteria]를 충족하는지 평가합니다.

## 3. 채점 원칙
- 5점: 기준을 완전히 충족
- 4점: 대체로 충족
- 3점: 핵심은 맞지만 약점 존재
- 2점: 여러 중요한 요구를 놓침
- 1점: 전반적으로 요청과 어긋남

## 4. 출력 형식
```json
{
    "score": [점수],
    "comment": [평가 코멘트]
}
```
"""

JUDGE_USER_PROMPT_TEMPLATE = """- 입력 프롬프트: {instruction}
- 모델 답변: {output}
- 평가 기준: {criteria}
"""

def evaluate_with_llm(instruction: str, output: str, criteria: str) -> dict:
    """
    생성 결과를 평가하는 범용 함수.
    입력 프롬프트, 실제 출력, 평가 기준을 함께 넘겨
    점수와 코멘트를 JSON으로 받는다.
    """
    # 기준과 데이터를 넣어 실제 평가용 사용자 프롬프트를 만든다.
    user_prompt = JUDGE_USER_PROMPT_TEMPLATE.format(
        instruction=instruction,
        output=output,
        criteria=criteria
    )

    # 평가는 일관성이 중요하므로 temperature를 0으로 둔다.
    response = client.chat.completions.create(
        model="solar-pro3",
        messages=[
            {"role": "system", "content": JUDGE_SYSTEM_PROMPT},
            {"role": "user", "content": user_prompt}
        ],
        temperature=0
    )

    # Judge도 JSON으로 돌려주면 후처리가 쉬워진다.
    return json_parsing(response.choices[0].message.content)
~~~

### 코드 흐름 해설

1. 생성에 쓰였던 지시문(`instruction`)을 함께 넣는다.
2. 실제 생성 결과(`output`)를 넣는다.
3. 평가 기준(`criteria`)을 별도로 넣는다.
4. Judge 모델은 이 세 가지를 보고 점수와 이유를 JSON으로 반환한다.

이 구조가 좋은 이유는,  
“무엇을 보고 어떤 기준으로 채점했는지”가 분명해지기 때문이다. 즉, 나중에 기준만 바꿔 재평가하기도 쉽다.

### 예시 3: 자동 필터링

~~~python
criteria_list = [
    "요청의 충실도: 요청된 장르에 맞는 영화를 추천했는지, 필수 정보가 모두 포함되었는지",
    "추천 이유의 구체성: 추천 이유가 구체적이고 설득력 있는지",
    "정보의 정확성: 영화 제목과 개봉 연도가 실제와 일치하는지"
]

evaluation_results = []

for data in synthetic_data:
    # 영화 추천 dict를 문자열 형태로 바꿔 Judge 입력으로 넣는다.
    data_output = json.dumps(data, ensure_ascii=False)

    scores = []
    for criteria in criteria_list:
        result = evaluate_with_llm(
            instruction=STRUCTURED_GENERATOR_SYSTEM_PROMPT,
            output=data_output,
            criteria=criteria
        )

        # score 필드가 있으면 목록에 누적한다.
        if result and "score" in result:
            scores.append(result["score"])

    # 기준별 점수를 평균내어 최종 품질 점수로 사용한다.
    avg_score = sum(scores) / len(scores) if scores else 0

    evaluation_results.append({
        "data": data,
        "scores": scores,
        "average_score": avg_score
    })

# 평균 점수 기준으로 통과 샘플만 남긴다.
threshold = 3.5
filtered = [r for r in evaluation_results if r["average_score"] >= threshold]

print(f"원본: {len(evaluation_results)}개 → 필터링 후: {len(filtered)}개")
~~~

### Text-to-SQL 번역 과제에서의 Judge 포인트

과제에서는 번역의 품질을 평가할 때  
“문장이 예쁘냐”가 아니라 **원문 의미가 보존됐느냐**를 기준으로 두었다.

즉, 페르소나 번역에서는 말투를 바꾸는 것은 허용되지만,  
원문의 사실 정보가 추가·삭제·왜곡되면 감점하는 구조였다. 이 판단 기준은 합성 데이터 평가에서 아주 중요하다.

### 자주 하는 실수 / 디버깅 포인트

⚠️ 생성 모델과 평가 모델을 똑같이 쓰는 경우  
- 자기 편향(Self-bias)이 생길 수 있다.

⚠️ 평가 기준이 너무 모호한 경우  
- 점수는 나오지만 왜 그렇게 나왔는지 일관성이 떨어질 수 있다.

⚠️ Judge 결과를 절대 진실처럼 믿는 경우  
- Judge도 모델이기 때문에 완벽하지 않다. 필요하면 다중 평가, 교차 모델 평가가 필요하다.

⚠️ 평가에 temperature를 높게 두는 경우  
- 같은 답에 대해 점수가 흔들릴 수 있다. 평가는 생성보다 일관성이 더 중요하다.

📌 핵심: **합성 데이터 파이프라인의 품질은 생성 단계가 아니라, 평가와 필터링 단계에서 최종적으로 결정된다.**

## 3.8 이미지 데이터 증강: 텍스트와는 다른 확장 전략

강의 마지막에서는 이미지 데이터 증강이 등장한다.  
이 부분이 중요한 이유는, 텍스트에서는 합성 데이터가 빠른 해결책이 될 수 있지만, 이미지에서는 비용과 품질 문제 때문에 **기존 데이터를 변형하는 증강**이 더 현실적인 경우가 많기 때문이다.

### 개념 한 줄 정의

> **이미지 데이터 증강은 원본 이미지를 회전, 반전, 밝기 조절 등으로 변형해 데이터 수를 늘리는 방법이다.**

### 왜 필요한가

- 이미지 데이터를 새로 수집하는 비용이 크다.
- 소량 데이터로도 모델이 다양한 상황을 보게 만들 수 있다.
- 실제 원본의 의미를 크게 훼손하지 않으면서 학습 샘플 수를 늘릴 수 있다.

### TorchVision 기반 예시

~~~python
from torchvision import transforms

# 원본 이미지를 모델 입력 크기에 맞춰 정리하는 기본 전처리
base_transform = transforms.Compose([
    transforms.CenterCrop(640),     # 중앙을 기준으로 잘라 불필요한 배경을 줄인다.
    transforms.Resize((224, 224)),  # 모델 입력 크기에 맞춘다.
    transforms.ToTensor()           # 이미지 → 텐서 변환
])

# 증강용 전처리 파이프라인
aug_transform = transforms.Compose([
    transforms.CenterCrop(640),                           # 먼저 관심 영역을 정리하고
    transforms.Resize((400, 400)),                       # 약간 큰 상태로 맞춘 뒤
    transforms.RandomHorizontalFlip(p=0.5),              # 50% 확률로 좌우 반전
    transforms.RandomRotation(degrees=10),               # -10~10도 범위에서 회전
    transforms.RandomApply(
        [transforms.RandomGrayscale(p=1.0)], p=0.2
    ),                                                   # 일부만 흑백 처리
    transforms.ColorJitter(
        brightness=0.3,
        contrast=0.3,
        saturation=0.3
    ),                                                   # 밝기/대비/채도 변화
    transforms.RandomCrop((224, 224)),                   # 최종 입력 크기로 랜덤 크롭
    transforms.ToTensor()
])
~~~

### 쉬운 해설

텍스트 증강이 “같은 의미를 다른 표현으로 바꾸는 것”이라면,  
이미지 증강은 “같은 물체를 다른 촬영 조건처럼 보이게 하는 것”에 가깝다.

예를 들어 강아지 사진 한 장을:

- 조금 회전시키고,
- 좌우를 뒤집고,
- 밝기를 바꾸고,
- 일부를 크롭하면,

모델 입장에서는 서로 조금씩 다른 학습 예시를 더 많이 보게 된다.

### 자주 하는 실수 / 디버깅 포인트

⚠️ 증강이 과해서 원본 의미를 깨뜨리는 경우  
- 너무 큰 회전, 과한 crop, 심한 색 왜곡은 오히려 라벨 의미를 훼손할 수 있다.

⚠️ 텍스트와 이미지 전략을 같은 감각으로 보는 경우  
- 텍스트는 작은 표현 변화가 의미 왜곡으로 이어질 수 있고, 이미지는 작은 시각 변화가 더 자연스럽게 허용되는 편이다.

📌 핵심: **프로젝트 데이터 전략은 모달리티에 따라 달라진다. 텍스트는 합성 데이터가 빠를 수 있고, 이미지는 증강이 더 실용적인 경우가 많다.**

## 4. 적용 관점에서 다시 보기

이제 본문에서 본 내용을 “실제로 문제를 풀거나 프로젝트를 할 때 어떻게 떠올릴지” 기준으로 다시 묶어보자.

### 4.1 어떤 상황에서 무엇을 먼저 떠올릴까

| 상황 | 먼저 떠올릴 것 |
|---|---|
| API가 안 붙는다 | `.env`, 키 이름, `base_url`, 현재 작업 경로 |
| 출력 형식이 들쑥날쑥하다 | Few-shot, JSON 구조 명시, `response_format` |
| 계산/분석 답이 자주 틀린다 | CoT, 단계별 추론 유도 |
| 생성 문장이 너무 비슷하다 | `temperature`, `top_p`, persona 다양화 |
| 생성 문장이 엉뚱하다 | 파라미터 낮추기, 프롬프트 제약 강화, Judge 필터링 |
| 데이터가 많아질수록 후처리가 힘들다 | Structured Output, 스키마 설계 |
| 품질이 들쑥날쑥해 채택이 어렵다 | LLM as a Judge, rubric, 평균 점수 기반 filtering |
| 이미지 데이터가 부족하다 | 합성보다 먼저 augmentation 고려 |

### 4.2 구현 순서는 어떻게 잡으면 좋은가

실전에서는 아래 순서가 가장 안정적이다.

1. **환경 설정**
   - `.env` 구성
   - 키 로드 확인
   - API 호출 함수 작성

2. **작은 실험**
   - Zero-shot으로 먼저 시도
   - 형식이 흔들리면 Few-shot 추가
   - 추론이 필요하면 CoT 적용

3. **구조화**
   - JSON 스키마 설계
   - `response_format` 또는 파싱 함수 도입

4. **대량 생성**
   - 입력 조합(페르소나, 장르, 감성 등) 설계
   - 반복 호출 및 저장

5. **품질 평가**
   - 평가 기준 정의
   - Judge 프롬프트 설계
   - 점수/사유 기록

6. **선별과 분석**
   - 임계값 기반 필터링
   - 평균 점수 확인
   - 부족한 유형 재생성

### 4.3 문제를 보면 어떤 신호를 포착해야 할까

- “형식을 꼭 맞춰야 한다” → `response_format` 신호
- “같은 질문에 여러 스타일 답이 필요하다” → persona + Few-shot 신호
- “이유까지 있어야 한다” → CoT 또는 rubric 신호
- “많이 만들어야 한다” → 생성 비용과 평가 비용 분리 신호
- “좋은 데이터만 남겨야 한다” → Judge + threshold 신호
- “원본은 적지만 조금씩 변형은 가능하다” → augmentation 신호

### 4.4 실전에서 특히 자주 틀리는 패턴

⚠️ JSON을 요청만 하고 검증하지 않음  
→ 초반엔 편하지만 나중에 후처리 코드가 복잡해진다.

⚠️ temperature를 올려놓고 품질 검증 없이 그대로 저장  
→ 다양성은 늘어도 데이터셋 품질은 쉽게 흔들린다.

⚠️ Judge 점수만 보고 왜 점수가 낮았는지 안 봄  
→ filtering은 했는데 프롬프트 개선으로 연결되지 않는다.

⚠️ 합성 데이터와 데이터 증강을 섞어 생각함  
→ 어떤 전략이 더 적합한지 판단이 흐려진다.

📌 핵심: **실전에서는 “어떤 개념을 아는가”보다 “지금 문제에서 어떤 신호를 보고 어떤 도구를 꺼내야 하는가”가 더 중요하다.**

## 5. 배운 점 / 느낀 점 / 확장 포인트

이번 강의의 좋은 점은, 프롬프트 몇 개를 소개하고 끝나는 구성이 아니라  
LLM 기반 데이터 생성 작업을 **하나의 엔지니어링 파이프라인**으로 보게 만든다는 데 있다.

처음에는 환경변수 설정이 가장 사소한 부분처럼 보일 수 있다.  
하지만 실제로는 이 단계가 흔들리면 뒤의 모든 실습이 막힌다. 반대로 이 기반이 잡히면 프롬프팅 실험, 구조화 출력, 평가 자동화가 자연스럽게 이어진다.

또 하나 중요한 점은,  
좋은 합성 데이터는 “잘 생성된 데이터”가 아니라 **잘 선별된 데이터**라는 사실이다. 생성 모델은 후보를 많이 만들어주는 역할에 가깝고, Judge는 그 후보들 중에서 실제로 쓸 수 있는 샘플을 추리는 역할을 한다. 이 관점이 잡히면, 합성 데이터 품질 문제를 훨씬 현실적으로 다루게 된다.

확장 포인트도 분명하다.

- 텍스트 생성에서는 **RAG 평가**, **챗봇 응답 비교**, **A/B 테스트**로 Judge 개념을 확장할 수 있다.
- 구조화 출력은 단순 JSON을 넘어 **스키마 중심 파이프라인**으로 발전할 수 있다.
- 이미지 쪽은 오늘의 증강 기법을 바탕으로 이후 CNN, 비전 모델 학습과 직접 연결된다.
- 로컬 sLLM + 대형 평가 모델 조합은 비용 효율적인 MLOps 관점으로도 이어질 수 있다.

즉, 이번 장은 단순 실습이 아니라  
나중에 프로젝트를 만들 때 **데이터 파이프라인을 설계하는 사고방식**의 출발점이라고 볼 수 있다.

## 6. 요약 정리

### 📌 핵심

- API 키는 코드에 직접 넣지 말고 **환경변수**로 관리한다.
- 같은 모델이라도 **Zero-shot / Few-shot / CoT**에 따라 출력 품질과 구조가 달라진다.
- 합성 데이터는 텍스트를 하나 뽑는 것이 아니라, **구조화된 샘플**로 만드는 것이 중요하다.
- 프롬프트 기반 JSON보다 **`response_format` 기반 Structured Output**이 반복 생성에서 더 안정적이다.
- 대량 생성에서는 **생성과 평가를 분리**하는 전략이 유효하다.
- **LLM as a Judge**는 점수화와 필터링을 통해 합성 데이터 품질을 자동 관리하게 해준다.
- 텍스트와 이미지에서는 데이터 확장 전략이 다르며, 이미지는 **증강**이 더 실용적인 경우가 많다.

### 🧠 기억할 것

- “생성”만 잘한다고 좋은 데이터셋이 되지 않는다.
- “형식 안정화”와 “품질 검증”이 함께 있어야 파이프라인이 된다.
- 다양성을 높일수록 Judge의 중요성도 함께 커진다.
- 실전에서는 개념 암기보다, 문제 상황에서 어떤 도구를 꺼낼지 판단하는 감각이 더 중요하다.
