# 화면을 만들기 전에 정리할 것: UX 흐름, 화면 설계, 디자인 시스템

- 🎯 글의 목표: 아이디어와 참고 이미지를 바로 코드로 옮기기 전에 서비스 흐름, 정보 구조, 화면 책임, 디자인 방향, 공통 UI 규칙을 순서대로 구체화한다.
- 🧩 핵심 키워드: 사용자 흐름, 정보 구조, 라우팅, 레이아웃, 역할 기반 화면, 무드보드, 컨셉보드, 디자인 토큰, 컴포넌트, 화면 명세, 상태 설계
- ⭐ 중요도: ★★★★★ — 화면 목록과 상태·권한·데이터 책임이 불명확하면 예쁜 UI를 만들어도 실제 서비스 흐름과 맞지 않기 때문이다.
- 📝 한눈에 보는 내용: 요구사항에서 사용자 역할과 핵심 과업을 찾고, 사용자 흐름과 사이트맵으로 화면 관계를 정한다. 컨셉보드는 디자인 방향을, 디자인 시스템은 반복 가능한 구현 규칙을 정한다. 마지막으로 화면 명세를 데이터·행동·상태·이동 기준으로 작성한 뒤 React 컴포넌트와 라우터에 옮긴다.
- 🔗 관련 주제: React Router, TypeScript, Tailwind CSS, 접근성, 반응형 디자인, Figma
- 🧱 선수 지식: 웹 페이지, 컴포넌트, URL의 기본 개념

## 1. 들어가며

프로젝트 초기에 참고 이미지를 보고 바로 React 화면을 만들면 빠르게 결과가 나오는 것처럼 보인다. 그러나 화면이 늘어나면 로그인 후 어디로 가야 하는지, 역할마다 어떤 메뉴가 보여야 하는지, API가 아직 없을 때 무엇을 표시할지, 같은 버튼이 화면마다 왜 다르게 보이는지가 문제가 된다.

좋은 화면 설계는 픽셀을 배치하는 작업만이 아니다. 사용자가 목표를 달성하는 흐름과 시스템이 처리해야 할 상태를 시각적으로 표현하는 작업이다.

```text
서비스 요구사항
      ↓
사용자 역할과 핵심 과업
      ↓
사용자 흐름과 정보 구조
      ↓
화면 목록과 화면별 책임
      ↓
컨셉보드와 디자인 시스템
      ↓
상세 UI·상태·이동 명세
      ↓
React 컴포넌트와 라우터 구현
```

## 2. 핵심 개념 정리

비슷해 보이는 산출물의 목적을 구분한다.

| 산출물 | 답하려는 질문 |
| --- | --- |
| 사용자 흐름 | 사용자가 목표를 달성하려면 어떤 단계를 거치는가? |
| 정보 구조·사이트맵 | 화면과 메뉴는 어떤 계층으로 묶이는가? |
| 와이어프레임 | 한 화면 안에서 정보와 행동은 어디에 놓이는가? |
| 무드보드 | 사용자가 어떤 감정과 분위기를 느껴야 하는가? |
| 컨셉보드 | 그 분위기를 색·글꼴·형태·이미지에 어떻게 적용하는가? |
| 디자인 시스템 | 반복되는 UI를 어떤 규칙과 컴포넌트로 구현하는가? |
| 화면 명세 | 데이터, 행동, 상태, 이동, 실패 처리는 어떻게 동작하는가? |

하나의 큰 문서나 Figma 페이지에 모두 들어갈 수 있지만, 서로 다른 질문에 답한다는 점은 유지해야 한다.

## 3. 본문 정리

### 3.1 기능 목록보다 사용자와 목표를 먼저 찾는다

요구사항을 읽을 때 버튼과 페이지 이름부터 뽑으면 비슷한 화면이 중복되기 쉽다. 먼저 사용자의 역할과 핵심 목표를 정한다.

예를 들어 온라인 이벤트 서비스에는 다음 역할이 있을 수 있다.

| 역할 | 핵심 목표 | 대표 과업 |
| --- | --- | --- |
| 참여자 | 원하는 이벤트에 참여하고 현재 상태를 확인한다. | 탐색, 신청, 장비 확인, 대기, 통화, 결과 확인 |
| 진행자 | 참여자와의 세션에 집중한다. | 일정 확인, 참여자 정보 확인, 통화, 메모 |
| 운영자 | 행사의 흐름과 예외를 관리한다. | 이벤트 생성, 대기열, 재호출, 상태 변경, 공지 |
| 관리자 | 계정·권한·정책을 관리한다. | 역할 변경, 잠금, 감사 기록 확인 |

역할 이름이 다르더라도 다음 질문은 같다.

1. 이 사용자가 서비스에 들어오는 이유는 무엇인가?
2. 목표를 달성하기 전에 어떤 조건이 필요한가?
3. 어떤 데이터를 볼 수 있고 수정할 수 있는가?
4. 실패하거나 권한이 없을 때 어디로 가는가?

### 3.2 사용자 흐름은 정상 경로만 그리지 않는다

사용자 흐름은 페이지 이름을 화살표로 연결한 목록이 아니다. 사용자의 행동, 시스템 처리, 분기와 복구가 함께 있어야 한다.

```text
이벤트 상세
   ↓ 신청
입력값 검사
   ├─ 실패 → 오류 메시지와 입력 유지
   └─ 성공 → 신청 결과
                 ├─ 선정 전 → 대기 상태
                 ├─ 선정 → 장비 점검
                 └─ 미선정 → 안내와 다른 이벤트 탐색
```

다음 상태를 최소한 검토한다.

- 로딩: 데이터를 기다리는 동안 무엇을 보여주는가?
- 빈 상태: 데이터가 아직 없을 때 다음 행동을 안내하는가?
- 오류: 실패 원인과 재시도 방법이 보이는가?
- 권한 제한: 숨길 것과 접근 거부를 보여줄 것을 구분했는가?
- 네트워크 끊김: 입력과 진행 상태를 유지할 수 있는가?
- 동시 수정: 다른 운영자가 상태를 바꾼 경우 어떻게 갱신하는가?

### 3.3 정보 구조와 라우팅

정보 구조(Information Architecture)는 콘텐츠와 기능을 사용자가 찾기 쉬운 계층으로 조직하는 방식이다. 라우팅은 그 구조를 URL과 화면 전환 규칙으로 구현한다.

```text
서비스
├─ 공통
│  ├─ 로그인
│  ├─ 회원가입
│  └─ 권한 안내
├─ 참여자
│  ├─ 이벤트 목록
│  ├─ 이벤트 상세
│  └─ 내 신청
├─ 진행자
│  ├─ 일정
│  └─ 세션
└─ 운영자
   ├─ 운영 대시보드
   ├─ 대기열
   └─ 통계
```

React Router를 사용하지 않고도 상태와 조건문으로 화면을 바꿀 수 있다. 하지만 URL이 필요한 여러 화면, 새로고침 후 복원, 뒤로 가기, 직접 링크 공유가 필요한 서비스에서는 라우터가 책임을 명확하게 만든다.

```tsx
import { createBrowserRouter } from 'react-router-dom'

const router = createBrowserRouter([
  {
    path: '/',
    lazy: () => import('./layouts/PublicLayout'),
    children: [
      { index: true, lazy: () => import('./pages/HomePage') },
      { path: 'login', lazy: () => import('./pages/LoginPage') },
    ],
  },
  {
    path: '/manager',
    lazy: () => import('./layouts/ManagerLayout'),
    children: [
      { index: true, lazy: () => import('./pages/ManagerDashboardPage') },
    ],
  },
])
```

이 코드는 구조를 보여주는 예시이며 실제 프로젝트에서는 인증 로더, 오류 화면, 사용하는 React Router 버전을 함께 확인해야 한다.

### 3.4 Layout을 나누는 이유

Layout은 여러 페이지가 공유하는 화면 뼈대다. 상단바, 사이드바, 공통 여백, 역할별 메뉴가 대표적이다.

```text
ManagerLayout
├─ ManagerHeader
├─ ManagerNavigation
└─ Outlet
   └─ 현재 선택된 운영자 페이지
```

레이아웃을 역할마다 무조건 만들 필요는 없다. 다음 기준으로 나눈다.

- 화면 골격과 내비게이션이 실제로 다른가?
- 권한과 데이터 로딩 경계가 다른가?
- 여러 페이지에서 반복되는가?
- 하나의 레이아웃에 조건문이 지나치게 많아지는가?

### 3.5 Guard는 무엇을 보호하는가

Guard는 특정 화면에 들어가기 전에 인증·권한·상태 조건을 확인하는 개념적 이름이다. React Router의 고정된 단일 API 이름이라기보다 프로젝트에서 보호 로직을 구성하는 패턴으로 자주 사용한다.

```tsx
import { Navigate, Outlet } from 'react-router-dom'

type Role = 'fan' | 'creator' | 'manager'

type RoleGuardProps = {
  currentRole: Role | null
  allowedRoles: Role[]
}

export function RoleGuard({ currentRole, allowedRoles }: RoleGuardProps) {
  // 로그인 정보가 아직 없다면 로그인 화면으로 보낸다.
  if (currentRole === null) {
    return <Navigate to="/login" replace />
  }

  // 로그인했지만 역할이 맞지 않으면 권한 안내 화면으로 보낸다.
  if (!allowedRoles.includes(currentRole)) {
    return <Navigate to="/forbidden" replace />
  }

  // 조건을 통과했을 때만 하위 화면을 렌더링한다.
  return <Outlet />
}
```

⚠️ 주의: 프론트엔드 Guard는 화면 접근 경험을 제어할 뿐 서버 보안을 대신하지 않는다. API 서버도 매 요청마다 인증과 권한을 검증해야 한다.

### 3.6 Lazy loading은 왜 사용하는가

Lazy loading은 처음부터 모든 화면 코드를 내려받지 않고 필요할 때 가져오는 방식이다. 라우트가 많고 각 화면 코드가 큰 경우 초기 번들 크기를 줄이는 데 도움이 된다.

그러나 화면 파일을 모두 lazy로 만들면 무조건 빨라지는 것은 아니다. 작은 앱에서는 네트워크 요청과 로딩 경계가 늘 수 있다. 번들 분석과 실제 사용자 흐름을 보고 적용한다.

### 3.7 무드보드와 컨셉보드의 차이

무드보드는 감정과 분위기에 초점을 둔다.

```text
따뜻함 · 설렘 · 활기 · 신뢰
사진 · 질감 · 조명 · 색감
```

컨셉보드는 그 분위기를 실제 디자인 언어로 바꾼다.

```text
설렘
  → 선명한 포인트 컬러
  → 부드러운 곡선
  → 가벼운 탄성 애니메이션

스크랩북
  → 겹친 종이 카드
  → 테이프·스티커 모티프
  → 손으로 배치한 듯한 제한된 비정형 정렬
```

좋은 컨셉보드는 “예쁘고 에너지 넘치게”에서 끝나지 않는다. 다음을 정한다.

- 핵심 키워드 3~5개
- 사용자와 제공할 경험
- 주조색·보조색·강조색의 역할
- 제목·본문 글꼴의 관계
- 카드·버튼·입력창의 형태
- 이미지와 아이콘 스타일
- 애니메이션의 강도와 사용 조건
- 피해야 할 표현

### 3.8 참고 이미지는 복사 대상이 아니라 근거다

여러 레퍼런스를 섞을 때는 이미지마다 가져올 요소를 분리한다.

| 레퍼런스 | 가져올 요소 | 가져오지 않을 요소 |
| --- | --- | --- |
| 스크랩북 포스터 | 겹침, 종이 질감, 테이프 장식 | 작은 본문 글씨, 과도한 기울기 |
| 젤리 캐릭터 | 탄성, 반투명 하이라이트, 포인트 색 | 모든 카드의 과도한 3D 효과 |
| 영상 서비스 | 상태 표시, 화면 집중 구조 | 브랜드와 맞지 않는 어두운 색 전체 |

이 기준이 없으면 한 화면에 서로 다른 시각 언어가 경쟁하게 된다.

### 3.9 디자인 토큰으로 규칙을 코드에 연결하기

디자인 토큰은 색, 간격, 글자 크기, 모서리, 그림자 같은 값을 의미 중심 이름으로 관리하는 방식이다.

```css
:root {
  --color-brand-primary: #ff5f7a;
  --color-brand-accent: #8b5cf6;
  --color-surface: #fffaf6;
  --color-text-primary: #2f2430;
  --color-danger: #c62828;

  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --space-4: 1rem;
  --space-6: 1.5rem;

  --radius-sm: 0.5rem;
  --radius-md: 1rem;
  --radius-pill: 9999px;
}
```

`pink-500` 같은 색상 모양 이름만 쓰면 브랜드 색의 책임이 흐려질 수 있다. `brand-primary`, `danger`, `surface`처럼 의미를 함께 표현하면 테마가 바뀌어도 컴포넌트의 의도를 유지하기 쉽다.

### 3.10 공통 UI 컴포넌트의 범위

공통 UI Kit에는 자주 반복되고 상태 규칙을 공유하는 요소를 넣는다.

- Button: 크기, 강조 단계, 로딩, 비활성
- Input: label, 도움말, 오류, 필수 표시
- Badge/Chip: 상태 의미와 색상
- Tabs: 선택 상태와 키보드 이동
- Alert: 정보·성공·경고·오류
- Card: 정보 계층과 행동 위치
- Modal: 제목, 본문, 취소·확인, focus 관리

컴포넌트를 너무 일찍 추상화하면 서로 다른 요구를 억지로 하나에 넣게 된다. 실제로 2~3회 반복되고 상태와 접근성 규칙을 공유할 때 공통화한다.

### 3.11 화면 명세는 무엇을 포함해야 하는가

화면마다 다음 정보를 기록하면 기획, 디자인, 프론트엔드, 백엔드의 해석 차이를 줄일 수 있다.

| 항목 | 확인 질문 |
| --- | --- |
| 목적 | 사용자가 이 화면에서 끝내야 할 일은 무엇인가? |
| 진입 조건 | 로그인, 역할, 이전 단계가 필요한가? |
| 데이터 | 어떤 API와 필드가 필요한가? |
| 주요 행동 | Primary Action은 무엇인가? |
| 보조 행동 | 취소, 뒤로 가기, 상세 보기는 무엇인가? |
| 상태 | 로딩·빈 상태·오류·성공·비활성은 어떻게 보이는가? |
| 검증 | 입력값을 어디서 어떤 기준으로 검사하는가? |
| 이동 | 성공·취소·오류·권한 실패 후 어디로 가는가? |
| 접근성 | 키보드, focus, label, 알림 전달이 가능한가? |

### 3.12 API가 없을 때 화면이 안 보이는 문제

화면 파일이 존재해도 API가 구현되지 않았거나 빈 응답을 반환하면 콘텐츠가 보이지 않을 수 있다. 이때 “페이지가 구현되지 않았다”와 “데이터가 없어 표시할 내용이 없다”를 구분한다.

```tsx
type StatisticsState =
  | { status: 'loading' }
  | { status: 'empty' }
  | { status: 'error'; message: string }
  | { status: 'success'; totalApplicants: number }

function StatisticsPanel({ state }: { state: StatisticsState }) {
  if (state.status === 'loading') return <p>통계를 불러오는 중입니다.</p>
  if (state.status === 'empty') return <p>아직 집계된 데이터가 없습니다.</p>
  if (state.status === 'error') return <p role="alert">{state.message}</p>

  return <p>총 응모자: {state.totalApplicants}명</p>
}
```

이렇게 상태를 명시하면 백지 화면 대신 현재 상황과 다음 행동을 보여줄 수 있다.

### 3.13 사용자에게 내부 ID를 입력시키지 않는다

DB의 `influencer_id`처럼 내부 식별자는 시스템에는 필요하지만 사용자가 외우는 값이 아니다. 사용자는 닉네임이나 검색어로 대상을 찾고, UI가 선택한 결과의 내부 ID를 API 요청에 사용하도록 설계한다.

```text
사용자: 닉네임 입력
        ↓
서버: 검색 후보 반환
        ↓
사용자: 정확한 대상 선택
        ↓
프론트엔드: 선택 결과의 내부 ID 보관
        ↓
생성 API에 ID 전송
```

닉네임은 중복될 수 있으므로 입력 문자열만으로 곧바로 대상을 확정하지 않는다. 프로필 이미지, 소속, 고유 핸들 등 식별 보조 정보를 함께 제공한다.

### Bootstrap, Tailwind CSS, 직접 작성 CSS

| 선택 | 장점 | 주의점 |

도구보다 중요한 것은 팀이 한 방식을 일관되게 사용하고, 디자인 토큰과 컴포넌트 책임을 공유하는 것이다.

## 5. 배운 점 / 확장 포인트

### 5.1 새로 이해한 것

- 라우터는 React의 필수 문법은 아니지만 URL 기반 다중 화면의 책임을 관리한다.
- Layout은 공통 골격, Guard는 진입 조건, Lazy loading은 코드 로딩 시점을 다룬다.
- 무드보드는 분위기, 컨셉보드는 적용 방향, 디자인 시스템은 반복 가능한 구현 규칙이다.
- 페이지가 존재하는 것과 실제 데이터가 표시되는 것은 다른 문제다.
- 사용자는 내부 ID가 아니라 이해할 수 있는 검색·선택 UI를 사용해야 한다.

### 5.2 이전·다음 학습과의 연결

이 문서는 React Router, 상태 관리, API 데이터 패칭, 웹 접근성, 테스트 문서와 연결된다. 이후에는 화면 명세를 TypeScript 타입과 API 스키마로 연결하는 계약 기반 개발을 학습할 수 있다.

### 5.3 더 확인할 주제

- 역할 기반 접근 제어와 서버 인가
- 디자인 토큰을 Tailwind 설정과 CSS 변수에 연결하는 방법
- Storybook을 이용한 컴포넌트 상태 문서화
- 사용자 흐름 기반 E2E 테스트

## 6. 요약 정리

1. 화면 설계는 사용자 목표와 서비스 상태를 표현하는 작업이다.
2. 사용자 역할과 핵심 과업을 기능 목록보다 먼저 정한다.
3. 정상 흐름뿐 아니라 로딩·빈 상태·오류·권한·재시도를 설계한다.
4. 정보 구조는 화면 계층을, 라우팅은 URL과 전환을 구현한다.
5. Layout, Guard, Lazy loading은 서로 다른 책임을 가진다.
6. 무드보드는 감정, 컨셉보드는 시각 적용 방향을 다룬다.
7. 디자인 토큰은 반복되는 값을 의미 중심 규칙으로 만든다.
8. 화면 명세는 데이터, 행동, 상태, 이동과 실패 처리를 포함한다.
9. API가 없을 때도 백지 대신 현재 상태를 설명해야 한다.
10. 사용자가 내부 ID를 직접 입력하도록 설계하지 않는다.

🧠 기억할 것: 코드를 만들기 전에 “누가, 어떤 목표로, 어떤 상태를 거쳐, 어디로 이동하는가”를 먼저 그린다.
