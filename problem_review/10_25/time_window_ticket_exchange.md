## 1. 들어가며

처음에는 가장 선호하지 않는 실습 참가권을 가지고 있다. 다른 참가자들의 교환 요청을 이용해 더 원하는 참가권을 얻고 싶지만, 각 요청에는 이용 가능한 시간이 정해져 있다. 좋은 참가권으로 가는 연결이 있어도 이미 교환 시간이 끝났다면 이용할 수 없다.

여기서 최종 목표는 **선호도가 가장 높은 실습 이름**이고, 탐색 과정에서 관리할 값은 **각 참가권을 가장 일찍 얻는 시각**이다. 더 일찍 확보하면 뒤의 교환 시간을 기다릴 수 있기 때문이다. 두 기준을 분리하면 시간대별로 모든 선택을 직접 시뮬레이션하지 않아도 된다.

대화에서 `heapq`와 다익스트라 사용이 가능하다고 확인되었다. 이번 노트는 일반적인 고정 거리의 다익스트라를 그대로 외워 쓰기보다, “현재 시각과 교환 시작 시각 중 늦은 시각으로 이동한다”는 전이 규칙이 왜 성립하는지부터 설명한다.

## 2. 핵심 개념 정리

입력의 요청은 상대방 관점으로 쓰여 있다. 먼저 내 참가권이 어떻게 바뀌는지 방향을 뒤집어 읽고, 이용 가능한 시각을 계산해야 한다.

```text
요청: [시작, 종료, 상대가 보유한 참가권, 상대가 원하는 참가권]
  → 내 이동: 상대가 원하는 참가권 → 상대가 보유한 참가권
  → 교환 시각 = max(내 획득 시각, 요청 시작 시각)
  → 교환 시각 < 종료 시각이면 도착 후보 갱신
  → 가장 이른 후보부터 조사
  → 도달 가능한 참가권 중 선호도가 가장 높은 이름 반환
```

그래프의 정점은 참가권 종류이고, 간선은 교환 요청 하나다. 최소 힙은 다음으로 조사할 후보를 시각순으로 꺼내는 도구이며, 선호도 순서는 마지막 답을 고르는 데 사용한다.

## 3. 본문 정리

### 3.1 확인한 입력·출력과 시간 규칙

`preferences`는 덜 선호하는 실습부터 더 선호하는 실습 순서의 이름 목록이다. 이름별 선호도는 서로 다르며, 시작 참가권은 `preferences[0]`이다. 시간은 오늘 `00:00`부터 시작하고, 참가권을 그대로 유지하거나 아무 교환도 하지 않아도 된다.

교환 요청 `[start, end, offered, wanted]`의 `offered`는 요청자가 가진 참가권이고 `wanted`는 요청자가 받으려는 참가권이다. 내가 `wanted`를 가지고 있어야 교환하여 `offered`를 받는다.

| 입력 조건 | 풀이에 주는 의미 |
| --- | --- |
| 실습 종류 2~3000개, 요청 1~3000개 | 인접 리스트로 실제 요청만 저장한다. |
| 시각은 `HH:MM`, `00:00`~`23:59`, 시작 < 종료 | 자정부터 지난 분으로 비교할 수 있다. |
| 시작 이상, 종료 미만에만 교환 가능 | `start <= time < end`를 지킨다. |
| 교환 시간은 0, 같은 시각에 여러 번 가능 | 도착 시각에 1분을 더하지 않는다. |
| 각 요청은 서로 다른 참가자가 등록, 요청당 최대 한 번 | 해당 요청을 같은 경로에서 재사용할 필요가 없는지 검토한다. |
| 이용하지 않은 요청은 지정 시간 동안 유효 | 임의의 다른 사람 간 교환으로 요청이 사라지는 상황은 모델링하지 않는다. |
| 요청은 정렬되어 있지 않음 | 입력 순서가 실제 이용 순서라는 가정을 하지 않는다. |

모든 실습 이름은 `preferences`에 포함되며, 한 요청의 보유·희망 실습은 서로 다르다. 대화의 “선호도 갖은 실습 참가권 교환 가능”이라는 문장은 오타가 있어 그 문장만으로 별도 제한을 확정하지 않는다. 명시된 교환 가능 조건에는 선호도 상승 제한이 없으므로, 이 정리에서는 선호도가 내려가는 중간 교환도 허용한다.

### 3.2 교환 요청의 방향을 내 입장에서 읽기

방향 그래프는 연결에 방향이 있는 그래프다. `A → B`는 A에서 B로 이동할 수 있다는 뜻이지, B에서 A로도 갈 수 있다는 뜻은 아니다.

요청이 `["09:00", "18:00", "security", "ai"]`이면 요청자는 security를 주고 ai를 받으려 한다. 따라서 **나는 ai를 가지고 있어야 security를 받을 수 있다.** 간선 방향은 `ai → security`다.

인접 리스트는 출발점별로 이용할 수 있는 간선 목록을 저장하는 방식이다. 이 문제에서는 `graph[ai의 번호]` 안에 `(security의 번호, 540, 1080)`을 넣는다. 540과 1080은 각각 9시와 18시를 분으로 바꾼 값이다.

⚠️ 주의: 입력의 세 번째·네 번째 항목 순서대로 `offered → wanted`를 만들면 반대 방향으로 탐색하게 된다. “내가 지금 가진 티켓이 상대방이 원하는 티켓인가?”를 먼저 확인한다.

### 3.3 현재 시각에서 실제 교환 시각을 계산하기

문자열 `"09:30"`에서 앞 두 글자는 9시, 네 번째 글자부터는 30분이다. `9 * 60 + 30 = 570`처럼 분으로 바꾸면 비교와 대기 계산이 명확해진다. 아래 코드에서는 문자열 슬라이싱과 `int`만 사용한다.

어떤 참가권을 `t`분에 얻었고 요청 시간이 `[s, e)`라면, 이용 가능한 가장 이른 시각은 `max(t, s)`다. `[s, e)`는 s를 포함하고 e를 제외한다는 수학적 구간 표기다.

| 현재 획득 시각 | 요청 시간 | 실제 교환 시각 | 이용 가능 |
| --- | --- | --- | --- |
| 08:00 | 09:00~10:00 | 09:00 | 시작까지 기다리므로 가능 |
| 09:30 | 09:00~10:00 | 09:30 | 즉시 가능 |
| 10:00 | 09:00~10:00 | 10:00 | 종료 시각이므로 불가능 |

교환에 걸리는 시간은 없으므로 `next_time = max(time, start_time)`이고, 이용 가능 조건은 `next_time < end_time`다. 시각을 1씩 늘리며 하루를 모두 순회할 필요가 없다.

⚠️ 주의: `next_time <= end_time`으로 검사하거나 교환 후 1분을 더하면 문제 조건이 달라진다. 종료 시각은 제외하고, 같은 시각의 연속 교환은 허용한다.

### 3.4 왜 참가권별 가장 이른 시각 하나만 저장하는가?

`earliest[v]`는 참가권 v를 얻을 수 있는 가장 이른 시각이다. v를 9시에 얻는 방법과 11시에 얻는 방법이 있다면, 9시에 얻은 뒤 11시까지 기다릴 수 있다. 참가권 유지에 비용·만료가 없으므로 늦게 얻는 것이 더 유리해지지 않는다.

여기서 `earliest`의 여러 칸이 채워졌다고 여러 참가권을 동시에 보유하는 것은 아니다. 각각 **서로 다른 선택 경로에서 그 참가권을 얻을 수 있다**는 가능성을 저장한다. 그중 실제로 목표로 삼을 하나를 마지막에 고른다.

단순 방문 배열로 “처음 발견했으니 끝”이라고 처리하면 안 된다. 예를 들어 cloud에서 ai로 직접 교환하는 시각이 15시여도, cloud → security → ai로 9시에 도착할 수 있다. ai의 기록을 9시로 갱신해야 10시에 끝나는 후속 요청을 사용할 수 있다.

이 설명에는 요청 사용 이력이 영향을 주지 않는다는 근거가 필요하다. 다음 절에서 1회 사용 제한을 별도로 확인한다.

### 3.5 요청당 1회 제한인데 사용 목록을 저장하지 않아도 되는 이유

요청 사용 이력을 무시해도 되는 것은 일반적인 그래프 문제의 규칙이 아니라 **이 문제의 대기·교환 조건에서 도출한 성질**이다. 요청을 이용하는 동안 시간은 줄어들지 않고, 같은 참가권을 원하는 만큼 유지할 수 있다.

어떤 경로가 `A → B → A`로 돌아왔다고 하자. 처음 A를 가진 시각이 9시, 돌아온 시각이 10시라면, 중간 두 교환을 하지 않고 A를 10시까지 유지해도 이후의 교환을 같은 시각에 시작할 수 있다. 이때 중간 요청을 소비하지 않았으므로 나중 선택에 불리해지지도 않는다.

이렇게 같은 참가권을 다시 방문하는 구간을 없애면, 가능한 도달 경로를 **정점을 반복하지 않는 경로**로 바꿀 수 있다. 정점을 반복하지 않으면 같은 요청 간선도 반복해서 사용할 수 없다. 따라서 요청 재사용을 허용한 그래프에서 도달 가능하더라도, 사이클을 지운 실제 1회 사용 경로가 존재한다.

이 성질 때문에 알고리즘에 요청별 `used` 배열을 넣지 않아도 최종 도달 가능성을 올바르게 구한다. 여러 후보 경로를 조사하면서 요청을 전역적으로 “사용 완료” 처리하면 오히려 아직 선택하지 않은 다른 경로를 잘못 차단한다.

⚠️ 주의: 대기에 비용이 들거나 참가권을 일정 시간 안에 넘겨야 한다면 위 논리가 깨질 수 있다. 그런 조건에서도 무조건 참가권별 시각 하나로 충분하다고 일반화하면 안 된다.

### 3.6 시간 구간이 있어도 다익스트라를 사용할 수 있는 이유

다익스트라는 현재 후보 중 가장 작은 도달 비용부터 확정해 가는 알고리즘이다. 이 문제에서 비용은 이동 거리 대신 **도달 시각**이며, 요청을 이용한 다음 시각은 `max(t, s)`다.

현재 시각 t보다 다음 시각이 작아질 수 없고, 일찍 도착한 사람이 기다린 뒤 늦게 도착한 사람과 같은 교환을 할 수 있다. 즉, 같은 요청에서 늦게 출발했다고 더 일찍 도착하는 역전이 없다. 이를 시간 의존 경로에서 FIFO 성질이라고 부르며, 여기서는 `max(t, s)`의 단조성과 대기 가능성으로 확인할 수 있다.

최소 힙에서 가장 이른 유효 후보를 꺼냈는데 더 이른 미발견 경로가 있다고 가정하면, 그 경로의 앞부분에도 현재보다 이른 후보가 있어야 한다. 그런 후보가 힙에서 먼저 처리되었어야 하므로 모순이다. 따라서 더 늦은 후보를 먼저 확정하지 않고 도달 시각순으로 조사할 수 있다.

`heapq`의 `heappush`는 후보를 넣고, `heappop`은 가장 작은 후보를 꺼낸다. `(time, ticket_id)` 튜플을 넣으면 시각을 우선 비교하고 시각이 같을 때 번호를 비교한다. 번호는 동점 처리에 쓰일 뿐 선호도를 먼저 고르는 기준이 아니다. [Python 공식 문서: heapq](https://docs.python.org/3.12/library/heapq.html)

같은 참가권의 더 이른 시각을 발견해도 예전 후보를 힙 중간에서 지우지는 않는다. 나중에 꺼냈을 때 `time != earliest[current]`라면 오래된 후보이므로 건너뛴다. 같은 시각으로는 갱신하지 않는 엄격한 `<` 비교도 있어, 0시간 교환 사이클이 무한히 후보를 만들지 않는다.

### 3.7 전체 풀이 코드

다음은 [time_window_ticket_exchange.py](./time_window_ticket_exchange.py)의 완성된 코드다. 문제 조건을 만족하는 `preferences`·`requests`를 받는 함수이며 입력 목록을 수정하지 않는다. 표준 라이브러리 외의 설치는 필요 없다.

```python
import heapq  # 가장 이른 시각의 후보를 먼저 꺼내는 최소 힙을 사용한다.


def solution(preferences, requests):
    n = len(preferences)  # 실습 종류의 수이며, 뒤쪽 실습일수록 더 선호한다.
    index = {}  # 실습 이름을 배열에서 사용할 정수 번호로 바꾼다.
    for i, name in enumerate(preferences):  # 번호 0이 처음 보유한 실습이다.
        index[name] = i  # 이름과 선호도 순서 번호를 연결한다.

    graph = [[] for _ in range(n)]  # 내가 가진 참가권별로 가능한 교환 요청을 저장한다.
    for start, end, offered, wanted in requests:  # offered/wanted는 요청자 관점이다.
        start_time = int(start[:2]) * 60 + int(start[3:])  # HH:MM을 자정 이후 분으로 바꾼다.
        end_time = int(end[:2]) * 60 + int(end[3:])  # 종료 시각은 교환할 수 없는 경계다.
        source = index[wanted]  # 내가 이 참가권을 가지고 있어야 요청을 이용할 수 있다.
        target = index[offered]  # 교환 후 내가 받는 참가권의 번호다.
        graph[source].append((target, start_time, end_time))  # wanted → offered 방향이다.

    inf = float("inf")  # 아직 그 참가권을 얻는 방법을 찾지 못했다는 표시다.
    earliest = [inf] * n  # 참가권별 가장 이른 획득 시각만 저장한다.
    earliest[0] = 0  # 00:00부터 가장 선호도가 낮은 참가권을 가지고 있다.
    heap = [(0, 0)]  # (획득 시각, 참가권 번호)이므로 시각이 작은 후보가 우선이다.

    while heap:  # 더 조사할 도달 후보가 있는 동안 반복한다.
        time, current = heapq.heappop(heap)  # 가장 이른 후보부터 다음 교환을 조사한다.
        if time != earliest[current]:  # 더 이른 기록으로 대체된 오래된 후보라면 버린다.
            continue

        for target, start_time, end_time in graph[current]:  # 현재 참가권을 원하는 요청들이다.
            next_time = max(time, start_time)  # 일찍 도착했으면 시작 시각까지 기다린다.
            if next_time >= end_time:  # 종료 시각과 같거나 늦으면 이용할 수 없다.
                continue
            if next_time < earliest[target]:  # 실제로 더 일찍 얻는 경우에만 갱신한다.
                earliest[target] = next_time  # 교환 시간이 0이므로 실행 시각이 획득 시각이다.
                heapq.heappush(heap, (next_time, target))  # 같은 시각의 연속 교환도 처리한다.

    for i in range(n - 1, -1, -1):  # 가장 선호하는 실습부터 도달 가능 여부를 확인한다.
        if earliest[i] != inf:  # 한 번 얻었다면 이후 교환하지 않고 유지할 수 있다.
            return preferences[i]  # 번호가 아니라 문제에서 요구한 실습 이름을 반환한다.
```

`index`는 이름으로 배열 위치를 찾는 딕셔너리다. `earliest`의 초기값인 `float("inf")`는 무한대로, 아직 도달 방법을 찾지 못했다는 표시이며 실제 시각이 아니다.

핵심 반복문은 현재 참가권에서 가능한 요청마다 `next_time`을 계산한 뒤, 기간 안에 있고 기존 기록보다 빠를 때만 갱신한다. 탐색이 끝나면 `range(n - 1, -1, -1)`로 마지막 번호부터 0까지 역순 확인한다. 시작 참가권은 항상 도달 가능하므로, 어떤 교환도 못 해도 `preferences[0]`이 반환된다.

### 3.8 같은 시각의 연속 교환을 따라가기

다음은 요청 배열의 순서와 실제 교환 순서가 다른 복습 예제다. 전체 풀이를 같은 파일에 두었다면 아래 호출 코드를 이어 붙여 실행할 수 있다.

```python
preferences = ["cloud", "ai", "security", "mobility"]  # 오른쪽일수록 더 선호한다.
requests = [
    ["09:00", "10:00", "mobility", "security"],  # security → mobility 요청이 먼저 적혀 있다.
    ["09:00", "10:00", "security", "ai"],  # ai → security가 그다음이다.
    ["09:00", "10:00", "ai", "cloud"],  # 실제로 처음 이용할 cloud → ai는 마지막이다.
]
print(solution(preferences, requests))  # 예상 출력: mobility
```

시작 기록은 cloud의 0분이고 나머지는 무한대다. cloud에서 ai로 가는 요청은 9시에 시작하므로 기다렸다가 540분에 도착한다. 이어지는 두 요청도 540분에 유효하여 다음처럼 갱신한다.

| 처리하는 참가권 | 현재 시각 | 새로 얻는 참가권 | 획득 시각 |
| --- | ---: | --- | ---: |
| cloud | 0 | ai | 540 |
| ai | 540 | security | 540 |
| security | 540 | mobility | 540 |

입력 순서대로 한 번만 요청을 검사하면 앞에 있던 요청들을 놓칠 수 있다. 인접 리스트와 힙으로 새 도달 후보를 계속 처리하면 입력 순서와 무관하게 같은 시각의 연결을 끝까지 따라간다.

### 3.9 최종 선호도와 중간 선택을 혼동하지 않기

보충 설명: 다음은 흔한 잘못된 접근을 구분하기 위해 작성한 반례다. 사용자에게 실제로 발생했던 오류라고 기록하는 것은 아니다.

| 잘못된 판단 | 반례 또는 확인 방법 |
| --- | --- |
| 더 선호하는 참가권으로만 이동한다. | cloud → security → ai → mobility처럼 중간에 내려가야 최종 선호도가 더 높아질 수 있다. |
| 제일 빨리 얻은 새 참가권을 바로 반환한다. | 9시의 ai보다 20시의 mobility를 최종적으로 더 선호할 수 있다. |
| 참가권을 처음 발견한 시각으로 확정한다. | ai를 15시에 얻는 경로보다 나중에 조사한 경로가 ai를 9시에 줄 수 있다. |
| 요청을 시작 시각순으로 한 번만 순회하면 된다. | 같은 시작 시각의 요청들이 필요한 교환 순서와 반대로 주어질 수 있다. |
| 요청을 탐색에서 한 번 조사했으니 사용 완료로 표시한다. | 조사한 후보 경로들은 대안이므로 서로의 요청을 실제로 소비하지 않는다. |

실습 종류를 `N`, 요청 수를 `M`이라 하면 그래프와 초기 배열을 만드는 데 `O(N+M)`이 든다. 유효하게 꺼낸 정점에서 나가는 요청을 조사하며 성공한 갱신 수는 최대 요청 수에 비례한다. 오래된 후보까지 고려하면 시간은 `O(N + M log(M+1))`, 보조 공간은 `O(N+M)`으로 잡을 수 있다.

같은 실습 사이에 여러 요청이 있을 수 있으므로 힙 크기를 단순히 정점 수라고 단정하지 않았다. `N, M ≤ 3000`에서 요청의 모든 순서를 완전 탐색하는 것보다 훨씬 작게 상태를 관리한다.


Python 3.12.12에서 실제 실행한 전체 결과는 9개 테스트 메서드 통과다. 이 문제에 해당하는 검사 범위는 다음과 같다.

- 실습 3개, 세 종류의 작은 시간 구간, 요청 1~3개를 조합한 모든 요청 배열 6,174개.

- 실습 3,000개·요청 3,000개의 역순 연결 사슬과 순환 간선.
- 입력 요청이 바뀌지 않는지, Markdown 전체 풀이 코드와 실행 파일이 같은지 확인.

보충 설명: 비교 기준 함수는 힙이나 `earliest`를 사용하지 않는다. 요청별 `used` 목록을 두고 가능한 교환 순서를 재귀로 모두 조사한다. 매 교환은 가장 이른 이용 시각에 하고, 다음 요청을 앞두고 기다리는 것으로 나중 교환 선택도 표현한다. 분기에서 돌아오면 `used`를 복원하여 다른 순서를 조사한다.

이 독립 비교는 특히 “요청당 한 번” 제약을 생략한 최종 풀이의 결과가 직접 제약을 적용한 결과와 맞는지 확인하기 위한 것이다. 작은 입력 비교와 논증은 함께 사용하며, 일부 테스트 통과를 모든 입력의 형식적 증명이라고 부르지 않는다. 공식 채점 사이트 제출·시간 제한·최대 메모리 측정은 수행하지 않았다.

## 4. 적용 관점에서 다시 보기

이 문제는 요청을 내 입장으로 다시 쓰는 것부터 시작한다. `wanted → offered`로 간선을 만든 뒤, 각 참가권의 상태를 가장 이른 획득 시각으로 정의하고, `max(현재 시각, 시작 시각) < 종료 시각`인 경우만 갱신한다.

오답을 점검할 때는 방향, 종료 시각, 같은 시각의 연속 교환 순서로 살핀다. 그다음 최초 발견을 확정으로 오해했는지, 선호도가 낮아지는 중간 이동을 막았는지 확인한다. 힙에서는 시각을 기준으로 조사하고, 정답에서는 선호도를 기준으로 고른다는 역할 구분을 끝까지 유지한다.

## 5. 배운 점 / 확장 포인트

### 5.1 이번 노트의 핵심 이해

최종 목표와 탐색 우선순위는 같지 않을 수 있다. 자유롭게 기다릴 수 있고 시간이 역행하지 않는 이 문제에서는 가장 이른 획득 시각이 늦은 도착을 대신하며, 사이클 제거로 요청 1회 제한도 만족하는 경로를 얻을 수 있다.

### 5.2 이전·다음 학습과의 연결

[다익스트라 기초](../../Algorithm/04_07_graph_2/04_06_graph_2.md)의 거리 갱신을 시간 구간이 있는 도달 시각 갱신으로 확장했다. [같은 날의 격자 문제](./square_components.md)에서는 방문 여부만으로 충분했지만, 여기서는 더 이른 기록으로 갱신할 수 있어 상태의 의미가 달라진다.

획득 시각뿐 아니라 실제 교환 요청 순서를 반환하려면 어떤 이전 경로 정보를 저장해야 할까? 교환 소요 시간·참가권 만료·대기 제한을 추가했을 때 지금의 상태와 사이클 제거 논리가 유지되는지도 별도 문제로 검토할 수 있다.

## 6. 요약 정리

- 요청자는 offered를 주고 wanted를 받으므로 내 이동은 `wanted → offered`다.
- `HH:MM`은 자정부터 지난 분으로 바꾸어 비교한다.
- 실제 교환 시각은 `max(현재 획득 시각, 시작 시각)`이며 종료 시각보다 작아야 한다.
- 교환 시간은 0이므로 같은 시각에 여러 요청을 연속으로 이용할 수 있다.
- 일찍 얻은 참가권은 기다릴 수 있어 가장 이른 시각만 저장한다.
- 같은 참가권으로 돌아오는 경로는 대기로 대체할 수 있어 요청 재사용이 필수적이지 않다.
- 힙에서는 시각이 빠른 후보를 꺼내고, 오래된 후보는 건너뛴다.
- 마지막에는 도달 가능한 이름을 선호도 높은 순서로 고른다.

🧠 기억할 것: **가장 빨리 얻을 수 있는 시각으로 가능성을 넓히고, 그 가능성 안에서 가장 원하는 참가권을 고른다.**

2. ai를 정확히 10:00에 얻으면 위 요청을 이용할 수 있는가?
3. 같은 참가권을 9시와 11시에 얻는 두 경로 중 11시 상태를 따로 저장하지 않는 이유는?
4. 요청별 사용 배열을 생략할 수 있다는 근거를 `A → B → A`와 대기를 이용해 설명해 보자.
5. cloud → security → ai → mobility 경로에서 security → ai를 무조건 막으면 어떤 문제가 생기는가?

<details>
<summary>정답과 해설</summary>

1. `ai → security`다. 내가 ai를 줘야 요청자가 가진 security를 받는다.
2. 이용할 수 없다. 10:00은 종료 시각이므로 `교환 시각 < 종료 시각`을 만족하지 않는다.
3. 9시에 얻은 뒤 11시까지 유지하면 된다. 자유로운 대기와 참가권 유지가 허용되므로 더 늦은 획득이 선택지를 늘리지 않는다.
4. A로 돌아오는 교환을 하지 않고 처음부터 A를 같은 시각까지 보유할 수 있다. 반복 정점 구간을 제거하면 요청을 반복하지 않는 도달 경로로 바꿀 수 있다.
5. 중간 선호도는 내려가더라도 마지막에 더 높은 mobility를 얻을 수 있다. 최종 선호도를 최대화하는 문제이지 매 교환의 선호도를 올리는 문제가 아니다.
