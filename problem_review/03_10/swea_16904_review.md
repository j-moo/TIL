# [16904] 문제풀이 정리

- 📚 문제 출처: **SWEA**
- 🔗 문제 링크: 사용자 미제공
- 🧭 문제 유형: **그리디(Greedy), 정렬**
- 🎯 목표: **서로 겹치지 않게 작업을 선택하면서 최대 몇 개까지 배정할 수 있는지 구하기**
- 🧩 키워드: **종료시간 정렬, 활동 선택(Activity Selection), last_end 갱신**
- ⭐ 난이도: 중
- 🛠 핵심 알고리즘: **종료 시간이 빠른 작업부터 선택하는 그리디**

---

## 1. 문제 이해

이 문제는 여러 개의 작업이 주어졌을 때,  
**서로 시간이 겹치지 않도록 작업을 선택하면서 최대 개수**를 구하는 문제다.

각 작업은 보통 `[시작시간, 종료시간]` 형태로 주어지고,  
이미 선택한 작업이 끝나기 전에 시작하는 작업은 함께 선택할 수 없다.

즉, 핵심 질문은 이것이다.

> **“겹치지 않게 가장 많은 작업을 고르려면 어떤 기준으로 골라야 할까?”**

이 문제에서 중요한 점은 단순히 빨리 시작하는 작업을 고르는 것이 아니라,  
**뒤에 더 많은 작업을 붙일 수 있도록 빨리 끝나는 작업을 우선적으로 고려해야 한다**는 점이다.

---

## 2. 문제를 내 말로 재정의

쉽게 말하면 이런 문제다.

- 여러 개의 일정이 있다.
- 한 번에 하나의 일정만 할 수 있다.
- 앞에서 고른 일정이 끝나야 다음 일정을 시작할 수 있다.
- 이때 **최대한 많은 일정**을 넣고 싶다.

헷갈리기 쉬운 포인트는 다음과 같다.

- **시작시간이 빠른 작업**이 유리한 게 아니다.
- **작업 길이가 짧은 작업**이라고 항상 좋은 것도 아니다.
- 이 문제에서는 **종료시간이 빠른 작업을 먼저 고르는 기준**이 핵심이다.

---

## 3. 관련 개념 정리

### 3-1. 그리디(Greedy)

그리디는 매 순간 **가장 좋아 보이는 선택**을 하는 방식이다.

이 문제에서는 그 선택 기준이 바로 다음과 같다.

- **현재 시점에서 가장 빨리 끝나는 작업을 먼저 고른다.**

이렇게 해야 이후에 더 많은 작업을 넣을 수 있기 때문이다.

### 3-2. 왜 종료시간 기준인가?

작업을 많이 선택하려면  
현재 하나를 선택했을 때 **미래 선택의 여유 공간이 많이 남아야 한다.**

예를 들어:

- 늦게 끝나는 작업을 고르면 뒤 일정이 많이 막힌다.
- 빨리 끝나는 작업을 고르면 다음 작업을 이어 붙일 수 있는 가능성이 커진다.

즉, 이 문제는  
**“지금 하나를 고를 때, 뒤에 남는 시간을 최대화하는 방향”** 으로 생각해야 한다.

### 3-3. 활동 선택 문제(Activity Selection)

이 문제는 전형적인 활동 선택 문제와 매우 비슷하다.

핵심 패턴은 거의 같다.

1. 종료시간 기준 정렬
2. 가장 빨리 끝나는 작업부터 순회
3. 이전 작업과 겹치지 않으면 선택

이 패턴은 이후 회의실 배정, 스케줄 선택 문제에도 자주 나온다.

---

## 4. 내 풀이 아이디어 분석

네 코드는 문제 핵심을 잘 파악한 **정석적인 그리디 풀이**다.

풀이 흐름은 다음과 같다.

1. `N`개의 작업을 입력받아 `work_list`에 저장한다.
2. `work_list`를 **종료시간 기준으로 정렬**한다.
3. 마지막으로 선택한 작업의 종료시간을 `last_end`에 저장한다.
4. 정렬된 작업을 앞에서부터 보면서,
   - `start >= last_end` 이면 선택
   - `count` 증가
   - `last_end = end` 갱신

이 접근의 장점은 다음과 같다.

- **핵심 아이디어가 코드에 바로 드러난다.**
- 구현이 짧고 명확하다.
- 완전탐색이 아니라 정렬 + 순회만 사용해서 효율적이다.

즉, 문제 요구와 알고리즘 선택이 잘 맞는 풀이야.

---

## 5. 최종 풀이 전략

### 단계별 흐름

1. 입력받은 작업들을 리스트에 저장한다.
2. **종료시간이 빠른 순서**로 정렬한다.
3. `last_end = 0` 으로 시작한다.
4. 정렬된 작업을 하나씩 보면서:
   - 작업 시작시간이 `last_end` 이상이면 선택
   - 선택했다면 `count += 1`
   - 그리고 `last_end = end` 로 갱신
5. 최종적으로 선택된 작업 개수를 출력한다.

### 의사코드

```text
작업 리스트를 종료시간 기준으로 정렬
count = 0
last_end = 0

for 작업 in 작업리스트:
    if 작업.start >= last_end:
        count += 1
        last_end = 작업.end
```

---

## 6. 검증

### 시간복잡도

- 작업 리스트 정렬: `O(N log N)`
- 정렬 후 한 번 순회: `O(N)`

따라서 전체 시간복잡도는 다음과 같다.

- **`O(N log N)`**

### 공간복잡도

- 작업 리스트 저장: `O(N)`

### 제한 조건에서 가능한 이유

작업 선택 문제를 모든 경우의 수로 보면 경우가 매우 많아진다.  
하지만 이 문제는 **종료시간 기준 그리디**가 성립하기 때문에,  
정렬 후 앞에서부터 한 번만 보면 충분하다.

### 반례 / 예외 상황 검토

- 모든 작업이 겹치지 않으면 → 전부 선택 가능
- 모든 작업이 서로 겹치면 → 가장 빨리 끝나는 작업 하나만 선택
- 이전 작업 종료시간과 다음 작업 시작시간이 같으면 → 선택 가능  
  (`start >= last_end` 여야 하는 이유)

---

## 7. 구현 포인트

### 중요한 변수 역할

- `work_list`  
  각 작업의 시작시간, 종료시간을 저장하는 리스트

- `count`  
  현재까지 선택한 작업 수

- `last_end`  
  마지막으로 선택한 작업의 종료시간

### 구현 시 주의점

- 반드시 **종료시간 기준 정렬**이어야 한다.
- 조건은 `start > last_end` 가 아니라 **`start >= last_end`** 여야 한다.
- `last_end`는 작업을 선택했을 때만 갱신해야 한다.

### 자주 실수하는 부분

- 시작시간 기준으로 정렬하는 실수
- 종료시간이 아니라 작업 길이로 판단하는 실수
- `last_end`를 잘못 갱신해서 겹치는 작업을 허용하는 실수

---

## 8. 코드

아래 코드는 **네 코드를 최대한 유지하면서**, 각 의미 단위마다 흐름이 보이도록 주석을 보강한 버전이다.

```python
T = int(input())

for tc in range(1, T + 1):
    N = int(input())

    # N개의 작업 정보를 입력받는다.
    # 각 작업은 [시작시간, 종료시간] 형태로 저장된다.
    work_list = [list(map(int, input().split())) for _ in range(N)]

    # 핵심 포인트:
    # 종료 시간이 빠른 작업이 앞에 오도록 정렬한다.
    # 그래야 뒤에 더 많은 작업을 붙일 수 있다.
    work_list.sort(key=lambda x: x[1])

    # 현재까지 선택한 작업 개수
    count = 0

    # 마지막으로 선택한 작업의 종료시간
    # 아직 아무 작업도 선택하지 않았으므로 0으로 시작
    last_end = 0

    # 종료 시간이 빠른 작업부터 하나씩 확인
    for start, end in work_list:
        # 현재 작업의 시작시간이
        # 마지막으로 고른 작업의 종료시간보다 같거나 늦으면
        # 서로 겹치지 않으므로 선택 가능
        if start >= last_end:
            count += 1

            # 이 작업을 선택했으므로
            # 다음 비교를 위해 마지막 종료시간 갱신
            last_end = end

    print(f'#{tc} {count}')
```

---

## 9. 코드 해설

전체 흐름은 매우 간단하다.

### 9-1. 입력과 정렬

먼저 모든 작업을 입력받고,  
`work_list.sort(key=lambda x: x[1])` 로 **종료시간 기준 정렬**을 한다.

이 한 줄이 사실상 이 문제의 핵심 아이디어다.

### 9-2. 선택 기준

그다음 작업을 앞에서부터 하나씩 보면서 다음 조건을 검사한다.

```python
if start >= last_end:
```

이 의미는 다음과 같다.

- 이전에 선택한 작업이 끝난 뒤에 시작할 수 있는 작업인가?
- 그렇다면 이 작업은 겹치지 않으므로 선택 가능하다.

### 9-3. 상태 갱신

작업을 선택했다면

```python
last_end = end
```

로 갱신해서, 다음 작업은 이 종료시간 이후의 것만 고를 수 있게 한다.

즉, 네 코드는  
**정렬 → 가능 여부 확인 → 상태 갱신** 구조가 아주 깔끔하게 연결되어 있다.

## 10. 코드 리뷰

### ✅ 잘한 점

- 문제 핵심인 **종료시간 기준 정렬**을 정확히 잡았다.
- 불필요한 자료구조 없이 구현이 간결하다.
- `count`, `last_end` 같은 변수가 직관적이다.
- 그리디 문제의 핵심 상태 관리가 깔끔하다.

### ⚠️ 아쉬운 점

- 종료시간이 같을 때 시작시간까지 같이 정렬하면 더 명시적일 수 있다.

```python
work_list.sort(key=lambda x: (x[1], x[0]))
```

- 코드만 보면 “왜 종료시간 기준이 항상 맞는가”는 드러나지 않으므로,  
  정리 노트에서는 이 reasoning을 함께 기억하는 게 중요하다.

### 💡 개선 아이디어

- 학습용 변수명으로 더 명확하게 바꿀 수 있다.
  - `count` → `selected_count`
  - `last_end` → `last_end_time`

### 🚨 디버깅 포인트

- `start >= last_end` 를 `>`로 잘못 쓰면 맞닿는 작업을 놓칠 수 있다.
- 시작시간 기준 정렬로 바꾸면 정답이 틀릴 수 있다.
- 작업 입력 순서를 반대로 해석하면 전체 로직이 무너진다.

## 11. 회고

이 문제에서 가장 중요한 건  
**그리디는 “아무 기준”이 아니라 “증명 가능한 기준”으로 골라야 한다**는 점이다.

이 문제에서는 그 기준이 바로 **종료시간**이다.  
앞으로 비슷한 문제를 만나면 먼저 이렇게 떠올리면 좋다.

- 많이 고르는 문제인가?
- 겹치지 않게 선택하는 문제인가?
- 그렇다면 종료시간 기준 그리디가 가능한가?

즉, 이 문제는 단순 구현보다  
**그리디 기준을 훈련하는 대표 문제**로 이해하면 좋다.
