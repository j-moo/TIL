# 데이터 엔지니어링 프로젝트 주제를 도출하고 검증하는 방법

- 🎯 글의 목표: 막연한 빅데이터 아이디어를 실제로 확보 가능한 데이터, 필요한 분산 처리, 사용자가 얻는 해결책이 연결된 프로젝트로 구체화한다.
- 🧩 핵심 키워드: 문제 정의, 데이터 가용성, 분석 단위, 파이프라인, 분산 처리, MVP, 의사결정, 검증
- ⭐ 중요도: ★★★★★ — 데이터와 사용자 행동이 연결되지 않으면 기술은 많아도 실행할 수 없는 프로젝트가 되기 쉽다.
- 📝 한눈에 보는 내용: 관심 분야에서 문제를 찾고, 데이터로 관찰 가능한 현상인지 확인한다. 그다음 탐지 결과를 사용자의 행동으로 연결하고, 작은 MVP로 데이터·분석·서비스 가정을 차례로 검증한다.
- 🔗 관련 주제: HDFS, Spark, Kafka, 데이터 모델링, 통계, 머신러닝, 서비스 기획
- 🧱 선수 지식: 테이블의 행과 열, 파일·API, 배치 처리와 실시간 처리의 차이

---

## 1. 들어가며

“빅데이터와 분산 처리를 사용하는 새로운 서비스”라는 목표만으로는 주제가 잘 떠오르지 않는다. Hadoop이나 Spark는 문제를 해결하는 도구이지 문제 자체가 아니기 때문이다.

좋은 데이터 프로젝트는 기술 이름보다 다음 질문에서 시작한다.

> 어떤 사용자가 어떤 판단을 내리기 어려워하며, 어떤 데이터를 처리하면 그 판단을 더 잘할 수 있는가?

아이디어가 흥미로워도 필요한 원자료를 구할 수 없거나, 공개 데이터의 집계 수준이 분석 목표와 맞지 않으면 구현할 수 없다. 반대로 공개 데이터만 나열하고 사용자에게 보여 줄 행동이 없다면 분석 보고서에서 끝나기 쉽다.

이 문서에서는 문제·데이터·분산 처리·서비스 가치를 한 흐름으로 연결하는 방법을 다룬다.

## 2. 핵심 개념 정리

```text
사용자의 불편 또는 의사결정
              ↓
데이터로 관찰 가능한 현상 정의
              ↓
실제로 확보 가능한 데이터 검증
              ↓
분산 처리가 필요한 계산 설계
              ↓
분석 결과를 행동 가능한 정보로 변환
              ↓
작은 범위의 MVP로 가정 검증
```

프로젝트 주제는 다음 식으로 점검할 수 있다.

```text
프로젝트 가치
= 명확한 사용자
 + 반복되는 문제
 + 확보 가능한 데이터
 + 설명 가능한 분석
 + 결과를 받은 뒤의 행동
```

어느 한 항목이 비어 있다면 기술 스택을 정하기 전에 주제를 다시 다듬는 편이 좋다.

## 3. 본문 정리

### 3.1 기술보다 문제와 사용자를 먼저 정한다

“Spark를 쓰고 싶다”에서 시작하면 Spark가 필요 없는 데이터에도 분산 기술을 억지로 넣기 쉽다. 먼저 사용자와 상황을 한 문장으로 적는다.

```text
[사용자]는 [상황]에서 [판단]을 하기 어렵다.
왜냐하면 [현재 정보의 한계]가 있기 때문이다.
```

예를 들어 대중교통 분야라면 다음처럼 문제를 구체화할 수 있다.

```text
정해진 시간에 도착해야 하는 이용자는
여러 경로 중 실제 이동 변동이 적은 경로를 고르기 어렵다.
기존 안내는 평균 예상 시간만으로 개인이 감수할 실패 위험을 충분히 설명하지 못하기 때문이다.
```

여기까지는 아직 해결책이 아니다. 다음 단계에서 이 문제를 어떤 데이터로 관찰할지 연결한다.

### 3.2 불편을 측정 가능한 지표로 바꾼다

“환승이 불편하다”, “기계 상태가 나쁘다”, “지역이 위험하다”는 그대로 계산할 수 없다. 모호한 표현을 관찰 가능한 변수로 바꿔야 한다.

| 모호한 표현 | 측정 가능한 후보 |
| --- | --- |
| 혼잡하다 | 시간대별 승하차 인원, 차량 혼잡도, 대기 인원 |
| 이동이 불안정하다 | 이동시간 분산, P90·P95, 지연 빈도 |
| 환승이 어렵다 | 환승 거리, 배차 간격, 예상 여유시간 |
| 설비가 위험하다 | 진동 편차, 온도 상승률, 경고 발생 횟수 |
| 영향이 크다 | 영향을 받는 사용자 수, 지연 시간, 비용 |

평균만 보면 드물지만 큰 실패가 감춰질 수 있다. 중앙값과 상위 백분위수, 변동성을 함께 보면 “평소에는 괜찮지만 가끔 크게 늦는 상황”을 구분할 수 있다.

📌 핵심: 지표는 계산 가능할 뿐 아니라 사용자의 실제 문제와 연결되어야 한다. 숫자를 만들 수 있다는 이유만으로 지표를 추가하면 결과를 해석하기 어려워진다.

### 3.3 데이터 존재와 분석 가능성은 다른 문제다

데이터 포털에 파일이 있다는 사실만으로 원하는 분석을 할 수 있는 것은 아니다. 다음 여섯 가지를 실제 파일과 명세서에서 확인해야 한다.

1. **접근 가능성**: 회원가입, 신청, 승인 또는 반출 심사가 필요한가?
2. **분석 단위**: 개인·거래·역·시간대 중 어느 단위인가?
3. **시간 범위**: 며칠치인지, 과거 파일도 받을 수 있는가?
4. **연결 키**: 다른 데이터와 결합할 식별자가 있는가?
5. **갱신 주기**: 실시간, 일간, 월간 중 무엇인가?
6. **이용 조건**: 재배포, 상업 이용, 개인정보 관련 제한이 있는가?

서울 열린데이터광장의 교통카드 이용정보는 지하철역과 버스정류장 단위의 승하차 인원을 OpenAPI와 파일 형태로 제공한다. 이런 집계 데이터는 시간대별 수요나 혼잡 후보를 분석하기에 적합하다. 그러나 개별 카드의 연속 이동을 복원하거나 개인별 환승 성공 여부를 계산하려면 더 세밀한 이동 기록이 필요하다.

```text
공개 집계 데이터로 가능한 것
├─ 역·정류장별 승하차 수요 비교
├─ 시간대별 혼잡 후보 탐색
└─ 지역·노선별 장기 추세 분석

개별 이동 기록이 있어야 가능한 것
├─ 한 사용자의 Trip Chain 복원
├─ 실제 개인별 환승 소요시간 계산
└─ 환승 성공·실패 label 생성
```

따라서 공개 집계 데이터로 개인 단위 결과를 직접 만들 수 있다고 가정하면 안 된다. 세부 원자료 접근이 불확실하다면 집계 데이터로 가능한 MVP를 먼저 설계하고, 개인화 기능은 데이터 확보 이후 확장 항목으로 둔다.

### 3.4 데이터 샘플을 먼저 내려받아 확인한다

프로젝트 제안서를 길게 쓰기 전에 샘플 파일 하나를 직접 열어 본다.

```text
데이터 페이지 확인
      ↓
명세서와 이용 조건 읽기
      ↓
샘플 파일 다운로드
      ↓
열 이름·자료형·결측치·중복 확인
      ↓
원하는 지표를 작은 코드로 계산
      ↓
가능하면 전체 규모 추정
```

Python과 Pandas로 첫 점검을 할 때는 다음 정도부터 시작할 수 있다.

```python
import pandas as pd


# 처음에는 일부 행만 읽어 열 이름과 값의 모양을 확인한다.
sample = pd.read_csv("transport_sample.csv", nrows=1_000)

print(sample.head())
print(sample.info())

# 열마다 결측값이 몇 개인지 확인한다.
print(sample.isna().sum())

# 같은 레코드가 반복되는지 확인한다.
print("중복 행:", sample.duplicated().sum())
```

이 코드는 전체 분석이 아니라 데이터 계약을 확인하는 탐색이다. 실제 열 이름, 인코딩, 구분자, 자료형은 제공 기관의 명세서와 샘플에 맞춰 조정해야 한다.

### 3.5 탐지 결과를 사용자 행동으로 연결한다

“취약 지역을 찾았다”는 분석 결과다. 서비스가 되려면 사용자가 결과를 보고 무엇을 할 수 있는지까지 설계해야 한다.

분석의 발전 단계를 다음처럼 생각할 수 있다.

```text
무슨 일이 있었는가?       → 설명
왜 그런 일이 생겼는가?    → 원인 분석
앞으로 어떻게 될 것인가?  → 예측
무엇을 선택해야 하는가?   → 추천
선택을 바꾸면 어떻게 되는가? → 시뮬레이션
```

모든 프로젝트가 다섯 단계를 전부 구현할 필요는 없다. 그러나 탐지에서 끝내지 않고 최소한 다음 행동 한 가지는 제공해야 한다.

| 분석 결과 | 행동 가능한 정보 |
| --- | --- |
| 특정 시간대 혼잡도가 높음 | 덜 혼잡한 출발 시간 또는 경로 비교 |
| 이동시간 변동성이 큼 | 정시 도착 확률과 권장 출발 시각 |
| 설비 이상 징후 증가 | 점검 우선순위와 확인할 부품 |
| 공정 한 지점의 장애 위험 | 후속 공정 영향과 대체 운영안 |

사용자용 해결책과 운영자용 해결책을 혼합하지 않는 것도 중요하다. 이용자는 더 나은 선택을 원하고, 운영자는 시설이나 정책 개선 우선순위를 원한다. 같은 분석 엔진을 공유할 수 있지만 화면과 의사결정은 다르다.

### 3.6 분산 처리가 정말 필요한 이유를 증명한다

파일이 크다는 말만으로 분산 처리가 필요한 것은 아니다. 단일 컴퓨터에서 처리 가능한 데이터라면 Pandas나 관계형 데이터베이스가 더 단순하고 저렴할 수 있다.

분산 처리 필요성은 다음 기준에서 찾는다.

- **Volume**: 한 컴퓨터의 메모리나 저장 공간을 넘는 데이터 규모
- **Velocity**: 지속적으로 들어와 제한 시간 안에 처리해야 하는 속도
- **반복 계산**: 대규모 정렬, 조인, 윈도우 계산, 그래프 탐색
- **확장성**: 데이터가 늘어날 때 여러 작업자로 수평 확장해야 함
- **장애 대응**: 일부 작업자가 실패해도 작업을 재시도해야 함

예를 들어 수년치 교통 기록을 사용자 또는 카드 기준으로 나누고 시간순으로 정렬한 뒤, 노선·정류장·날씨 데이터를 반복 조인한다면 분산 처리의 이유가 생긴다.

```text
원시 이동 기록
      ↓
HDFS 또는 객체 저장소에 분산 저장
      ↓
Spark에서 식별자 기준 partition
      ↓
시간순 정렬과 window 계산
      ↓
노선·시간·공간 데이터 join
      ↓
역·시간대별 분포와 위험 지표 집계
```

하지만 발표에서 “Spark를 사용했다”만 말하면 근거가 약하다. 같은 계산을 작은 단일 노드와 분산 환경에서 실행해 데이터 크기별 실행 시간, shuffle 양, partition 수를 비교해야 한다.

### 3.7 배치 처리와 실시간 처리를 구분한다

과거 수년치 데이터를 분석하는 작업과 현재 위치를 반영하는 작업은 시간 요구사항이 다르다.

| 구분 | 배치 처리 | 스트리밍·준실시간 처리 |
| --- | --- | --- |
| 입력 | 일정 기간 모은 파일 | 계속 들어오는 이벤트 |
| 목적 | 기준선, 통계, 모델 학습 | 현재 상태 갱신, 빠른 경고 |
| 예시 | 월별 혼잡 패턴 | 현재 지연 반영 |
| 후보 도구 | Spark batch, SQL | Kafka, Spark Structured Streaming, Flink |

처음부터 실시간 구조를 모두 만들면 범위가 커진다. MVP에서는 과거 데이터로 기준선을 만들고, 실시간 데이터는 한두 개 API와 제한된 지역에만 결합하는 편이 검증하기 쉽다.

### 3.8 MVP는 가장 작은 기능이 아니라 가장 중요한 가정을 검증한다

MVP(Minimum Viable Product)는 기능이 적기만 한 제품이 아니다. 실패 위험이 큰 가정을 가장 적은 비용으로 확인하는 결과물이다.

데이터 프로젝트의 가정은 보통 세 층으로 나뉜다.

```text
데이터 가정: 필요한 데이터가 실제로 있고 품질이 충분한가?
분석 가정: 계산한 지표가 문제를 설명하거나 예측하는가?
서비스 가정: 사용자가 그 결과를 이해하고 행동을 바꾸는가?
```

대중교통 프로젝트의 초기 범위는 다음처럼 줄일 수 있다.

- 도시 전체가 아니라 환승 수요가 많은 몇 개 지점
- 하루 전체가 아니라 출퇴근 시간대
- 완전한 개인 예측이 아니라 경로별 변동성 비교
- 모든 실시간 데이터를 결합하지 않고 한 종류의 도착 정보만 연결
- 고급 AI보다 통계 기준선과 규칙 기반 추천부터 검증

이 범위에서 가치가 확인된 뒤 지역, 데이터 기간, 사용자 유형, 모델 복잡도를 늘린다.

### 3.9 아이디어 평가표를 사용한다

후보가 여러 개라면 느낌보다 공통 기준으로 비교한다. 각 항목을 1~5점으로 평가할 수 있다.

| 평가 항목 | 확인 질문 |
| --- | --- |
| 문제 명확성 | 사용자의 불편을 한 문장으로 설명할 수 있는가? |
| 데이터 가용성 | 지금 샘플을 받을 수 있는가? |
| 데이터 적합성 | 원하는 분석 단위와 열이 존재하는가? |
| 분산 처리 근거 | 규모·속도·계산 복잡성을 측정할 수 있는가? |
| 해결책 가치 | 사용자가 결과를 보고 행동을 바꿀 수 있는가? |
| MVP 가능성 | 제한된 기간 안에 핵심 가정을 검증할 수 있는가? |
| 차별성 | 기존 서비스와 다른 판단 기준이 분명한가? |

점수는 정답이 아니라 팀의 숨은 가정을 드러내는 도구다. 데이터 가용성이 낮은 주제는 아이디어가 매력적이어도 우선순위를 낮추는 근거가 된다.

## 4. 적용 관점에서 다시 보기

새로운 데이터 프로젝트를 시작할 때는 다음 산출물을 순서대로 만든다.

1. 사용자·상황·어려운 판단을 적은 문제 정의 한 문장
2. 목표 지표와 필요한 데이터 열 목록
3. 실제 데이터 페이지, 명세서, 샘플 파일
4. 작은 샘플에서 지표 하나를 계산한 탐색 코드
5. 단일 처리와 분산 처리의 범위 구분
6. 분석 결과를 받은 사용자의 다음 행동
7. 2~4주 안에 검증할 MVP 범위

아이디어가 막히면 산업 분야를 무작정 늘리지 말고 하나의 공개 데이터셋을 먼저 살펴본다. 데이터의 시간·공간·개체 축을 확인한 뒤 “누가 이 변화를 미리 알면 더 나은 결정을 할 수 있는가?”를 질문하면 문제 후보를 만들기 쉽다.

## 5. 배운 점 / 확장 포인트

### 5.1 새로 이해한 것

- 빅데이터 기술은 프로젝트 주제가 아니라 문제를 처리하는 수단이다.
- 데이터가 공개되어 있어도 분석에 필요한 세부 단위가 없을 수 있다.
- 탐지 결과를 사용자의 선택과 연결해야 서비스 가치가 생긴다.
- 분산 처리 필요성은 데이터 규모와 계산 특성을 측정해 증명해야 한다.
- MVP는 데이터·분석·서비스 가정 중 가장 위험한 부분을 먼저 검증한다.

### 5.2 이전·다음 학습과의 연결

HDFS와 MapReduce의 기본 원리를 실제 프로젝트 파이프라인에 연결했다. 다음에는 Spark DataFrame, partition, shuffle, window function, 분산 join과 성능 측정을 학습한다.

### 5.3 더 확인할 주제

- 데이터 품질 프로파일링
- 데이터 계보(lineage)와 재현 가능한 파이프라인
- 시계열의 데이터 누수와 학습·검증 분리
- 사용자 추천 결과의 설명 가능성과 공정성
- 개인정보 비식별화와 결합 위험

## 6. 요약 정리

- 데이터 프로젝트는 기술보다 사용자의 어려운 판단에서 시작한다.
- 모호한 불편을 계산 가능한 지표로 바꾼다.
- 데이터 페이지뿐 아니라 명세서와 실제 샘플을 확인한다.
- 공개 집계 데이터와 개인 단위 원자료로 가능한 분석은 다르다.
- 탐지 결과는 추천·우선순위·대안 비교 같은 행동으로 연결한다.
- 사용자용 해결책과 운영자용 해결책의 책임을 구분한다.
- 분산 처리는 규모·속도·조인·정렬·장애 대응 필요성으로 설명한다.
- MVP는 가장 중요한 가정을 작은 범위에서 검증한다.

🧠 기억할 것: **좋은 빅데이터 주제는 데이터가 많아 보이는 주제가 아니라, 확보 가능한 데이터로 사용자의 중요한 결정을 실제로 개선할 수 있는 주제다.**

## 7. 미니 퀴즈 또는 체크리스트

1. 공개 데이터가 존재해도 프로젝트를 바로 구현할 수 없는 이유는 무엇인가?
2. 집계 승하차 데이터와 개인 이동 기록으로 가능한 분석은 어떻게 다른가?
3. 취약 지역 탐지를 서비스 기능으로 발전시키려면 무엇을 더 설계해야 하는가?
4. Spark가 필요한 이유를 어떤 지표로 증명할 수 있는가?
5. 배치 기준선과 실시간 상태를 분리하면 어떤 장점이 있는가?
6. MVP에서 가장 먼저 검증해야 할 세 가지 가정은 무엇인가?

<details>
<summary>정답과 해설</summary>

1. 분석 단위, 열, 기간, 연결 키와 이용 조건이 목표에 맞는지 별도로 확인해야 하기 때문이다.
2. 집계 데이터는 시간대·지점별 수요 분석에 적합하고, 개인 이동 기록은 Trip Chain이나 개인별 환승 시간 계산에 필요하다.
3. 분석 결과를 받은 사용자가 선택할 대안, 추천 기준과 다음 행동을 설계해야 한다.
4. 데이터 크기별 실행 시간, 메모리 한계, shuffle 양, partition 수, 처리 지연 등을 비교할 수 있다.
5. 과거의 안정적인 통계 계산과 현재 상태 갱신의 시간 요구사항을 각각 단순한 구조로 설계할 수 있다.
6. 데이터 확보 가능성, 분석 지표의 유효성, 사용자가 결과를 이해하고 행동하는지를 검증한다.
