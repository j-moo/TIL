## 1. 들어가며

작은 텍스트 파일은 한 컴퓨터에서 읽고 반복문으로 처리할 수 있다. 하지만 파일이 수십 TB이고 매일 새로운 센서 데이터가 들어온다면 한 컴퓨터의 디스크 용량, 처리 시간, 장애 위험이 문제가 된다.

이때 질문은 “더 빠른 반복문을 어떻게 작성할까?”에서 다음과 같이 바뀐다.

```text
큰 파일을 여러 컴퓨터에 어떻게 나누어 저장할까?
여러 컴퓨터가 각자 맡은 부분을 어떻게 동시에 계산할까?
중간에 컴퓨터 한 대가 고장 나도 작업을 어떻게 이어갈까?
나뉜 결과를 마지막에 어떻게 합칠까?
```

Hadoop 생태계에서 HDFS는 주로 저장을, MapReduce는 배치 계산을 담당한다.

## 2. 핵심 개념 정리

전체 흐름을 먼저 보면 각 용어의 위치가 보인다.

```text
아주 큰 입력 파일
      ↓
HDFS가 여러 블록으로 분할·복제 저장
      ↓
Map: 각 입력 조각을 독립적으로 변환
      ↓
Shuffle / Sort: 같은 Key끼리 모음
      ↓
Reduce: Key별 값을 집계
      ↓
HDFS에 결과 파일 저장
```

여기서 중요한 구분은 다음과 같다.

- HDFS 블록은 큰 파일을 저장하기 위한 물리적 분할 단위다.
- MapReduce 레코드는 계산 함수가 읽고 내보내는 논리적 Key-Value 단위다.
- 블록, 줄, 레코드, Key-Value는 항상 같은 단위가 아니다.

## 3. 본문 정리

### 3.1 병렬 처리와 분산 처리

병렬 처리는 여러 계산을 동시에 수행하는 방식이다. 분산 처리는 여러 독립된 컴퓨터가 네트워크로 협력해 저장과 계산을 나누는 방식이다.

```text
병렬 처리
한 컴퓨터 안의 여러 CPU 코어가 일을 나눌 수 있다.

분산 처리
컴퓨터 A, B, C가 네트워크를 통해 일을 나눈다.
```

두 개념은 함께 사용될 수 있다. 분산된 각 컴퓨터가 자기 내부의 여러 코어로 병렬 계산할 수도 있다.

| 구분 | 병렬 처리 | 분산 처리 |
| --- | --- | --- |
| 주요 목적 | 동시에 계산해 시간 단축 | 데이터와 계산을 여러 장비로 확장 |
| 통신 | 주로 같은 장비 내부 | 네트워크 통신 필요 |
| 장애 | 한 장비 장애가 전체에 영향 | 일부 장비 장애를 고려한 설계 필요 |
| 어려움 | 동시성, 작업 분할 | 네트워크, 데이터 위치, 장애, 결과 일관성 |

### 3.2 Hadoop과 HDFS

Hadoop은 대규모 데이터를 분산 저장·처리하기 위한 오픈 소스 생태계다. HDFS(Hadoop Distributed File System)는 Hadoop의 분산 파일 시스템이다.

HDFS는 매우 큰 파일을 여러 블록으로 나누어 여러 DataNode에 저장한다. 사용자는 하나의 파일처럼 다루지만 내부적으로는 여러 컴퓨터의 디스크에 나뉠 수 있다.

```text
sensor.log
  ├─ Block A → DataNode 1, DataNode 3, DataNode 5
  ├─ Block B → DataNode 2, DataNode 4, DataNode 5
  └─ Block C → DataNode 1, DataNode 2, DataNode 4
```

블록을 여러 노드에 저장하는 이유는 저장 용량 확장뿐 아니라 장애 복구 때문이다.

### 3.3 NameNode와 DataNode의 책임

HDFS를 처음 볼 때는 파일 데이터와 파일 위치 정보가 어디에 있는지 구분해야 한다.

| 구성 요소 | 주요 책임 |
| --- | --- |
| NameNode | 파일 이름, 디렉터리, 블록 목록, 블록 위치 같은 메타데이터 관리 |
| DataNode | 실제 블록 데이터 저장, 읽기·쓰기 수행, 상태 보고 |

비유하면 NameNode는 도서관의 목록 시스템이고 DataNode는 실제 책이 놓인 서가에 가깝다. 단, 실제 HDFS의 장애 대응과 고가용성 구조는 이 비유보다 복잡하다.

```text
클라이언트: sensor.log를 읽고 싶다.
      ↓
NameNode: 필요한 블록은 A, B, C이며 위치는 다음과 같다.
      ↓
클라이언트: 해당 DataNode에서 실제 블록을 읽는다.
```

### 3.4 파일을 순차적인 블록으로 나눈다는 의미

파일을 블록으로 나눈다는 것은 파일의 바이트 범위를 앞에서부터 일정 크기 단위로 구분한다는 뜻이다.

```text
원본 파일 바이트 범위
0 ---------------------------------------------------- 끝

Block 0       Block 1       Block 2       마지막 Block
[앞부분]      [다음 부분]    [다음 부분]    [남은 부분]
```

파일 블록은 서로 다른 노드에 저장되어도 논리적 순서를 가진다. 파일을 읽을 때 시스템은 블록 순서에 맞게 데이터를 제공한다.

⚠️ 주의: “블록 하나가 항상 텍스트 한 줄과 정확히 맞는다”고 생각하면 안 된다. 입력 포맷이 블록 경계와 레코드 경계를 조정해 Map 함수에 올바른 레코드를 전달한다.

### 3.5 복제와 Fault Tolerance

Fault Tolerance는 일부 구성 요소에 장애가 생겨도 시스템 전체가 즉시 사용할 수 없게 되지 않고 정상 또는 제한된 기능을 이어가는 성질이다.

HDFS는 블록을 여러 DataNode에 복제해 둘 수 있다.

```text
Block A의 복제본
  ├─ DataNode 1
  ├─ DataNode 3
  └─ DataNode 5
```

DataNode 3이 고장 나도 다른 복제본에서 Block A를 읽을 수 있다. HDFS는 노드의 상태를 관찰하고 필요한 경우 부족해진 복제본을 다시 만들도록 조정한다.

복제가 해결하는 것과 해결하지 않는 것을 구분해야 한다.

- 해결에 도움: 디스크·노드 장애로 특정 블록을 읽을 수 없는 위험
- 대가: 저장 공간 증가와 복제 네트워크 비용
- 자동 해결 아님: 사용자가 잘못 삭제한 데이터, 잘못된 데이터 입력, 애플리케이션 논리 오류

### 3.6 MapReduce의 Key-Value 사고방식

MapReduce에서는 입력과 중간 결과를 `(Key, Value)` 쌍으로 표현한다.

예를 들어 단어 수를 세는 작업은 다음처럼 볼 수 있다.

```text
입력 줄: "jelly meet jelly"
        ↓ Map
(jelly, 1)
(meet, 1)
(jelly, 1)
        ↓ Shuffle
(jelly, [1, 1])
(meet, [1])
        ↓ Reduce
(jelly, 2)
(meet, 1)
```

Map과 Reduce가 반드시 입력 하나당 출력 하나만 만드는 것은 아니다.

- 출력하지 않을 수 있다: 필터링된 레코드
- 하나를 출력할 수 있다: 단순 변환
- 여러 개를 출력할 수 있다: 한 문장을 여러 단어 쌍으로 분리

### 3.7 텍스트 입력의 Offset Key

텍스트 파일을 줄 단위로 읽는 입력 형식에서는 Map 함수의 입력 Key로 줄이 시작하는 바이트 위치(offset), Value로 줄 전체가 전달되는 형태를 볼 수 있다.

```text
파일 내용
0:  apple banana
14: banana grape
27: apple
```

개념적인 Map 입력은 다음과 같다.

```text
(0,  "apple banana")
(14, "banana grape")
(27, "apple")
```

여기서 0, 14, 27은 줄 번호가 아니라 파일 앞부분에서 해당 줄 시작점까지의 바이트 위치를 나타내는 offset이다. 실제 값은 인코딩과 줄바꿈 바이트에 영향을 받으므로 위 숫자는 이해를 위한 예시다.

단어 수 세기에서는 이 offset을 사용하지 않을 수 있다. Key가 입력으로 전달된다고 해서 모든 작업에서 반드시 활용해야 하는 것은 아니다.

### 3.8 Map 단계

Map은 입력 레코드 하나를 받아 0개 이상의 중간 Key-Value 쌍을 만든다.

개념을 보여주기 위한 Python 형태의 의사 코드다. Hadoop Streaming이나 실제 프레임워크 API와 완전히 같은 코드는 아니다.

```python
def map_line(offset: int, line: str) -> list[tuple[str, int]]:
    """한 줄을 단어별 (단어, 1) 쌍으로 바꾼다."""
    outputs: list[tuple[str, int]] = []

    for word in line.split():
        # 같은 단어가 여러 번 나타나면 그만큼 여러 쌍을 만든다.
        outputs.append((word, 1))

    return outputs
```

Map 단계는 다른 줄의 전체 결과를 몰라도 현재 줄을 처리할 수 있어 작업을 여러 머신에 나누기 쉽다.

### 3.9 Shuffle과 Sort 단계

각 Mapper가 만든 결과는 여러 컴퓨터에 흩어져 있다. Reduce가 단어별 합계를 계산하려면 같은 Key의 값이 같은 Reducer 쪽으로 모여야 한다.

```text
Mapper A: (jelly, 1), (meet, 1)
Mapper B: (jelly, 1), (fan, 1)
Mapper C: (meet, 1), (jelly, 1)

             ↓ Shuffle / Sort

jelly → [1, 1, 1]
meet  → [1, 1]
fan   → [1]
```

Shuffle은 노드 사이에서 많은 데이터를 옮길 수 있으므로 네트워크 비용이 크다. Map 출력의 크기를 줄이는 최적화가 중요한 이유다.

### 3.10 Reduce 단계

Reduce는 하나의 Key와 그 Key에 모인 값들을 받아 최종 결과를 만든다.

```python
def reduce_word(word: str, counts: list[int]) -> tuple[str, int]:
    """한 단어에 모인 부분 개수를 최종 합계로 만든다."""
    return word, sum(counts)
```

실제 프레임워크에서는 값이 리스트 객체로 한 번에 메모리에 만들어지기보다 반복 가능한 값 흐름으로 전달될 수 있다. 개념상 “같은 Key에 속한 값들의 모음”으로 이해하면 된다.

### 3.11 Combiner가 Shuffle 비용을 줄이는 원리

Combiner는 각 Mapper의 출력 중 같은 Key를 로컬에서 먼저 합칠 수 있을 때 사용하는 선택적 단계다.

```text
Combiner 없음
Mapper A → (jelly,1), (jelly,1), (jelly,1), (meet,1)
           네트워크로 4개 전송

Combiner 사용
Mapper A → (jelly,3), (meet,1)
           네트워크로 2개 전송
```

최종 Reduce를 없애는 것이 아니라, Shuffle 전에 중간 데이터의 크기를 줄이는 것이다.

모든 Reduce 로직을 Combiner로 사용할 수 있는 것은 아니다. 다음 조건을 고려한다.

- 입력 순서와 그룹 분할 방식에 관계없이 안전한가?
- 부분 결과를 다시 같은 방식으로 합쳐도 최종 결과가 같은가?
- Combiner가 실행되지 않거나 여러 번 실행되어도 정답이 같은가?

합계와 개수는 적용하기 쉽다. 단순 평균은 주의해야 한다.

```text
그룹 A 평균 = 10, 데이터 수 = 2
그룹 B 평균 = 20, 데이터 수 = 8

(10 + 20) / 2 = 15  ← 전체 평균이 아님

합계와 개수를 함께 전달해야 함
(20 + 160) / (2 + 8) = 18
```

📌 핵심: Combiner는 실행이 보장된 최종 집계 단계가 아니라, 실행되어도 정답이 변하지 않는 로컬 최적화 단계다.

### 3.12 메인 프로그램, Mapper, Reducer의 관계

사용자가 작성하는 드라이버 또는 메인 프로그램은 작업 전체를 설정한다.

```text
드라이버 프로그램
  ├─ 입력 경로 지정
  ├─ 출력 경로 지정
  ├─ Mapper / Reducer 클래스 지정
  ├─ Key와 Value 타입 설정
  └─ Job 실행 요청 및 결과 확인
```

전처리와 후처리가 필요하다면 드라이버에서 작업 전후 흐름을 조정할 수 있지만, 대규모 데이터를 메인 프로그램 한 곳에서 직접 모두 읽어 처리하면 분산 처리의 장점을 잃는다.

### 3.13 출력은 어디에 저장되는가

Mapper의 중간 출력은 Shuffle을 위한 로컬 디스크·네트워크 처리에 사용될 수 있고, 일반적인 MapReduce 작업의 최종 출력은 HDFS의 파일 형태로 저장된다. “Map의 모든 중간 결과가 곧바로 영구 HDFS 파일이 된다”고 단순화하면 실제 실행 구조를 오해할 수 있다.

최종 출력은 Reducer 수에 따라 여러 part 파일로 나뉠 수 있다.

```text
output/
  ├─ part-r-00000
  ├─ part-r-00001
  └─ _SUCCESS
```

### 설비 건강도 분석 예시

공장 설비의 진동, 온도, 전류, RPM 데이터를 주기적으로 수집한다고 가정한다.

```text
센서 이벤트 대량 수집
        ↓
HDFS에 날짜·설비 단위로 저장
        ↓
Map: 레코드 정제, 설비 ID와 날짜를 Key로 생성
        ↓
Shuffle: 같은 설비·기간 데이터 모음
        ↓
Reduce: 평균·최댓값·이상 횟수·추세 계산
        ↓
설비별 건강도 모델의 입력 특성 생성
```

예시 결과는 다음처럼 구성할 수 있다.

```text
설비 #32
- 최근 진동 평균과 기준 대비 변화
- 모터 온도 상승 폭
- 과부하 발생 횟수
- 최근 정비 이후 사용 시간
- 건강 점수와 점검 권장 시점
```

MapReduce만으로 실시간 예측 서비스 전체가 완성되는 것은 아니다. 데이터 수집, 배치 저장, 특성 생성, 모델 학습·서빙, 모니터링과 사용자 화면이 추가로 필요하다.

### 데이터가 실제로 수집 가능한지 먼저 검증하기

서비스 기획 단계에서는 모델보다 데이터 확보 가능성을 먼저 확인한다.

1. 센서 원천 데이터가 존재하는가?
2. 고장·정비 이력과 시간 기준으로 연결할 수 있는가?
3. 정상 데이터와 고장 데이터의 비율은 어떠한가?
4. 설비·공정의 기밀 데이터를 사용할 권한이 있는가?
5. 공개 데이터로 PoC를 만들 수 있는가?
6. 건강 점수의 정답과 검증 기준을 어떻게 정의할 것인가?

### MapReduce가 항상 최선은 아니다

MapReduce는 대규모 배치 처리의 기본 원리를 배우기에 좋다. 반복적인 메모리 연산, 대화형 분석, 낮은 지연 시간이 중요한 작업에서는 Spark나 스트리밍 시스템 등 다른 도구가 더 적합할 수 있다. 도구보다 먼저 데이터 크기, 처리 지연, 장애 요구사항을 정의한다.

## 5. 배운 점 / 확장 포인트

### 5.1 새로 이해한 것

- 분산 처리는 단순히 반복문을 여러 번 실행하는 것이 아니라 저장·통신·장애 복구까지 포함한다.
- HDFS는 파일을 블록으로 나누고 복제해 일부 노드 장애에 대비한다.
- 텍스트 입력의 offset은 줄 번호가 아니라 파일 내 바이트 위치다.
- Map은 0개 이상의 쌍을 만들 수 있고, Shuffle이 같은 Key를 모은다.
- Combiner는 정답을 만드는 필수 단계가 아니라 네트워크 비용을 줄이는 선택적 최적화다.

### 5.2 이전·다음 학습과의 연결

이 내용은 Spark의 RDD/DataFrame 분산 처리, Kafka의 파티션, 데이터 레이크, 배치·스트리밍 파이프라인으로 이어진다. 알고리즘의 분할 정복과 비슷해 보이지만, 분산 시스템에는 네트워크와 부분 장애라는 추가 문제가 있다.

### 5.3 더 확인할 주제

- HDFS의 rack awareness와 고가용성 NameNode
- MapReduce partitioner와 Reducer 수
- 데이터 지역성(data locality)
- Spark가 MapReduce 반복 작업을 개선하는 방식
- 센서 시계열 데이터의 이상 탐지와 라벨 품질

## 6. 요약 정리

1. 병렬 처리는 동시 계산, 분산 처리는 여러 컴퓨터의 협력에 초점이 있다.
2. HDFS는 큰 파일을 블록으로 나누어 DataNode에 저장한다.
3. 블록 복제는 일부 노드 장애에도 데이터를 읽도록 돕는다.
4. NameNode는 메타데이터, DataNode는 실제 블록을 관리한다.
5. MapReduce는 데이터를 Key-Value 쌍으로 변환하고 집계한다.
6. 텍스트 입력의 offset Key는 줄 시작 바이트 위치를 뜻할 수 있다.
7. Shuffle은 같은 Key의 값을 같은 Reduce 그룹으로 모은다.
8. Combiner는 안전한 연산에서 Map 출력을 미리 줄여 네트워크 비용을 낮춘다.
9. 최종 결과는 여러 HDFS part 파일로 저장될 수 있다.

🧠 기억할 것: HDFS가 데이터를 안전하게 나누어 저장한다면, MapReduce는 계산을 나누고 같은 Key의 결과를 다시 모은다.

## 7. 미니 퀴즈 또는 체크리스트

1. HDFS 블록과 MapReduce 입력 레코드는 왜 같은 개념이 아닌가?
2. DataNode 한 대가 고장 나도 블록을 읽을 수 있는 이유는 무엇인가?
3. 텍스트 입력의 offset Key는 무엇을 나타내는가?
4. Shuffle 단계에서 네트워크 비용이 커지는 이유는 무엇인가?
5. 단순 평균을 Combiner로 바로 계산하면 왜 틀릴 수 있는가?
6. Combiner가 실행되지 않아도 최종 정답이 같아야 하는 이유는 무엇인가?

<details>
<summary>정답과 해설</summary>

1. 블록은 저장 단위이고 레코드는 계산 함수가 읽는 논리 단위이기 때문이다.
2. 같은 블록의 복제본을 다른 DataNode에 저장할 수 있기 때문이다.
3. 일반적인 텍스트 입력 형식에서는 해당 줄이 파일에서 시작하는 바이트 위치를 뜻한다.
4. 여러 Mapper에 흩어진 같은 Key의 값을 Reducer 쪽으로 이동해야 하기 때문이다.
5. 크기가 다른 부분 집합의 평균을 다시 단순 평균하면 각 데이터 개수의 가중치가 사라진다.
6. Combiner는 선택적으로 0회 또는 여러 번 실행될 수 있는 최적화 단계이기 때문이다.

</details>
