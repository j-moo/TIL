## 2. 핵심 개념 정리

사용자와 게시글의 관계도 N:1이다. 한 사용자는 여러 게시글을 작성할 수 있지만, 게시글 하나의 작성자는 보통 한 명이다. 사용자와 댓글 관계도 마찬가지다.

Django에서는 게시글 모델이나 댓글 모델에 `ForeignKey`로 사용자 모델을 연결한다. 이때 직접 `User` 클래스를 import하기보다 `settings.AUTH_USER_MODEL`을 사용하는 방식이 권장된다.

관계가 생기면 단순 CRUD 로직도 바뀐다. 게시글을 저장할 때 작성자를 함께 넣어야 하고, 수정/삭제할 때는 요청한 사용자가 작성자인지 확인해야 한다.

## 3. 본문 정리

### 3.1 게시글에 작성자 정보를 연결하기

게시글 작성자는 사용자 한 명이고, 한 사용자는 여러 게시글을 작성할 수 있다. 그래서 `Article` 모델에 사용자 외래 키를 둔다.

```python
# articles/models.py

from django.conf import settings
from django.db import models


class Article(models.Model):
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
    )
    title = models.CharField(max_length=100)
    content = models.TextField()
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
```

`settings.AUTH_USER_MODEL`을 사용하면 프로젝트에서 커스텀 유저 모델을 쓰더라도 관계가 깨지지 않는다. 사용자 모델을 직접 참조하는 것보다 유연하다.

⚠️ 주의: 이미 데이터가 있는 모델에 `ForeignKey`를 추가하면 기존 레코드의 user 값을 어떻게 채울지 migration 과정에서 물어볼 수 있다. 실습 중이라면 데이터 초기화나 기본값 설정 여부를 신중히 선택해야 한다.

### 3.2 게시글 생성 시 request.user를 저장하기

게시글 작성 form에는 제목과 내용만 들어가는 경우가 많다. 작성자는 사용자가 직접 고르는 값이 아니라, 현재 로그인한 사용자 `request.user`로 정해야 한다.

```python
# articles/views.py

from django.contrib.auth.decorators import login_required
from django.shortcuts import redirect, render
from .forms import ArticleForm


@login_required
def create(request):
    if request.method == 'POST':
        form = ArticleForm(request.POST)

        if form.is_valid():
            article = form.save(commit=False)
            article.user = request.user
            article.save()
            return redirect('articles:detail', article.pk)
    else:
        form = ArticleForm()

    return render(request, 'articles/create.html', {'form': form})
```

여기서도 `commit=False`가 중요하다. form이 만든 Article 인스턴스에 작성자 정보를 추가한 뒤 저장해야 하기 때문이다.

📌 핵심: 작성자 정보는 사용자가 form에서 보내는 값이 아니라, 서버가 현재 로그인 세션의 `request.user`를 기준으로 넣어야 한다.

### 3.3 수정과 삭제는 작성자만 가능해야 한다

작성자 관계를 저장했다면 이제 권한 확인에 사용할 수 있다. 게시글을 수정하거나 삭제할 때 요청한 사용자와 게시글 작성자가 같은지 확인한다.

```python
from django.shortcuts import get_object_or_404, redirect
from .models import Article


@login_required
def delete(request, article_pk):
    article = get_object_or_404(Article, pk=article_pk)

    if request.user == article.user:
        article.delete()

    return redirect('articles:index')
```

템플릿에서도 같은 기준으로 버튼을 보여줄 수 있다.

```html
{% if request.user == article.user %}
  <a href="{% url 'articles:update' article.pk %}">수정</a>
  <form action="{% url 'articles:delete' article.pk %}" method="POST">
    {% csrf_token %}
    <button type="submit">삭제</button>
  </form>
{% endif %}
```

템플릿에서 버튼을 숨기는 것은 사용자 경험을 위한 처리다. 하지만 실제 보안은 view에서 다시 확인해야 한다. 사용자가 URL을 직접 호출할 수도 있기 때문이다.

### 3.4 댓글 작성자도 사용자와 연결한다

댓글 역시 작성자 정보가 필요하다. 댓글은 게시글에도 속하고 사용자에게도 속한다. 즉, `Comment`는 두 개의 N:1 관계를 가질 수 있다.

```python
class Comment(models.Model):
    article = models.ForeignKey(
        Article,
        on_delete=models.CASCADE,
    )
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
    )
    content = models.CharField(max_length=200)
    created_at = models.DateTimeField(auto_now_add=True)
```

댓글을 저장할 때는 게시글과 작성자를 모두 채워야 한다.

```python
@login_required
def comments_create(request, article_pk):
    article = get_object_or_404(Article, pk=article_pk)
    comment_form = CommentForm(request.POST)

    if comment_form.is_valid():
        comment = comment_form.save(commit=False)
        comment.article = article
        comment.user = request.user
        comment.save()

    return redirect('articles:detail', article.pk)
```

### 3.5 related_name으로 역참조 이름을 정리하기

사용자와 여러 모델이 연결되면 기본 역참조 이름이 충돌하거나 읽기 어려워질 수 있다. 이때 `related_name`을 사용한다.

```python
class Article(models.Model):
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name='articles',
    )
    title = models.CharField(max_length=100)
    content = models.TextField()
```

이렇게 하면 특정 사용자가 작성한 게시글을 다음처럼 조회할 수 있다.

```python
user_articles = request.user.articles.all()
```

`article_set`보다 `articles`가 훨씬 의미가 분명하다. 관계가 많아질수록 `related_name`은 단순한 옵션이 아니라 코드 가독성을 지키는 장치가 된다.

## 4. 적용 관점에서 다시 보기

사용자와 연결되는 N:1 관계를 설계할 때는 "이 데이터의 소유자 또는 작성자가 누구인가"를 먼저 생각한다. 게시글, 댓글, 리뷰, 주문 같은 데이터는 대부분 사용자와 연결된다.

구현 순서는 다음처럼 잡으면 좋다.

1. 모델에 사용자 외래 키를 추가한다.
2. migration을 적용한다.
3. 생성 view에서 `commit=False` 후 `request.user`를 저장한다.
4. 수정/삭제 view에서 작성자 권한을 확인한다.
5. 템플릿에서 작성자일 때만 수정/삭제 UI를 보여준다.
6. 필요하면 `related_name`으로 역참조 이름을 정리한다.

⚠️ 주의: 템플릿에서 버튼을 숨기는 것만으로 권한 처리가 끝났다고 생각하면 안 된다. 실제 데이터 변경은 view에서 막아야 한다.

## 5. 배운 점 / 확장 포인트

### 5.1 이번 강의 이전에 몰랐던 것 또는 새로 이해된 것

사용자와 콘텐츠의 관계를 저장하면 단순히 작성자 이름을 보여주는 것 이상으로, 수정/삭제 권한과 마이페이지 조회 같은 기능의 기준이 생긴다.

### 5.2 앞으로 이어지는 연결점

이 구조는 이후 좋아요, 팔로우 같은 N:M 관계로 이어진다. 사용자와 콘텐츠가 N:1로 연결되는 것에서 출발해, 사용자와 게시글이 여러 대 여러로 연결되는 기능까지 확장된다.

### 5.3 더 파볼 만한 주제

권한 처리가 복잡해지면 view 함수 안의 단순 비교를 넘어 permission, mixin, decorator 같은 구조로 분리할 수 있다. DRF에서는 permission class로 같은 문제를 다룬다.

## 6. 요약 정리

사용자와 게시글, 사용자와 댓글 관계는 대표적인 N:1 관계다. 작성자 정보를 모델에 저장하면 화면 표시뿐 아니라 권한 제어의 기준까지 만들 수 있다.

🧠 기억할 것:

- 사용자 외래 키는 `settings.AUTH_USER_MODEL`로 연결하는 것이 안전하다.
- 생성 form에는 작성자 필드가 없어도 view에서 `request.user`를 넣을 수 있다.
- 작성자만 수정/삭제할 수 있도록 view에서 반드시 검증한다.
- 댓글은 게시글에도 속하고 사용자에게도 속할 수 있다.
- `related_name`은 역참조 이름을 명확하게 만든다.
