## 1. 들어가며
이번 강의는 단순히 Django 명령어 몇 개를 외우는 시간이 아니다. 오히려 **웹 애플리케이션이 어떤 구조로 동작하는지**를 먼저 이해하고, 그 위에서 **Django가 그 구조를 어떻게 구현하게 도와주는지**를 익히는 시간에 가깝다.

처음 Django를 배울 때 막히는 이유는 보통 비슷하다. 프로젝트와 앱의 차이가 모호하고, 가상 환경은 왜 만드는지 체감이 잘 안 되며, `urls.py`, `views.py`, `templates`가 각각 무슨 역할을 하는지도 코드 몇 줄만 보고는 잘 연결되지 않는다. 그래서 이 강의는 개별 파일 설명을 따로 떼어 외우기보다, **요청과 응답의 흐름 속에서 각 요소를 이해하는 것**이 중요하다.

이 글은 그 흐름을 따라간다. 먼저 웹과 서버의 기본 구조를 잡고, Django를 쓰는 이유와 가상 환경의 필요성을 정리한 뒤, Django 프로젝트를 만들고 앱을 연결하고, 마지막에는 **사용자의 요청이 URL → View → Template를 거쳐 화면으로 돌아오는 과정**까지 이어서 살펴본다.

## 2. 핵심 개념 정리
이 강의의 큰 흐름은 아래처럼 잡아두면 이해가 훨씬 쉽다.

1. **웹 애플리케이션은 클라이언트와 서버의 요청-응답 구조로 동작한다.**  
   브라우저가 요청을 보내고, 서버가 필요한 결과를 만들어 응답한다.
2. **Frontend와 Backend는 역할이 다르다.**  
   화면을 보여주고 상호작용을 만드는 쪽이 프론트엔드라면, 요청을 처리하고 데이터를 다루는 쪽이 백엔드다.
3. **Django는 백엔드 개발을 빠르게 도와주는 웹 프레임워크다.**  
   이미 필요한 구조와 규칙을 제공하기 때문에, 개발자는 핵심 기능 구현에 집중할 수 있다.
4. **프로젝트마다 가상 환경과 의존성 관리를 분리해야 한다.**  
   같은 컴퓨터에서 여러 프로젝트를 다룰 때 버전 충돌과 협업 문제를 줄이기 위해서다.
5. **Django는 MVT 패턴으로 구조를 나눈다.**  
   프로젝트와 앱을 분리하고, 요청을 URL에서 받고, View에서 처리한 뒤, Template으로 화면을 만든다.
6. **실제 구현은 데이터 흐름을 따라 작성해야 한다.**  
   즉, `URLS → View → Template` 순서로 생각하고 코드를 작성하는 습관이 중요하다.

이제부터는 이 큰 그림을 놓치지 않은 채, 각 개념을 필요한 자리에서 바로 예시와 코드까지 붙여서 정리해 보자.

## 3. 본문 정리
이제부터는 강의의 핵심 내용을 흐름대로 정리한다. 각 개념은 정의만 적고 끝내지 않고, 왜 필요한지와 실제 코드에서 어떻게 보이는지까지 함께 묶어 이해한다.

### 3.1 웹 애플리케이션과 클라이언트-서버 구조
**웹 애플리케이션**은 인터넷을 통해 브라우저에서 접근해 사용하는 소프트웨어다.

여기서 가장 먼저 잡아야 할 개념이 **클라이언트와 서버**다. 사용자의 브라우저나 모바일 앱은 서비스를 요청하는 쪽이고, 서버는 그 요청을 받아 필요한 데이터를 찾거나 계산한 뒤 결과를 응답하는 쪽이다. 웹 페이지를 본다는 것은 사실상, 브라우저가 어딘가의 서버에 파일이나 데이터를 요청하고 그 응답을 받아 화면으로 해석하는 과정이라고 볼 수 있다.

![클라이언트와 서버 구조](assets/images/01_client_server.png)

위 그림처럼 핵심은 단순하다. **클라이언트는 요청하고, 서버는 응답한다.** 그런데 Django를 배우는 이유는 바로 이 “응답을 만들어내는 서버 쪽 로직”을 체계적으로 구현하기 위해서다.

예를 들어 사용자가 브라우저 주소창에 어떤 주소를 입력하면, 브라우저는 서버에 특정 페이지를 달라고 요청한다. 서버는 그 요청에 맞는 내용을 찾아 돌려주고, 브라우저는 그것을 사람이 읽을 수 있는 화면으로 바꿔 보여준다. 이 기본 구조를 놓치면 뒤에서 배우는 `urls.py`, `views.py`, `template`도 각각 따로 노는 개념처럼 보이기 쉽다.

⚠️ 주의  
처음에는 “웹 페이지를 보여주는 것”만 눈에 들어와서 브라우저가 주인공처럼 느껴지지만, 실제로는 **응답을 어떻게 만들지 결정하는 서버 쪽 설계**가 훨씬 중요하다. Django는 바로 그 서버를 만드는 도구다.

📌 핵심: **웹은 요청과 응답의 구조로 움직이며, Django는 그중 서버의 응답 생성 과정을 담당한다.**

### 3.2 Frontend, Backend, 그리고 Django
**Frontend**는 사용자가 직접 보는 화면과 상호작용을 다루고, **Backend**는 요청 처리, 데이터 관리, 인증, 보안 같은 서버 측 기능을 담당한다.

처음 웹 개발을 배울 때 프론트엔드와 백엔드를 단순히 “화면 / 뒤쪽” 정도로 외우면 금방 헷갈린다. 더 정확하게 보면, 프론트엔드는 **사용자 경험이 실제로 드러나는 영역**이고, 백엔드는 **그 경험이 가능하도록 뒤에서 로직과 데이터를 관리하는 영역**이다.

강의 노트에서는 프론트엔드 예시로 HTML, CSS, JavaScript, 그리고 Vue.js 같은 프레임워크가 언급되고, 백엔드 예시로 Python 기반의 Django가 등장한다. 즉, Django는 화면 자체를 화려하게 만드는 도구라기보다, **클라이언트의 요청을 받아 적절한 응답을 생성하는 백엔드 프레임워크**로 이해해야 한다.

이 지점에서 함께 나오는 개념이 **웹 프레임워크**다. 웹 서비스에는 로그인, 회원 관리, 라우팅, 보안, 데이터베이스 연결처럼 반복적으로 필요한 기능이 많다. 이런 것을 매번 바닥부터 다 만들기보다, 이미 검증된 구조와 도구를 제공받아 빠르게 개발할 수 있게 해 주는 것이 프레임워크다.

Django를 쓰는 이유도 여기 있다.

- Python 기반이라 문법 접근성이 좋고 활용 범위가 넓다.
- 보안, 관리자 기능, ORM 등 실무에서 자주 필요한 기능이 기본 제공된다.
- 구조가 비교적 뚜렷해서 프로젝트를 체계적으로 확장하기 좋다.
- 대규모 서비스 사례와 커뮤니티가 풍부하다.

💡 포인트  
강의에서는 Django를 “클라이언트-서버 구조의 서버를 구현하는 것이 목적”이라고 설명한다. 이 문장을 중심에 두면, 왜 Django가 필요한지 훨씬 분명해진다.

📌 핵심: **Django는 백엔드 개발을 빠르게 하기 위한 웹 프레임워크이며, 요청을 받아 응답을 만드는 서버 로직을 구조적으로 구현하게 도와준다.**

### 3.3 가상 환경과 의존성 관리
**가상 환경(virtual environment)**은 하나의 컴퓨터 안에서 프로젝트마다 독립된 Python 실행 환경을 따로 두는 방식이다.

처음에는 “그냥 Python 하나 설치해서 쓰면 되는 것 아닌가?” 싶지만, 프로젝트가 두 개만 되어도 금방 문제가 생긴다. 어떤 프로젝트는 `Django 4.2`가 필요하고, 다른 프로젝트는 `Django 5.x`가 필요할 수 있다. 또 어떤 패키지는 서로 버전 충돌을 일으킬 수도 있다. 이때 전역 환경 하나만 쓰면 프로젝트끼리 서로 영향을 주게 된다.

가상 환경은 이런 충돌을 막는다. 같은 집 안에 방을 따로 나눠 쓰는 것처럼, **프로젝트마다 필요한 패키지와 버전을 따로 관리하는 공간**을 만드는 셈이다.

![가상 환경 구조 예시](assets/images/02_virtual_env_structure.png)

위 그림처럼 전역 Python 환경 위에 프로젝트별 독립 환경을 만들어 두면, 각 환경이 서로 다른 패키지 조합을 가져도 충돌하지 않는다.

가상 환경을 다룰 때 기본 흐름은 아래와 같다.

```bash
# 1) 가상 환경 생성
python -m venv venv

# 2) 가상 환경 활성화
# Git Bash 기준 예시
source venv/Scripts/activate

# 3) 작업 종료 후 비활성화
deactivate
```

여기서 중요한 점은, 가상 환경은 “어딘가로 들어간다”기보다 **현재 터미널이 사용할 Python 환경을 전환한다**는 개념이라는 것이다. 그래서 새 터미널을 열면 다시 활성화해야 한다.

가상 환경과 함께 반드시 따라오는 개념이 **의존성(dependencies)** 이다. 프로젝트가 실행되기 위해 필요한 외부 라이브러리들이 곧 의존성이다. 이 의존성을 다른 사람과 똑같이 맞춰야 협업이 가능해진다.

```bash
# 현재 환경에 설치된 패키지 확인
pip list

# 현재 환경의 패키지와 버전을 기록
pip freeze > requirements.txt

# 기록된 의존성을 그대로 설치
pip install -r requirements.txt
```

`requirements.txt`가 중요한 이유는 단순히 목록을 적어두기 위해서가 아니다. 같은 프로젝트를 다른 컴퓨터에서 다시 실행할 때, **어떤 버전의 패키지들이 설치되어 있어야 하는지 재현하는 기준점**이 되기 때문이다.

⚠️ 주의  
- `venv` 폴더 자체는 보통 `.gitignore`에 넣고 저장소에 올리지 않는다.  
- 대신 `requirements.txt`를 공유해서 각자 같은 환경을 재구성한다.  
- 활성화 명령은 운영체제와 셸에 따라 조금씩 다를 수 있다.

📌 핵심: **가상 환경은 프로젝트 간 충돌을 막고, 의존성 관리는 협업과 재현 가능한 실행 환경을 만든다.**

### 3.4 Django 프로젝트 시작 루틴
**Django 프로젝트 생성**은 단순히 명령어를 실행하는 작업이 아니라, 앞으로의 개발 환경을 올바르게 세팅하는 출발점이다.

강의에서는 프로젝트 생성 전에 먼저 가상 환경과 의존성 파일을 만드는 루틴을 강조한다. 이 순서를 익혀 두면 나중에 새 프로젝트를 시작할 때 훨씬 덜 흔들린다.

```bash
# 1. 가상 환경 생성
python -m venv venv

# 2. 가상 환경 활성화
source venv/Scripts/activate

# 3. Django 설치
pip install django

# 4. 의존성 기록
pip freeze > requirements.txt

# 5. 프로젝트 생성
django-admin startproject firstpjt .

# 6. 개발 서버 실행
python manage.py runserver
```

여기서 `django-admin startproject firstpjt .` 명령은 `firstpjt`라는 Django 프로젝트를 현재 위치에 생성하겠다는 뜻이다. 마지막의 `.` 은 **현재 디렉터리에 바로 생성하라**는 의미다.

서버를 실행하면 기본적으로 로컬 개발 서버가 열리고, 브라우저에서 접속해 동작을 확인할 수 있다. 이때 중요한 것은, 명령어를 외우는 것보다 **왜 이 순서로 진행하는지 이해하는 것**이다. 프로젝트를 만들기 전에 가상 환경을 준비해야, 이후 설치되는 패키지들이 해당 프로젝트에만 묶이기 때문이다.

💡 포인트  
Git 저장소까지 함께 만들 예정이라면, 보통 `.gitignore`를 먼저 만들고 `venv` 같은 폴더가 추적되지 않도록 정리한 뒤 `git init`을 하는 편이 깔끔하다.

📌 핵심: **Django 프로젝트는 가상 환경과 의존성 관리가 먼저 정리된 상태에서 시작해야 이후 관리가 쉬워진다.**

### 3.5 디자인 패턴: MVC와 Django의 MVT
**디자인 패턴**은 소프트웨어 설계에서 반복적으로 나타나는 문제를 검증된 방식으로 풀기 위한 구조적 해법이다.

웹 개발에서 대표적으로 자주 언급되는 패턴이 **MVC**다.

- **Model**: 데이터와 비즈니스 로직 처리
- **View**: 사용자에게 보이는 화면
- **Controller**: 사용자의 입력을 받고 흐름을 제어

그런데 Django는 이 MVC를 그대로 부르지 않고, **MVT(Model, View, Template)** 구조로 설명한다.

- **Model**: 데이터와 관련된 로직 관리
- **Template**: 사용자에게 보여 줄 화면 구성
- **View**: 요청을 받아 필요한 로직을 처리하고 응답 반환

처음엔 이름이 달라서 전혀 다른 구조처럼 느껴질 수 있지만, 강의의 핵심은 이 부분이다. **Django의 MVT는 본질적으로 MVC와 같은 역할 분리를 다른 이름으로 표현한 것**이다. 보통 MVC의 `Controller` 역할을 Django의 `View`가 담당하고, MVC의 `View` 역할을 Django의 `Template`이 맡는다고 이해하면 흐름이 정리된다.

왜 이런 구조가 중요할까? 화면, 데이터, 제어 흐름을 한 파일에 몰아넣지 않고 역할별로 나누면, 수정 범위를 분리할 수 있고 유지보수가 쉬워진다. 특히 웹 서비스처럼 기능이 계속 늘어나는 구조에서는 역할 분리가 곧 생산성과 연결된다.

⚠️ 주의  
MVT를 외울 때 이름만 바꾸어 암기하면 금방 헷갈린다. **“누가 데이터를 다루고, 누가 응답을 조립하고, 누가 화면을 담당하는가”**를 기준으로 역할을 잡아야 한다.

📌 핵심: **Django의 MVT는 MVC와 본질적으로 같은 역할 분리 구조이며, 이름보다 역할 흐름으로 이해해야 한다.**

### 3.6 프로젝트와 앱의 관계
**프로젝트(project)** 는 전체 설정과 앱들을 묶는 큰 단위이고, **앱(application)** 은 특정 기능을 담당하는 독립 모듈이다.

처음 Django를 접하면 프로젝트와 앱의 차이가 가장 헷갈린다. 하지만 강의의 비유를 따라가면 꽤 직관적이다. 예를 들어 온라인 커뮤니티를 만든다고 했을 때, 프로젝트는 전체 서비스 그 자체이고, 앱은 게시글, 댓글, 회원 관리처럼 기능별로 나뉜 구성 요소다.

![프로젝트와 앱의 관계](assets/images/03_project_app.png)

즉, 프로젝트는 전체 운영 틀을 잡고, 앱은 실제 기능을 담당한다. 이 구분이 필요한 이유는 기능을 모듈 단위로 나눠 관리하기 위해서다. 기능이 커질수록 파일 하나에 다 넣는 방식은 금방 한계에 부딪힌다.

앱 생성은 다음과 같이 한다.

```bash
python manage.py startapp articles
```

앱을 만들었다고 바로 끝나는 것은 아니다. Django가 이 앱을 사용하도록 알려 주기 위해 **반드시 프로젝트 설정에 앱을 등록**해야 한다.

![INSTALLED_APPS에 앱 등록](assets/images/04_installed_apps.png)

아래는 학습용으로 주석을 보강한 예시다.

```python
# firstpjt/settings.py

INSTALLED_APPS = [
    'articles',              # 우리가 방금 만든 앱을 Django에 등록
    'django.contrib.admin',  # 관리자 페이지 기능
    'django.contrib.auth',   # 인증 기능
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
]
```

여기서 중요한 순서는 **앱을 먼저 생성하고, 그다음 등록하는 것**이다. 존재하지 않는 앱 이름을 먼저 적어 두면 Django가 해당 앱을 찾지 못해 오류가 난다.

⚠️ 주의  
- 앱 이름은 보통 복수형을 권장한다. 예: `articles`, `comments`  
- 앱 생성 전 등록은 불가능하다.  
- 프로젝트는 전체 설정, 앱은 기능 단위라는 구분을 계속 유지해야 구조가 안 헷갈린다.

📌 핵심: **프로젝트는 전체 틀, 앱은 기능 단위 모듈이며, 앱은 생성 후 `INSTALLED_APPS`에 등록해야 Django가 인식한다.**

### 3.7 Django의 요청-응답 흐름: URL → View → Template
**Django의 핵심 흐름**은 사용자의 요청이 URL에서 시작해 View를 거쳐 Template로 연결되고, 최종적으로 응답이 브라우저에 전달되는 구조다.

이 부분은 Django를 배우는 초반에 가장 중요하다. 파일 이름을 따로 외우기보다, **하나의 요청이 시스템 안에서 어떻게 이동하는지**를 따라가야 한다.

![요청과 응답의 전체 흐름](assets/images/05_request_response.png)

예를 들어 사용자가 `/articles/` 라는 주소로 접속했다고 가정해 보자. 그러면 Django는 먼저 URL 설정을 보고, 이 요청을 어떤 함수가 처리해야 하는지 결정한다.

#### 3.7.1 URLs: 요청을 어떤 View로 보낼지 정한다
`urls.py` 는 들어온 경로를 적절한 View와 연결하는 역할을 한다.

![urls.py 연결 예시](assets/images/06_urls_py.png)

```python
# firstpjt/urls.py

from django.contrib import admin
from django.urls import path
from articles import views  # articles 앱의 views 모듈을 가져온다

urlpatterns = [
    path('admin/', admin.site.urls),      # 관리자 페이지 경로
    path('articles/', views.index),       # /articles/ 요청을 index 함수로 연결
]
```

이 코드에서 중요한 것은 경로 문자열과 연결 대상이다. `/articles/` 요청이 들어오면 `views.index` 함수가 호출된다. 즉, URL 설정은 **“이 주소로 들어온 요청을 누구에게 맡길 것인가”**를 정하는 라우팅 표라고 볼 수 있다.

⚠️ 주의  
강의에서 강조한 규칙 중 하나는 **URL 문자열 경로를 `/` 로 끝내는 것**이다. 작은 규칙처럼 보이지만, Django는 이런 프레임워크 규칙을 전제로 동작하므로 습관처럼 지키는 편이 좋다.

#### 3.7.2 View: 요청을 받아 응답을 조립한다
`views.py` 의 View 함수는 요청을 받아 필요한 로직을 처리하고, 최종 응답 객체를 반환한다.

![views.py 예시](assets/images/07_views_py.png)

```python
# articles/views.py

from django.shortcuts import render


def index(request):
    # request: 사용자의 요청 정보가 담긴 객체
    # 'articles/index.html': 사용자에게 보여 줄 템플릿 경로
    return render(request, 'articles/index.html')
```

여기서 `render()` 함수는 Django 초반 학습에서 꼭 익숙해져야 하는 함수다. 역할은 분명하다. **템플릿과 필요한 데이터를 결합해, 브라우저에 돌려줄 응답 객체를 만들어 준다.**

강의 노트 기준으로 `render()`의 핵심 인자는 다음 세 가지다.

- `request`: 현재 요청 객체
- `template_name`: 어떤 템플릿을 렌더링할지 지정
- `context`: 템플릿에 전달할 데이터 딕셔너리(필요할 때 사용)

초기 단계에서는 데이터 없이 템플릿만 반환하는 예제부터 시작하지만, 이후에는 `context`로 데이터를 넘기게 된다. 그래서 지금부터 `render()`를 단순히 화면 출력 함수로 보기보다, **요청과 화면을 이어 주는 핵심 함수**로 이해해 두는 것이 좋다.

⚠️ 주의  
모든 View 함수는 첫 번째 인자로 요청 객체를 받는다. 매개변수 이름은 이론적으로 달라도 되지만, 관례적으로 `request`를 사용한다.

#### 3.7.3 Template: 실제로 보여 줄 화면을 작성한다
Template은 브라우저에 보일 HTML 문서다. 중요한 것은 Django가 템플릿을 아무 위치에서나 찾는 것이 아니라, **정해진 폴더 규칙**을 따라 찾는다는 점이다.

![템플릿 폴더 구조](assets/images/08_templates_structure.png)

강의의 예시는 아래 구조다.

```text
articles/
 └─ templates/
     └─ articles/
         └─ index.html
```

그리고 템플릿 파일은 다음처럼 작성할 수 있다.

```html
<!-- articles/templates/articles/index.html -->
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>Document</title>
</head>
<body>
    <h1>Hello, Django</h1>
</body>
</html>
```

여기서 왜 `templates/articles/index.html` 처럼 앱 이름을 한 번 더 포함하는 구조를 쓰는지가 중요하다. 여러 앱이 동시에 존재할 때 `index.html` 같은 이름은 쉽게 겹칠 수 있기 때문이다. 그래서 **앱 이름으로 한 번 더 폴더를 구분해 충돌을 피하는 것**이 일반적이다.

![템플릿 경로 규칙](assets/images/09_template_path_rule.png)

View에서 템플릿 경로를 적을 때는 Django가 이미 `app/templates/` 까지는 기본 경로로 인식하고 있기 때문에, 그 뒤의 경로인 `'articles/index.html'` 만 적는다. 이 규칙을 이해하지 못하면 템플릿 경로를 잘못 써서 오류가 나는 경우가 많다.

⚠️ 주의  
- 폴더 이름은 반드시 `templates` 여야 한다.  
- 이 폴더는 개발자가 직접 만들어야 한다.  
- View에서 경로를 적을 때는 `templates` 이전이 아니라, 그 **이후 경로**를 적는다.

#### 3.7.4 브라우저에서 응답 확인하기
위 과정을 모두 연결하면, 사용자가 `/articles/` 로 요청했을 때 `index` View가 실행되고, 그 안에서 `articles/index.html` 템플릿을 렌더링해 브라우저로 돌려주게 된다.

![브라우저 결과 화면](assets/images/10_browser_result.png)

즉, 브라우저에 보이는 “Hello, Django” 화면은 단순히 HTML 파일 하나가 떠 있는 것이 아니라, **URL 연결 → View 실행 → Template 렌더링**이라는 내부 과정을 거쳐 완성된 결과다.

![요청과 응답 과정 정리](assets/images/11_request_response_summary.png)

마지막으로 강의에서 특히 강조한 부분이 있다. 실제 구현도 데이터 흐름을 따라 작성해야 한다는 점이다.

![코드 작성 순서 정리](assets/images/12_code_flow_order.png)

요청은 `URLs → View → Template` 순서로 흐르므로, 코드를 작성할 때도 이 흐름을 기준으로 구조를 잡으면 덜 헷갈린다. 예를 들어 어떤 페이지를 만들고 싶다면, 먼저 어떤 URL로 들어올지 정하고, 그 요청을 처리할 View를 만든 뒤, 마지막으로 보여 줄 Template을 작성하는 식으로 생각하면 된다.

📌 핵심: **Django의 핵심 흐름은 URL이 요청을 받고, View가 처리하며, Template이 화면을 구성하는 구조다.**

### 3.8 Django에서 초반에 꼭 지켜야 할 규칙들
처음 배우는 단계에서는 “왜 이렇게까지 규칙이 많지?”라는 생각이 들 수 있다. 하지만 프레임워크의 규칙은 개발자를 괴롭히기 위한 것이 아니라, **일관성과 유지보수성을 확보하기 위한 약속**이다.

강의에서 반복해서 나온 규칙은 특히 아래 세 가지다.

1. `urls.py` 에서 경로 문자열은 보통 `/` 로 끝낸다.  
2. 모든 View 함수는 첫 번째 인자로 요청 객체를 받는다.  
3. Django는 정해진 템플릿 경로(`app/templates/...`)를 따라 파일을 찾는다.

또 하나 흥미로운 보조 개념으로 **Trailing Comma(후행 쉼표)** 도 등장한다. 리스트, 딕셔너리, 튜플 등에서 마지막 요소 뒤에 쉼표를 두는 방식인데, 문법상 필수는 아니지만 여러 줄 구조에서 요소를 추가하거나 순서를 바꿀 때 편하고, 코드 변경 이력도 깔끔해지는 장점이 있다.

예를 들면 아래처럼 쓸 수 있다.

```python
urlpatterns = [
    path('articles/', views.index),
]
```

지금 단계에서 후행 쉼표 자체가 핵심은 아니지만, 이런 작은 문법 습관도 결국은 **협업과 유지보수에 유리한 코드 스타일**로 이어진다는 점을 알아 두면 좋다.

📌 핵심: **프레임워크 규칙은 암기 대상이라기보다, 일관된 구조를 유지하기 위한 약속으로 이해해야 한다.**

## 4. 적용 관점에서 다시 보기
이제 이 강의 내용을 실제로 어떻게 떠올리고 적용하면 좋은지 정리해 보자.

처음 Django 프로젝트를 만들 때는 세부 파일 설명을 한꺼번에 외우려 하지 말고, 아래 순서로 생각하면 된다.

1. **환경부터 분리한다.**  
   새 프로젝트를 시작하면 먼저 가상 환경을 만들고 활성화한다. 그다음 Django를 설치하고 `requirements.txt`를 관리한다.

2. **큰 틀은 프로젝트, 기능은 앱으로 나눈다.**  
   전체 서비스 설정은 프로젝트가 맡고, 게시글·댓글·회원 관리처럼 기능 단위는 앱으로 분리한다.

3. **페이지 하나를 만들 때는 URL → View → Template 순서로 떠올린다.**  
   사용자가 어떤 주소로 들어오는지 정하고, 그 요청을 누가 처리할지 View를 만들고, 마지막에 보여 줄 Template을 연결한다.

4. **문제가 생기면 흐름을 끊어 확인한다.**  
   예를 들어 화면이 안 뜬다면, URL이 잘 연결되었는지, View 함수가 맞는 템플릿을 반환하는지, 템플릿 경로가 규칙에 맞는지 순서대로 확인하면 된다.

실전에서 자주 틀리는 패턴도 거의 비슷하다.

- 앱을 생성하지 않았는데 `INSTALLED_APPS`에 먼저 등록함
- `templates` 폴더 이름이나 위치를 잘못 만듦
- View에서 템플릿 경로를 전체 파일 경로처럼 잘못 적음
- URL 경로와 브라우저 주소가 서로 맞지 않음
- 가상 환경을 활성화하지 않은 상태에서 패키지를 설치하거나 서버를 실행함

💡 포인트  
이 강의에서 배운 내용은 사실 “Django를 처음 실행하는 방법”보다 더 넓다. **웹 서비스가 구조적으로 어떻게 분리되는가**를 배우는 입문 단계이기 때문에, 나중에 데이터베이스, 폼, 인증, ORM, 템플릿 문법을 배우더라도 계속 같은 흐름 위에 쌓이게 된다.

## 5. 배운 점 / 느낀 점 / 확장 포인트
이번 강의에서 가장 중요한 배움은 Django가 단순 명령어 모음이 아니라, **웹 애플리케이션을 일정한 구조로 만들게 해 주는 프레임워크**라는 점이다.

특히 가상 환경과 의존성 관리는 초반에는 번거롭게 느껴지지만, 실제로는 프로젝트를 안정적으로 유지하기 위한 기본 습관이라는 점이 드러난다. 이 부분을 초기에 제대로 익혀 두면, 나중에 프로젝트 수가 늘어나도 환경 문제로 흔들릴 가능성이 크게 줄어든다.

또 하나 중요한 확장 포인트는 MVT 구조다. 지금은 단순히 URL 하나, View 하나, Template 하나를 연결하는 수준이지만, 이후에는 여기에 Model이 붙고, 데이터 조회와 저장, 사용자 입력 처리, 인증과 권한, 정적 파일 관리까지 차례로 확장된다. 따라서 이번 강의는 작은 예제를 다룬 것처럼 보여도, 실제로는 **앞으로 배울 Django 전체 구조의 뼈대를 세우는 시간**이라고 볼 수 있다.

앞으로 더 공부해 보면 좋은 주제는 아래와 같다.

- Django 앱과 프로젝트를 더 체계적으로 분리하는 기준
- `render()`의 `context`를 활용한 동적 데이터 전달
- Model을 이용한 데이터베이스 연동
- URL 분리(`include`)와 앱 단위 라우팅
- Django의 LTS 버전과 버전별 차이 이해

## 6. 요약 정리
📌 핵심  
- 웹 애플리케이션은 **클라이언트의 요청과 서버의 응답** 구조로 동작한다.
- Django는 그중 **서버 로직을 구조적으로 구현하는 백엔드 프레임워크**다.
- 프로젝트마다 가상 환경을 분리해야 패키지 버전 충돌을 막을 수 있다.
- `requirements.txt` 는 협업과 재현 가능한 환경 구성을 위한 핵심 파일이다.
- Django는 MVC와 유사한 **MVT 패턴**으로 구조를 나눈다.
- 프로젝트는 전체 설정, 앱은 기능 단위 모듈이다.
- 사용자의 요청은 **URL → View → Template** 흐름으로 처리된다.

🧠 기억할 것  
- Django 초반 학습의 핵심은 파일 이름 암기가 아니라 **요청과 응답의 흐름 이해**다.  
- 코드도 데이터 흐름을 따라 작성하면 구조가 훨씬 선명해진다.  
- 프레임워크의 규칙은 제약이 아니라, 일관된 개발을 위한 약속이다.
