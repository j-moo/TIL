- 🎯 글의 목표: HTTP의 무상태 특성에서 왜 인증이 필요한지 이해하고, Django에서 쿠키·세션·커스텀 User 모델·로그인 구현이 하나의 흐름으로 어떻게 이어지는지 정리한다.

## 1. 들어가며
웹 애플리케이션에서 로그인은 너무 익숙해서, 마치 당연히 되는 기능처럼 느껴지기 쉽다. 하지만 HTTP 자체는 사용자를 기억하지 못하는 프로토콜이다. 한 번 요청을 처리하고 나면 연결이 끊기고, 다음 요청이 같은 사람에게서 왔는지도 스스로는 알 수 없다.

그래서 로그인 기능을 이해하려면 먼저 “왜 서버가 사용자를 기억하지 못하는가”를 알아야 한다. 그 위에서 쿠키가 어떤 역할을 하고, 세션은 왜 서버 쪽에 저장되는지, Django는 이 과정을 어떻게 감싸서 인증 시스템으로 제공하는지를 봐야 한다.

이번 강의는 바로 그 흐름을 따라간다. 먼저 쿠키와 세션을 이해하고, 그다음 Django 기본 User 모델의 한계를 짚은 뒤, 프로젝트 초기에 커스텀 User 모델로 바꾸는 이유를 확인한다. 마지막으로 `AuthenticationForm`, `login`, `request.user`를 이용해 실제 로그인 기능이 어떻게 완성되는지까지 이어진다.

## 2. 핵심 개념 정리
이번 강의의 큰 흐름은 아래처럼 잡아두면 이해가 훨씬 쉽다.

1. **HTTP는 무상태(stateless)다.**  
   서버는 요청과 응답이 끝나면 사용자를 기억하지 않는다.
2. **그래서 상태를 유지할 장치가 필요하다.**  
   이때 쿠키와 세션이 등장한다.
3. **쿠키는 브라우저 쪽, 세션은 서버 쪽 중심의 상태 유지 방식이다.**  
   실무에서는 보통 “세션 데이터는 서버에 저장하고, 세션 ID만 쿠키로 주고받는 구조”를 많이 쓴다.
4. **Django는 이 과정을 인증 시스템으로 제공한다.**  
   User 모델, 세션 관리, 로그인/로그아웃 관련 기능이 모두 묶여 있다.
5. **프로젝트에서는 기본 User 모델 대신 커스텀 User 모델을 일찍 설정하는 것이 중요하다.**  
   나중에 바꾸려면 마이그레이션과 DB 구조가 꼬이기 쉽기 때문이다.
6. **그 위에서 로그인 기능을 구현한다.**  
   `AuthenticationForm`으로 입력을 받고, `auth_login()`으로 세션을 생성하며, 템플릿에서는 `request.user` 또는 `user`로 현재 로그인 상태를 활용한다.

즉, 이번 강의는 단순히 로그인 화면 하나를 만드는 강의가 아니라, **Django 인증 구조 전체를 처음부터 끝까지 연결해서 보는 입문 강의**라고 보면 된다.

## 3. 본문 정리
이제 개념별로 흐름을 따라가 보자. 중요한 점은 각 개념이 따로 떨어져 있지 않다는 것이다. HTTP의 무상태성 때문에 쿠키와 세션이 필요해지고, 그 위에 인증이 올라가며, Django는 이를 User 모델과 인증 시스템으로 제공한다.

### 3.1 HTTP가 무상태이기 때문에 인증이 필요하다
- **개념 한 줄 정의**: HTTP는 요청과 응답이 끝나면 연결과 상태를 유지하지 않는 프로토콜이다.

웹 브라우저가 어떤 페이지를 요청하고 서버가 응답을 보내면, 그 연결은 끝난다. 이 말은 서버 입장에서 “방금 로그인한 사용자”와 “지금 다시 요청한 사용자”를 자동으로 같은 사람으로 연결할 수 없다는 뜻이다.

이 지점이 처음에는 조금 어색할 수 있다. 우리는 쇼핑몰 장바구니도 유지되고, 로그인도 유지되는 웹을 रोज रोज 쓰기 때문이다. 하지만 그것은 HTTP가 원래 그렇게 하는 것이 아니라, **별도의 상태 유지 장치가 위에 덧붙어 있기 때문**이다.

쉽게 말하면, HTTP는 매 요청마다 처음 만나는 사람처럼 행동한다. 따라서 로그인 상태, 장바구니, 개인 설정 같은 정보를 유지하려면 추가 장치가 반드시 필요하다.

⚠️ 주의  
HTTP의 무상태성을 “서버가 아무것도 저장하지 못한다”로 이해하면 안 된다. 정확히는 **프로토콜 자체가 요청 간 상태를 자동으로 연결해주지 않는다**는 뜻이다. 서버는 별도의 저장 장치를 통해 얼마든지 상태를 관리할 수 있다.

📌 핵심  
로그인 기능은 HTTP가 원래 기억하지 못하는 상태를, 별도의 메커니즘으로 이어 붙이는 과정이다.

### 3.2 쿠키는 브라우저가 들고 다니는 작은 상태 정보다
- **개념 한 줄 정의**: 쿠키는 서버가 브라우저에 저장시키는 작은 key-value 데이터 조각이다.

쿠키는 웹사이트가 브라우저에게 “이 정보 좀 기억해 둬”라고 맡겨 두는 작은 메모라고 생각하면 이해가 쉽다. 서버는 응답할 때 `Set-Cookie` 헤더를 통해 쿠키를 전달하고, 브라우저는 이를 저장한 뒤 같은 사이트에 다시 요청할 때 `Cookie` 헤더에 담아 보낸다.

이 구조 덕분에 서버는 “이 요청이 이전 요청과 같은 브라우저에서 왔는가”를 판단할 수 있다. 로그인 유지, 장바구니, 언어 설정 저장 같은 기능이 여기서 출발한다.

![쿠키 요청-응답 흐름](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 221815-1.png>)

위 그림처럼 쿠키는 결국 **브라우저가 매 요청마다 서버에 들고 가는 정보**다. 그래서 상태가 없는 HTTP 위에서도 어느 정도의 연속성을 만들 수 있다.

쿠키의 핵심 특징은 다음과 같다.

- 브라우저에 저장된다.
- key-value 형식이다.
- 요청마다 자동으로 함께 전송된다.
- 로그인 유지, 장바구니, 사용자 설정 저장 등에 자주 사용된다.

여기서 중요한 점은, 쿠키는 편리하지만 브라우저에 저장된다는 점이다. 따라서 비밀번호처럼 민감한 정보를 그대로 넣는 것은 위험하다.

⚠️ 주의  
쿠키는 모든 요청에 포함되어 전송될 수 있으므로 크기를 불필요하게 키우면 성능에 불리하다. 또 클라이언트 쪽에 저장되므로 민감한 원본 데이터를 그대로 넣는 방식은 피해야 한다.

📌 핵심  
쿠키는 “브라우저가 서버에 계속 들고 가는 상태 정보”이며, 인증 상태 유지의 출발점이 된다.

### 3.3 세션은 실제 인증 데이터를 서버 쪽에 저장하는 방식이다
- **개념 한 줄 정의**: 세션은 사용자 상태 정보를 서버에 저장하고, 브라우저는 그 세션을 가리키는 ID만 쿠키로 보관하는 방식이다.

쿠키만으로 상태를 유지할 수도 있지만, 로그인 정보처럼 중요한 데이터를 브라우저에 직접 두는 것은 부담이 크다. 그래서 보통은 **실제 데이터는 서버에 저장하고, 브라우저에는 세션 ID만 전달**한다.

이 구조를 이해할 때는 “열쇠” 비유가 잘 맞는다. 서버 안에 중요한 정보가 들어 있는 사물함이 있고, 브라우저는 그 사물함 번호표만 들고 다닌다고 생각하면 된다. 브라우저가 다음 요청에서 번호표를 보여주면, 서버는 그 번호표를 보고 해당 사용자의 로그인 상태를 다시 확인할 수 있다.

![세션 구조 1](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 221941-1.png>)

![세션 구조 2](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 221954-1.png>)

세션의 흐름은 보통 다음과 같다.

1. 사용자가 로그인 요청을 보낸다.
2. 서버가 인증에 성공하면 세션 데이터를 저장한다.
3. 서버가 세션 ID를 발급한다.
4. 브라우저는 이 세션 ID를 쿠키에 저장한다.
5. 이후 요청마다 브라우저는 세션 ID를 쿠키로 보낸다.
6. 서버는 세션 ID를 보고 로그인 상태를 확인한다.

이 방식은 쿠키에 실제 로그인 정보를 직접 넣는 것보다 안전하다. 다만 세션 ID 자체가 탈취되면 문제가 될 수 있으므로, 세션도 보안 관점에서 관리가 필요하다.

추가로 쿠키의 수명도 알아둘 필요가 있다.

- **Session Cookie**: 브라우저 세션이 끝나면 사라진다.
- **Persistent Cookie**: `Expires`나 `Max-Age`에 따라 일정 기간 유지된다.

⚠️ 주의  
세션 데이터는 서버 자원을 사용한다. 즉, 세션은 보안에 유리하지만 공짜가 아니다. 사용량이 많아질수록 저장과 만료 정책도 함께 고민해야 한다.

📌 핵심  
세션은 “중요한 상태 정보는 서버에 두고, 브라우저는 세션 ID만 들고 다니게 만드는 방식”이다.

### 3.4 Django 인증 시스템은 User, Session, Login 기능을 묶어 제공한다
- **개념 한 줄 정의**: Django Authentication System은 사용자 인증과 세션 기반 로그인에 필요한 기본 뼈대를 제공하는 시스템이다.

Django는 단순히 User 테이블 하나만 제공하는 것이 아니라, 인증과 관련된 여러 요소를 함께 제공한다. 대표적으로 다음이 포함된다.

- User 모델
- 세션 관리
- 로그인/로그아웃 기능
- 권한과 그룹 관리

즉, 우리가 처음부터 인증 시스템을 설계하지 않아도, Django가 이미 기본 구조를 마련해 두고 있다. 이번 강의에서 하는 일은 그 구조를 **이해하고 프로젝트에 맞게 연결하는 것**이다.

인증의 필요성을 다시 연결해서 보면, 결국 인증은 “서버가 여러 사용자를 구분하기 위해 필요한 과정”이다. 아이디/비밀번호 기반 인증, 소셜 로그인, 생체 인증 등 다양한 방식이 있지만, Django의 기본 인증 시스템은 그중에서도 가장 기본적인 로그인 구조를 안정적으로 제공한다.

💡 포인트  
Django 인증 시스템을 배울 때는 기능을 외우는 것보다, **User 모델 ↔ 세션 ↔ 로그인 함수 ↔ 템플릿의 user 변수**가 하나의 흐름이라는 점을 이해하는 것이 더 중요하다.

📌 핵심  
Django 인증 시스템은 “사용자 식별 + 로그인 상태 유지 + 인증 관련 기능”을 하나로 묶은 기본 프레임워크다.

### 3.5 기본 User 모델은 편리하지만 확장성에 한계가 있다
- **개념 한 줄 정의**: Django 기본 User 모델은 바로 쓸 수 있지만, 프로젝트 요구에 맞게 바꾸기에는 제약이 있다.

기본 User 모델은 `username`, `password`, `email` 같은 기본 필드를 제공하므로 빠르게 개발을 시작할 수 있다. 하지만 실제 프로젝트에서는 금방 한계에 부딪힌다.

예를 들어,
- 이메일을 아이디처럼 쓰고 싶을 수 있고,
- 닉네임, 생년월일, 프로필 이미지 같은 필드를 추가하고 싶을 수 있으며,
- 반대로 필요 없는 필드는 줄이고 싶을 수도 있다.

문제는 기본 User 모델을 프로젝트 중간에 바꾸는 것이 매우 까다롭다는 점이다. 그래서 Django도 **프로젝트를 시작할 때부터 커스텀 User 모델을 쓰는 것을 강하게 권장**한다.

### 3.6 커스텀 User 모델은 프로젝트 초기에 반드시 잡아두는 것이 좋다
- **개념 한 줄 정의**: 커스텀 User 모델은 기본 User 모델 대신 프로젝트에서 사용할 사용자 모델을 직접 지정하는 방식이다.

이번 강의에서는 `accounts` 앱을 만들고, `AbstractUser`를 상속받는 `User` 클래스를 작성하는 방식으로 커스텀 User 모델을 설정한다. 여기서 `accounts`라는 앱 이름을 권장하는 이유는 Django 내부에서 인증 관련 흐름과 잘 어울리고, 프로젝트 구조도 읽기 쉬워지기 때문이다.

먼저 `accounts` 앱을 만들고 프로젝트에 등록한다.

![accounts 앱 준비와 include](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222102-1.png>)

그 다음, `models.py`에서 `AbstractUser`를 상속받는 `User` 모델을 만든다.

![커스텀 User 모델 정의](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222134-1.png>)

```python
# accounts/models.py
from django.contrib.auth.models import AbstractUser

class User(AbstractUser):
    # 지금은 기본 User와 같은 필드 구조를 그대로 사용한다.
    # 하지만 이후 닉네임, 프로필 이미지 같은 필드를 추가하기 쉬워진다.
    pass
```

이 코드가 중요한 이유는, 지금은 `pass` 한 줄이라 별 차이가 없어 보여도 **프로젝트가 앞으로 사용할 사용자 모델의 주도권을 우리가 가져온 것**이기 때문이다.

그다음 `settings.py`에 아래 설정을 추가한다.

![AUTH_USER_MODEL 설정](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222207-1.png>)

```python
# settings.py
AUTH_USER_MODEL = 'accounts.User'
```

이 설정은 Django에게 “이 프로젝트에서 User라고 하면 이제 기본 auth.User가 아니라 accounts.User를 써라”라고 알려주는 역할을 한다.

마지막으로 admin 페이지에서도 새 User 모델을 볼 수 있도록 등록한다.

![admin 등록](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222229-1.png>)

```python
# accounts/admin.py
from django.contrib import admin
from django.contrib.auth.admin import UserAdmin
from .models import User

admin.site.register(User, UserAdmin)
```

그리고 마이그레이션을 진행하면, 실제로 사용하는 User 테이블이 `accounts_user`로 바뀌는 것을 확인할 수 있다.

![커스텀 User 테이블 반영](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222305-1.png>)

여기서 가장 많이 하는 실수는 **프로젝트를 한참 진행한 뒤에 User 모델을 바꾸려는 것**이다. Django 공식 문서도 중간 변경을 강하게 권장하지 않는다. 이미 마이그레이션이 쌓인 상태라면 DB 초기화가 필요해질 수 있다.

⚠️ 주의  
커스텀 User 모델은 프로젝트 시작 직후, 가능하면 첫 마이그레이션 전에 설정하는 것이 가장 안전하다.

📌 핵심  
지금 당장 추가 필드가 없어도, Django 프로젝트는 처음부터 커스텀 User 모델을 쓰는 습관이 중요하다.

### 3.7 `AbstractUser`는 기본 User 모델의 기능을 거의 그대로 가져오는 출발점이다
- **개념 한 줄 정의**: `AbstractUser`는 Django 기본 User 모델의 핵심 필드와 기능을 이미 구현해 둔 추상 기본 클래스다.

`AbstractUser`를 상속받는다는 말이 처음에는 조금 낯설 수 있다. 여기서 핵심은 **데이터베이스 테이블을 바로 만드는 클래스가 아니라, 다른 User 모델을 만들기 위한 기반 클래스**라는 점이다.

![AbstractUser 구조](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 223421-1.png>)

![추상 기본 클래스 비교](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 223458-1.png>)

쉽게 말하면, `AbstractUser`는 “완성된 User를 만들기 위한 기본 틀”이다. 이미 `username`, `email`, `password`, 권한 관련 필드 등 대부분이 준비되어 있으므로, 우리는 그 틀을 가져와 프로젝트에 맞게 살짝 확장하면 된다.

이 강의에서 굳이 `AbstractBaseUser`가 아니라 `AbstractUser`를 사용하는 이유도 여기 있다. 인증 구조를 처음 배우는 단계에서는 필요한 기본 기능이 대부분 준비된 `AbstractUser`가 훨씬 실용적이다.

💡 포인트  
처음 커스텀 유저 모델을 만들 때는 `AbstractUser`를 기본 선택지로 생각하는 편이 좋다. 정말 사용자 인증 구조를 처음부터 전부 설계해야 할 특별한 이유가 있을 때만 더 낮은 수준의 클래스까지 내려가면 된다.

📌 핵심  
`AbstractUser`는 “기본 User의 기능을 거의 그대로 가진 채, 프로젝트 맞춤형 User로 확장하기 좋은 출발점”이다.

### 3.8 로그인은 인증에 성공한 사용자를 세션과 연결하는 과정이다
- **개념 한 줄 정의**: 로그인은 단순 입력이 아니라, 인증에 성공한 사용자를 서버 세션에 연결하는 과정이다.

이번 강의에서 아주 중요한 문장은 이것이다. **로그인은 아이디와 비밀번호를 맞게 입력하는 행위 자체가 아니라, 인증이 끝난 사용자를 세션과 연결해 상태를 유지하게 만드는 과정**이라는 점이다.

![로그인 개념도](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222346-1.png>)

그래서 로그인 구현은 보통 아래 흐름으로 이해해야 한다.

1. 로그인 페이지를 보여준다.
2. 사용자가 아이디/비밀번호를 입력해 전송한다.
3. 서버가 입력값을 검증한다.
4. 검증이 성공하면 세션을 만든다.
5. 세션 ID를 쿠키로 브라우저에 보낸다.
6. 이후 요청에서 로그인 상태가 유지된다.

즉, 로그인은 화면을 띄우는 일과 인증 처리, 세션 생성이 모두 합쳐진 동작이다.

📌 핵심  
로그인은 “인증 성공 + 세션 생성 + 이후 요청에서 상태 유지”까지 포함하는 개념이다.

### 3.9 로그인 URL과 템플릿은 GET과 POST를 분리해서 생각해야 한다
- **개념 한 줄 정의**: 로그인 기능은 GET 요청으로 폼을 보여주고, POST 요청으로 사용자 입력을 받아 인증을 처리한다.

먼저 URL을 연결한다.

![로그인 URL 연결](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222413-1.png>)

```python
# accounts/urls.py
from django.urls import path
from . import views

app_name = 'accounts'
urlpatterns = [
    path('login/', views.login, name='login'),
]
```

프로젝트 메인 URL에서도 `accounts` 앱의 경로를 include 해준다.

```python
# project/urls.py
from django.urls import path, include

urlpatterns = [
    path('accounts/', include('accounts.urls')),
]
```

그리고 다른 템플릿에서 로그인 페이지로 이동할 수 있는 링크를 둔다.

```django
<!-- articles/index.html -->
<a href="{% url 'accounts:login' %}">Login</a>
```

이제 뷰에서 GET 요청일 때는 빈 로그인 폼을 화면에 보여준다.

![로그인 폼 표시용 뷰](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222440-1.png>)

```python
# accounts/views.py
from django.shortcuts import render
from django.contrib.auth.forms import AuthenticationForm

def login(request):
    if request.method == 'POST':
        pass
    else:
        form = AuthenticationForm()

    context = {
        'form': form,
    }
    return render(request, 'accounts/login.html', context)
```

여기서 `AuthenticationForm`은 로그인 인증을 위한 Django 내장 폼이다. 이 폼은 사용자를 새로 만들거나 수정하는 `ModelForm`이 아니라, 입력받은 아이디와 비밀번호가 올바른지를 검사하는 데 초점을 둔다.

그리고 템플릿에서는 반드시 `POST` 방식과 `csrf_token`을 사용해야 한다.

![로그인 폼 템플릿](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222518-1.png>)

```django
<!-- accounts/login.html -->
<h1>로그인</h1>
<form action="{% url 'accounts:login' %}" method="POST">
  {% csrf_token %}
  {{ form.as_p }}
  <input type="submit">
</form>
```

왜 GET이 아니라 POST를 쓰는지도 꼭 이해해야 한다. 로그인 정보는 민감한 데이터이므로 URL에 그대로 노출되는 GET보다, 요청 본문으로 전송되는 POST가 적절하다.

⚠️ 주의  
로그인 폼에서 `csrf_token`을 빼먹으면 Django가 요청을 막는다. 인증 기능은 특히 CSRF 보호를 반드시 챙겨야 한다.

📌 핵심  
로그인 페이지는 GET으로 보여주고, 실제 인증 처리는 POST로 수행한다.

### 3.10 `AuthenticationForm`과 `auth_login()`이 로그인 처리의 중심이다
- **개념 한 줄 정의**: `AuthenticationForm`은 사용자 입력을 검증하고, `auth_login()`은 인증된 사용자를 세션에 연결한다.

이제 POST 요청이 들어왔을 때의 핵심 로직을 보자.

![POST 처리와 로그인](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222544-1.png>)

![get_user와 auth_login 연결](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222736-1.png>)

```python
# accounts/views.py
from django.shortcuts import render, redirect
from django.contrib.auth.forms import AuthenticationForm
from django.contrib.auth import login as auth_login


def login(request):
    if request.method == 'POST':
        # AuthenticationForm은 request와 사용자 입력값을 함께 받는다.
        form = AuthenticationForm(request, request.POST)

        # 입력값이 유효하고, 실제 인증까지 통과했는지 검사한다.
        if form.is_valid():
            # 인증된 사용자 객체를 꺼내 현재 request의 세션에 로그인 상태로 기록한다.
            auth_login(request, form.get_user())
            return redirect('articles:index')
    else:
        # GET 요청일 때는 빈 로그인 폼을 만들어 화면에 보여준다.
        form = AuthenticationForm()

    context = {
        'form': form,
    }
    return render(request, 'accounts/login.html', context)
```

이 코드에서 흐름을 잘 봐야 한다.

- `AuthenticationForm(request, request.POST)`는 로그인에 필요한 입력을 받는다.
- `form.is_valid()`는 단순 형식 검사가 아니라 실제 인증 가능 여부까지 확인한다.
- `form.get_user()`는 인증에 성공한 사용자 객체를 돌려준다.
- `auth_login(request, user)`는 그 사용자를 현재 세션에 연결한다.
- 그 뒤 `redirect()`로 메인 페이지 등 원하는 곳으로 보내면 된다.

처음 배우는 입장에서는 `AuthenticationForm`이 폼을 보여주는 역할도 하고, 검증도 하고, 사용자 객체도 꺼내주는 점이 조금 복합적으로 느껴질 수 있다. 하지만 전체 흐름을 보면 깔끔하다. **폼이 입력을 받고 검증하고, 로그인 함수가 세션에 기록한다**고 생각하면 된다.

⚠️ 주의  
`auth_login`을 그냥 `login`으로 import 하면 현재 작성 중인 뷰 함수 이름 `login`과 충돌할 수 있다. 그래서 `login as auth_login`처럼 별칭을 주는 습관이 안전하다.

📌 핵심  
`AuthenticationForm`은 인증 확인, `auth_login()`은 세션 연결을 담당한다.

### 3.11 로그인 후에는 세션 테이블과 브라우저 쿠키에서 흔적을 확인할 수 있다
- **개념 한 줄 정의**: 로그인에 성공하면 서버 DB의 세션 테이블과 브라우저 쿠키 둘 다에서 결과를 확인할 수 있다.

로그인이 “눈에 보이지 않는 내부 동작”처럼 느껴질 때는, 실제 저장 위치를 확인해 보면 이해가 훨씬 빨라진다.

![django_session 테이블 확인](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222824-1.png>)

위 화면처럼 Django는 기본적으로 `database-backed sessions`를 사용하므로, 세션 정보가 `django_session` 테이블에 저장된다.

브라우저 개발자 도구에서도 쿠키를 확인할 수 있다.

![브라우저 쿠키 확인](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 222905-1.png>)

이때 브라우저에서 보이는 것은 실제 로그인 정보 전체가 아니라 **세션 ID**에 가깝다. 이 점을 직접 확인해 보면 “왜 세션은 서버 저장 방식이라고 하는가”가 훨씬 선명해진다.

💡 포인트  
세션 기반 로그인은 서버와 브라우저 둘 중 한쪽만 보면 반쪽 이해가 되기 쉽다. DB의 `django_session`과 브라우저 쿠키를 함께 확인해 보는 습관이 디버깅에도 좋다.

📌 핵심  
로그인 성공의 흔적은 서버의 `django_session`과 브라우저의 쿠키에 동시에 남는다.

### 3.12 템플릿에서는 `user` 변수를 통해 로그인 상태를 바로 활용할 수 있다
- **개념 한 줄 정의**: Django 템플릿에서는 context processor 덕분에 인증 관련 `user` 데이터를 기본적으로 사용할 수 있다.

로그인까지 끝났다면, 이제 화면에서 “누가 로그인했는지”를 보여주고 싶어진다. 이때 별도로 뷰에서 `user`를 넘기지 않아도 템플릿에서 `{{ user }}`나 `{{ user.username }}`을 쓸 수 있다.

![템플릿에서 user 사용](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 223054-1.png>)

```django
<!-- articles/index.html -->
<h3>Hello, {{ user.username }}</h3>
```

왜 이런 변수가 자동으로 들어오는지는 context processor를 보면 이해할 수 있다.

![context processor 설정](<../assets/images/04_21_Django_Auth_1/화면 캡처 2026-04-26 223213-1.png>)

`django.contrib.auth.context_processors.auth`가 활성화되어 있으면, 인증 관련 데이터가 템플릿 컨텍스트에 기본 포함된다. 그래서 현재 로그인한 사용자를 템플릿에서 곧바로 사용할 수 있다.

이 지점은 실무에서도 매우 중요하다. 로그인/로그아웃 버튼을 조건부로 표시하거나, 사용자 이름을 헤더에 보여주거나, 작성자 본인에게만 수정 버튼을 보여주는 기능이 모두 여기서 시작되기 때문이다.

⚠️ 주의  
`user` 변수가 자동으로 보인다고 해서, 모든 요청에서 항상 인증된 사용자라는 뜻은 아니다. 비로그인 상태에서는 `AnonymousUser`일 수 있으므로, 보통 `user.is_authenticated`와 함께 사용한다.

📌 핵심  
템플릿의 `user` 변수는 Django가 미리 넣어주는 인증 컨텍스트 데이터다.

### 3.13 Django의 세션 관리 기본값과 보안 관점도 함께 알아둘 필요가 있다
- **개념 한 줄 정의**: Django는 기본적으로 DB 기반 세션 저장 방식을 사용하며, 쿠키와 세션은 수명과 보안 관점에서 함께 이해해야 한다.

Django는 기본적으로 세션 정보를 데이터베이스의 `django_session` 테이블에 저장한다. 즉, 인증 관련 상태를 우리가 직접 일일이 관리하지 않아도 기본 메커니즘이 상당 부분 대신 처리해 준다.

하지만 “Django가 알아서 해 준다”와 “아무것도 몰라도 된다”는 다르다. 다음 정도는 반드시 기억해 두는 것이 좋다.

- 쿠키에는 보통 세션 ID 같은 제한된 정보만 둔다.
- 쿠키에는 만료 시간이 있을 수 있다.
- 세션 ID가 탈취되면 공격자가 사용자인 척할 수 있다.
- 쿠키 사용에는 개인정보 보호와 동의 이슈도 따라올 수 있다.

로그인 기능을 단순 구현 과제로만 보면 이 부분이 뒤로 밀리기 쉽다. 하지만 실제 서비스에서는 인증과 보안이 거의 붙어 다닌다. 따라서 쿠키와 세션을 배울 때부터 보안 관점도 함께 가져가는 것이 좋다.

📌 핵심  
Django는 세션 관리를 많이 도와주지만, 수명과 보안까지 포함해 이해해야 인증 기능을 제대로 다룰 수 있다.

### 4.1 이런 요구가 나오면 쿠키와 세션을 떠올린다
- 로그인 상태를 유지해야 한다.
- 장바구니나 사용자 설정을 기억해야 한다.
- 요청이 여러 번 이어져도 같은 사용자인지 식별해야 한다.

이런 요구가 나오면, HTTP가 원래 무상태라는 사실을 먼저 떠올려야 한다. 그리고 “무엇을 브라우저에 둘지, 무엇을 서버에 둘지”를 나눠 생각하면 구조가 잡힌다.

### 4.2 Django 프로젝트를 시작하면 User 모델부터 점검한다
새 프로젝트를 만들 때는 아래 순서를 습관처럼 가져가면 좋다.

1. `accounts` 앱 생성
2. `AbstractUser` 상속 User 모델 작성
3. `AUTH_USER_MODEL` 설정
4. admin 등록
5. 그다음 마이그레이션 진행

이 순서를 놓치면 나중에 인증 구조를 수정할 때 일이 커진다. 특히 “일단 기본 User로 시작했다가 나중에 바꾸자”는 생각이 가장 위험하다.

### 4.3 로그인 구현은 항상 GET/POST를 나눠서 본다
로그인 뷰를 보면 헷갈리기 쉬운 이유는, 한 함수 안에 폼 표시와 폼 처리 로직이 같이 있기 때문이다. 이럴 때는 아래처럼 나누어 생각하면 정리가 된다.

- **GET**: 빈 `AuthenticationForm`을 만들어 화면에 보여준다.
- **POST**: 사용자가 입력한 값으로 `AuthenticationForm`을 다시 만들고, 유효성 검사를 거쳐 로그인 처리한다.

이 구조는 로그인뿐 아니라 회원가입, 글 작성, 수정 같은 거의 모든 폼 처리의 기본 패턴이 된다.

### 4.4 디버깅할 때는 DB와 브라우저를 함께 본다
로그인이 안 될 때는 코드만 보는 것보다 아래를 같이 확인하는 편이 더 빠르다.

- `form.is_valid()`를 통과하는지
- `redirect()`가 실행되는지
- `django_session` 테이블에 세션이 생기는지
- 브라우저 쿠키에 세션 ID가 들어왔는지
- 템플릿에서 `user.is_authenticated`가 True인지

즉, 인증 디버깅은 **뷰 코드 + 세션 테이블 + 브라우저 쿠키 + 템플릿 상태**를 같이 봐야 흐름이 보인다.

## 5. 배운 점 / 느낀 점 / 확장 포인트
이번 강의에서 가장 크게 남는 점은, 로그인 기능을 단순한 화면 기능이 아니라 **프로토콜 특성 위에 구축되는 구조**로 봐야 한다는 것이다.

처음 Django 인증을 배울 때는 `AuthenticationForm`, `login`, `request.user` 같은 이름만 외우기 쉽다. 하지만 그렇게 접근하면 왜 세션이 생기고, 왜 쿠키가 필요하며, 왜 커스텀 User 모델을 프로젝트 초기에 바꿔야 하는지가 각각 따로 노는 지식이 된다.

반대로 이번 흐름대로 보면 모든 것이 연결된다. HTTP의 무상태성 때문에 상태 유지 장치가 필요하고, 그 장치로 쿠키와 세션이 쓰이며, Django는 이를 인증 시스템으로 제공하고, 그 위에서 커스텀 User 모델과 로그인 구현이 이어진다.

확장해서 공부해 볼 만한 포인트도 분명하다.

- 회원가입 구현과 `UserCreationForm`
- 로그인 후 로그아웃 처리
- `request.user.is_authenticated`를 이용한 화면 분기
- 작성자 본인만 수정/삭제 가능하도록 권한 분기
- `LOGIN_REDIRECT_URL`, `next` 파라미터 처리
- 커스텀 User 모델에 추가 필드 붙이기

즉, 이번 강의는 인증의 끝이 아니라 시작점이다. 이후의 회원가입, 권한 제어, 작성자 인증, 소셜 로그인까지 모두 여기서 뻗어 나간다.

## 6. 요약 정리
📌 핵심
- HTTP는 무상태라서 로그인 상태를 자동으로 기억하지 못한다.
- 쿠키는 브라우저에 저장되는 작은 상태 정보다.
- 세션은 실제 상태 정보를 서버에 저장하고, 브라우저는 세션 ID만 쿠키로 들고 다닌다.
- Django 인증 시스템은 User, 세션, 로그인 기능을 기본 제공한다.
- 프로젝트는 처음부터 커스텀 User 모델을 설정하는 것이 안전하다.
- `AuthenticationForm`은 로그인 입력 검증, `auth_login()`은 세션 연결을 담당한다.
- 템플릿에서는 context processor 덕분에 `user` 변수를 바로 사용할 수 있다.

🧠 기억할 것
- 로그인은 단순 입력이 아니라 **인증된 사용자를 세션과 연결하는 과정**이다.
- `AUTH_USER_MODEL`은 **프로젝트 초기에** 설정해야 한다.
- 로그인 디버깅은 코드만 보지 말고 **세션 테이블과 브라우저 쿠키까지 함께 확인**해야 한다.
