# Vue SFC와 프로젝트 구조 정리

- 🎯 글의 목표: Vue의 Single-File Components 구조를 이해하고, Vite 기반 Vue 프로젝트를 생성한 뒤 컴포넌트를 나누어 등록하는 흐름까지 정리한다.
- 🧩 핵심 키워드: Component, SFC, Vite, NPM, package.json, package-lock.json, node_modules, 컴포넌트 등록, Virtual DOM, Composition API, CSS scoped
- ⭐ 중요도: 높음
- 📝 한눈에 보는 내용: 이번 강의는 Vue 프로젝트를 처음 만들 때 반드시 알아야 하는 파일 구조와 컴포넌트 작성 방식을 다룬다. 하나의 `.vue` 파일 안에서 화면, 로직, 스타일이 어떻게 나뉘는지 확인하고, Vite와 NPM이 프로젝트 실행과 패키지 관리에서 어떤 역할을 하는지 연결해서 이해한다.
- 🔗 관련 문제 / 주제: Vue 프로젝트 생성, 컴포넌트 분리, 부모-자식 컴포넌트 등록, 스타일 범위 제한, DOM 직접 접근 대신 ref 사용

---

## 1. 들어가며

Vue를 처음 배울 때 가장 먼저 막히는 부분은 문법 하나하나보다도, 파일 구조와 실행 흐름이 낯설다는 점이다. HTML, CSS, JavaScript를 따로 작성하던 방식과 달리 Vue에서는 하나의 컴포넌트를 기준으로 화면 구조, 동작 로직, 스타일을 함께 관리한다.

이때 등장하는 핵심 개념이 **SFC(Single-File Components)**이다. SFC는 하나의 `.vue` 파일 안에 `template`, `script`, `style`을 담아 컴포넌트 단위로 화면을 구성하는 방식이다. 이 방식은 코드가 처음에는 낯설어 보일 수 있지만, 화면을 작은 블록으로 나누어 재사용하고 관리하기 쉽게 만든다는 점에서 Vue 개발의 중심이 된다.

이번 강의는 크게 세 흐름으로 이해하면 좋다. 먼저 컴포넌트와 SFC의 개념을 잡고, 그다음 Vite와 NPM을 사용해 Vue 프로젝트가 어떻게 만들어지는지 확인한다. 마지막으로 실제 프로젝트 구조 안에서 컴포넌트를 생성하고 부모-자식 관계로 등록하는 방법, 그리고 Virtual DOM과 `style scoped`처럼 Vue가 내부적으로 화면과 스타일을 관리하는 방식을 정리한다.

---

## 2. 핵심 개념 정리

이번 강의가 해결하려는 질문은 다음과 같다.

> Vue에서는 화면을 왜 컴포넌트로 나누고, 그 컴포넌트를 실제 프로젝트 안에서 어떻게 작성하고 실행할까?

이 질문에 답하려면 단순히 `.vue` 파일 문법만 외워서는 부족하다. 컴포넌트가 왜 필요한지, Vite가 왜 필요한지, `npm install`이 무엇을 설치하는지, `package.json`과 `node_modules`가 어떤 관계인지까지 하나의 흐름으로 이해해야 한다.

본문에서는 다음 순서로 내용을 정리한다.

1. **Component와 SFC**  
   웹 화면을 재사용 가능한 블록으로 나누고, 그 블록을 `.vue` 파일 하나에 담는 방식을 이해한다.

2. **Vite, NPM, Build 도구**  
   Vue SFC는 브라우저가 바로 실행하는 파일이 아니므로, 프로젝트를 생성하고 실행하기 위한 빌드 도구와 패키지 관리자가 필요하다는 점을 연결한다.

3. **Vue 프로젝트 구조**  
   `public`, `src`, `App.vue`, `main.js`, `index.html`, 설정 파일, 패키지 관리 파일이 각각 어떤 역할을 하는지 살펴본다.

4. **컴포넌트 활용**  
   부모 컴포넌트인 `App.vue`에서 자식 컴포넌트를 import하고 템플릿에서 사용하는 과정을 정리한다.

5. **Virtual DOM과 추가 주제**  
   Vue가 실제 DOM을 직접 자주 수정하지 않고 효율적으로 화면을 갱신하는 원리를 이해한다. 이후 Composition API, Single Root Element, CSS scoped, Scaffolding, 패키지 관리 주의사항까지 함께 정리한다.

## 3. 본문 정리

이 섹션에서는 강의 흐름을 따라가되, 개념이 등장하는 자리에서 예시와 코드, 이미지를 바로 연결해 정리한다. Vue는 파일 구조와 코드 흐름이 함께 이해되어야 하므로, 설명과 예시를 분리하지 않는 것이 중요하다.

### 3.1 Component: 화면을 재사용 가능한 블록으로 나누기

컴포넌트는 웹 페이지를 구성하는 **재사용 가능한 UI 블록**이다. 쉽게 말하면 화면을 한 번에 통째로 만드는 것이 아니라, 레고 블록처럼 작은 단위로 나누어 조립하는 방식이다.

웹 페이지가 커질수록 하나의 파일이나 하나의 덩어리 안에 모든 화면을 작성하면 관리가 어려워진다. 버튼, 카드, 내비게이션, 게시글 목록, 댓글 영역처럼 반복되거나 독립적으로 관리할 수 있는 부분을 컴포넌트로 분리하면 재사용성이 높아지고 유지보수가 쉬워진다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 112144.png>)

위 그림처럼 화면은 여러 구성 요소로 나눌 수 있고, 이 구성 요소들이 계층 구조를 이룬다. Vue 애플리케이션도 자연스럽게 중첩된 컴포넌트 트리 형태로 구성된다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 112213.png>)

실제 웹 서비스도 하나의 거대한 덩어리가 아니라 여러 컴포넌트의 조합으로 이루어진다. 예를 들어 프로필 카드, 메뉴 영역, 이미지 카드, 버튼 영역이 각각 컴포넌트가 될 수 있다.

💡 포인트: 컴포넌트를 나눈다는 것은 단순히 파일을 많이 만든다는 뜻이 아니다. **역할이 분명한 UI 단위를 따로 관리한다는 뜻**이다.

---

### 3.2 SFC: 하나의 `.vue` 파일 안에 화면, 로직, 스타일을 묶기

SFC는 **Single-File Components**의 약자로, 하나의 `.vue` 파일 안에 컴포넌트의 템플릿, 로직, 스타일을 함께 작성하는 Vue의 파일 형식이다.

기존 방식에서는 HTML, JavaScript, CSS가 각각 다른 파일에 흩어져 있을 수 있다. 하지만 Vue의 SFC는 특정 컴포넌트와 관련된 화면 구조, 동작, 스타일을 한 파일 안에 모아둔다. 덕분에 어떤 컴포넌트를 수정해야 할 때 관련 코드를 한곳에서 확인할 수 있다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 112106.png>)

위 예시는 `MyComponent.vue` 하나의 파일 안에 `template`, `script setup`, `style scoped`가 함께 들어 있는 구조를 보여준다. 화면에는 `Hello World!`라는 문구가 출력되고, 스타일은 해당 컴포넌트 안에서만 적용된다.

```vue
<!-- MyComponent.vue -->

<template>
  <!-- 화면에 보여줄 HTML 구조를 작성하는 영역 -->
  <!-- msg는 script setup에서 선언한 반응형 데이터이다. -->
  <div class="greeting">{{ msg }}</div>
</template>

<script setup>
// Vue에서 ref 함수를 가져온다.
// ref는 값이 바뀌었을 때 화면도 함께 갱신되도록 만드는 반응형 데이터 도구이다.
import { ref } from 'vue'

// msg라는 반응형 변수를 만들고 초기값으로 'Hello World!'를 넣는다.
// template에서는 msg를 바로 사용할 수 있다.
const msg = ref('Hello World!')
</script>

<style scoped>
/* scoped가 붙어 있으므로 이 스타일은 현재 컴포넌트 범위에만 적용된다. */
.greeting {
  color: red;
}
</style>
```

코드를 읽을 때는 세 영역의 역할을 구분하면 이해가 쉽다.

| 영역 | 역할 | 핵심 이해 |
|---|---|---|
| `<template>` | 화면 구조 작성 | 사용자에게 보이는 HTML 구조를 작성한다. |
| `<script setup>` | 로직 작성 | 변수, 함수, import 등 컴포넌트의 동작을 정의한다. |
| `<style scoped>` | 스타일 작성 | 현재 컴포넌트의 CSS를 작성하고 범위를 제한할 수 있다. |

📌 핵심: SFC는 HTML, JavaScript, CSS를 무작정 섞는 방식이 아니라, **하나의 컴포넌트라는 관심사 안에서 화면·로직·스타일을 함께 관리하는 방식**이다.

### 3.3 SFC 구성 요소: template, script, style

각 `.vue` 파일은 일반적으로 세 가지 최상위 블록으로 구성된다. 작성 순서가 반드시 고정된 것은 아니지만, 보통 `template → script → style` 순서로 작성하면 읽기 쉽다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 112407.png>)

#### `<template>` 블록

`template`은 컴포넌트의 화면 구조를 작성하는 영역이다. 각 `.vue` 파일에는 최상위 `template` 블록을 하나만 포함할 수 있다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 112500.png>)

```vue
<template>
  <!-- script에서 선언한 msg 값을 화면에 출력한다. -->
  <div class="greeting">{{ msg }}</div>
</template>
```

여기서 `{{ msg }}`는 Vue의 템플릿 문법이다. JavaScript 변수인 `msg`의 값을 화면에 출력한다. 단순히 문자열을 쓰는 것이 아니라, 데이터와 화면을 연결하는 자리라고 보면 된다.

#### `<script setup>` 블록

`script setup`은 컴포넌트의 로직을 작성하는 영역이다. `.vue` 파일에는 `<script setup>` 블록을 하나만 포함할 수 있다. 이 블록에서 선언한 변수와 함수는 같은 컴포넌트의 템플릿에서 자동으로 사용할 수 있다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 112640.png>)

```vue
<script setup>
// ref는 Vue의 반응형 상태를 만들 때 사용한다.
import { ref } from 'vue'

// msg는 template에서 {{ msg }} 형태로 바로 사용할 수 있다.
const msg = ref('Hello World!')
</script>
```

여기서 중요한 점은 `script setup` 안에서 만든 값이 템플릿과 자연스럽게 연결된다는 것이다. 그래서 컴포넌트 내부에서 필요한 데이터나 함수를 간결하게 작성할 수 있다.

#### `<style scoped>` 블록

`style`은 컴포넌트의 스타일을 작성하는 영역이다. 하나의 `.vue` 파일에는 여러 개의 `<style>` 태그가 들어갈 수 있다. 여기에 `scoped`를 붙이면 CSS가 현재 컴포넌트에만 적용되도록 범위가 제한된다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 112744.png>)

```vue
<style scoped>
/* 현재 컴포넌트 안의 .greeting 요소에만 적용된다. */
.greeting {
  color: red;
}
</style>
```

⚠️ 주의: `scoped`를 붙이지 않은 CSS는 전역 스타일처럼 다른 컴포넌트에도 영향을 줄 수 있다. 특히 `div`, `p`, `h1`처럼 흔히 쓰는 태그 선택자에 스타일을 주면 예상치 못한 컴포넌트까지 스타일이 적용될 수 있다.

### 3.4 SFC를 실행하려면 빌드 도구가 필요하다

Vue SFC는 일반 HTML 파일처럼 브라우저에서 바로 실행되는 파일이 아니다. `.vue` 파일은 브라우저가 그대로 이해할 수 없기 때문에, 컴파일러와 빌드 도구를 거쳐 실행 가능한 JavaScript 코드로 변환되어야 한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 112907.png>)

이때 실제 프로젝트에서는 **Vite** 같은 공식 빌드 도구를 사용한다.

```text
빌드(build): 개발자가 작성한 소스 코드를 실행 가능한 형태로 변환하는 과정
```

쉽게 말하면, 우리가 작성한 `.vue` 파일은 개발자가 보기 좋고 관리하기 좋은 형태이고, 빌드 도구는 이 코드를 브라우저가 실행할 수 있는 형태로 바꾸어 준다.

---

### 3.5 Vite: Vue 프로젝트를 빠르게 실행하는 개발 도구

Vite는 프론트엔드 개발을 위한 빌드 도구이자 개발 서버를 제공하는 도구이다. Vue 프로젝트를 생성하고 실행할 때 Vite를 사용하면 개발 서버를 빠르게 띄울 수 있고, 코드 수정 사항도 거의 즉시 화면에 반영된다.

```text
Vite는 개발 중에는 필요한 파일을 빠르게 제공하고,
배포할 때는 최적화된 파일로 묶어주는 역할을 한다.
```

Vite가 필요한 이유는 단순히 프로젝트를 만드는 명령어 때문만이 아니다. Vue SFC, 여러 JavaScript 모듈, CSS, 이미지 같은 리소스를 실제 브라우저가 사용할 수 있는 형태로 처리해야 하기 때문이다.

---

### 3.6 Build와 Bundling: 여러 파일을 실행 가능한 결과물로 묶기

Build는 프로젝트의 소스 코드를 최적화하고, 배포할 수 있는 형식으로 변환하는 과정이다. 개발 중에는 여러 JavaScript, CSS, 이미지 파일이 나뉘어 있지만, 실제 배포 단계에서는 이를 최적화된 형태로 조합해야 한다.

```text
번들링(bundling): 여러 개로 흩어진 코드 파일을 하나 또는 몇 개의 파일로 묶는 작업
```

처음에는 JavaScript 파일이 몇 개 없기 때문에 큰 문제가 없어 보인다. 하지만 애플리케이션이 커질수록 모듈이 늘어나고, 모듈 사이의 의존성도 복잡해진다. 이때 Bundler는 어떤 파일이 어떤 파일을 필요로 하는지 파악하고, 실행에 필요한 코드와 리소스를 묶어 준다.

### 3.7 NPM과 Node.js: 패키지를 설치하고 관리하는 기반

NPM은 **Node Package Manager**의 약자로, Node.js의 기본 패키지 관리자이다. 개발자가 만든 JavaScript 패키지를 설치하고, 프로젝트에서 어떤 패키지를 사용하는지 관리할 수 있게 해준다.

```bash
# package.json에 기록된 패키지들을 설치한다.
npm install
```

NPM은 단순히 파일을 다운로드하는 도구가 아니다. 프로젝트에 필요한 패키지 목록과 버전 정보를 `package.json`에 기록하고, 실제 설치된 정확한 버전은 `package-lock.json`에 남긴다. 덕분에 다른 사람의 컴퓨터에서도 비슷한 개발 환경을 재현할 수 있다.

Node.js는 Chrome의 V8 JavaScript 엔진을 기반으로 하는 서버 측 실행 환경이다. 원래 JavaScript는 브라우저 안에서 실행되는 언어였지만, Node.js 덕분에 브라우저 밖에서도 JavaScript를 실행할 수 있게 되었다.

```text
Server-Side: 브라우저가 아니라 서버에서 로직을 처리하는 것
```

Vue 프로젝트를 실행할 때 NPM 명령어를 사용하는 이유도 여기에 있다. 프로젝트 생성, 패키지 설치, 개발 서버 실행 같은 작업은 Node.js와 NPM 환경 위에서 이루어진다.

### 3.8 Vue 프로젝트 생성 흐름

Vue 프로젝트는 Vite 기반으로 생성할 수 있다. 터미널에서 다음 명령어를 입력한다.

```bash
# 최신 안정화 버전의 Vue 프로젝트 생성 도구를 실행한다.
npm create vue@latest
```

문서나 튜토리얼에서 명령어 앞에 `$`가 붙어 있다면, 이는 터미널 또는 명령 프롬프트에 입력하는 명령어라는 뜻이다. 실제로 입력할 때 `$`는 제외하고 입력하는 경우가 많다.

```text
latest: 가장 최신 안정화 버전을 사용하겠다는 의미
```

프로젝트 생성 과정에서는 프로젝트 이름과 추가 설정을 선택한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 114228.png>)

프로젝트명 입력 단계에서는 기본값을 사용할 수도 있고, 원하는 프로젝트 이름을 직접 입력할 수도 있다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 114320.png>)

추가 설정 선택 단계에서는 방향키와 space, enter를 사용해 필요한 옵션을 선택한다. 처음 학습 단계에서는 수업에서 요구하는 설정만 선택하고, 불필요한 기능은 나중에 추가하는 편이 이해하기 쉽다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 114341.png>)

프로젝트 생성이 완료되면 안내 메시지에 따라 프로젝트 폴더로 이동하고 패키지를 설치한 뒤 개발 서버를 실행한다.

```bash
# 생성된 프로젝트 폴더로 이동한다.
cd vue-project

# package.json에 적힌 패키지를 설치한다.
npm install

# 개발 서버를 실행한다.
npm run dev
```

⚠️ 주의: `npm install`은 반드시 `package.json` 파일이 있는 프로젝트 루트 디렉토리에서 실행해야 한다. 폴더 위치가 잘못되면 설치 대상 프로젝트를 찾지 못하거나, 엉뚱한 위치에 패키지가 설치될 수 있다.

### 3.9 Module과 Bundler: 파일이 많아질 때 필요한 정리 도구

모듈은 프로그램을 구성하는 독립적인 코드 블록이다. JavaScript 프로젝트에서는 보통 하나의 `.js` 파일을 하나의 모듈로 볼 수 있다.

```text
Module: 프로그램을 구성하는 독립적인 코드 블록
```

애플리케이션이 작을 때는 하나의 파일에 모든 기능을 넣어도 큰 문제가 없어 보인다. 하지만 기능이 많아지면 파일을 나누어 관리해야 하고, 이때 분리된 각 파일이 서로를 import하며 의존성을 갖게 된다.

문제는 모듈 수가 많아질수록 의존성 관계도 복잡해진다는 점이다. 어떤 코드가 어떤 모듈을 필요로 하는지, 특정 문제가 어느 모듈에서 시작되었는지 파악하기 어려워질 수 있다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 114938.png>)

위 이미지는 `node_modules`의 의존성 깊이를 비유적으로 보여준다. `node_modules`는 `npm install`로 설치한 모든 패키지가 모여 있는 저장소이며, 내부적으로 매우 많은 패키지와 하위 의존성을 포함할 수 있다.

Bundler는 이 복잡한 모듈과 파일을 하나 또는 여러 개의 번들로 묶고 최적화하여 사용할 수 있게 만들어 주는 도구이다.

```text
Bundler: 여러 모듈과 파일을 묶고 최적화하여 브라우저에서 사용할 수 있게 만드는 도구
```

Vite는 내부적으로 Rollup이라는 Bundler를 사용한다. 개발자가 일일이 복잡한 설정을 하지 않아도, 기본적인 번들링과 최적화 흐름을 Vite가 처리해 준다.

💡 포인트: 번들링은 단순히 파일을 합치는 작업만이 아니다. import되지 않은 코드를 제거하는 트리 쉐이킹, CSS와 이미지 같은 정적 자원의 처리, 최종 로딩 성능 개선까지 포함한다.

### 3.10 Vue 프로젝트 기본 구조

Vue 프로젝트를 생성하면 여러 폴더와 파일이 자동으로 만들어진다. 이 구조를 한 번에 모두 외우려고 하기보다, 자주 수정하는 곳과 설정을 담당하는 곳을 구분해 이해하면 된다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 114601.png>)

Vue 프로젝트의 기본 구조는 크게 다음과 같이 나눌 수 있다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 115649.png>)

| 위치 | 역할 |
|---|---|
| `public` | import 없이 그대로 참조할 정적 파일을 둔다. |
| `src` | 실제 개발자가 주로 작업하는 소스 코드가 위치한다. |
| `index.html` | Vue 앱이 마운트되는 기본 HTML 파일이다. |
| 설정 파일 | Vite, JavaScript 설정 등 프로젝트 동작 방식을 정의한다. |
| 패키지 관리 파일 | 패키지 목록, 버전, 설치 결과를 관리한다. |

#### public 디렉토리

`public` 디렉토리는 주로 소스 코드에서 직접 import하지 않는 정적 파일을 둘 때 사용한다. 항상 같은 이름으로 접근해야 하거나, 루트 절대 경로로 참조할 파일을 위치시킨다.

예를 들어 `public/icon.png`가 있다면 코드에서는 `/icon.png`처럼 참조할 수 있다.

#### src 디렉토리

`src`는 실제 개발자가 가장 많이 작업하는 폴더이다. 컴포넌트, 스타일, 라우팅 등 프로젝트의 핵심 소스 코드가 이 안에 들어간다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 115925.png>)

`src/assets`는 프로젝트 내부에서 사용하는 이미지, 폰트, 스타일시트 같은 정적 자원을 관리한다. 컴포넌트에서 직접 import해서 사용하는 파일은 보통 이곳에 둔다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 120041.png>)

`src/components`는 재사용 가능한 Vue 컴포넌트를 모아두는 폴더이다. 화면을 구성하는 작은 UI 블록들이 이곳에 위치한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 120148.png>)

#### App.vue

`App.vue`는 Vue 앱의 Root 컴포넌트이다. 다른 하위 컴포넌트들을 포함하며, 애플리케이션 전체의 레이아웃과 공통 요소를 정의하는 출발점 역할을 한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 150242.png>)

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 150305.png>)

#### main.js

`main.js`는 Vue 애플리케이션을 초기화하고 `App.vue`를 실제 DOM에 마운트하는 시작점이다. 필요한 라이브러리를 import하고 전역 설정을 수행하는 파일이기도 하다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 150359.png>)

흐름을 간단히 표현하면 다음과 같다.

```javascript
// Vue 앱을 만들기 위한 createApp 함수를 가져온다.
import { createApp } from 'vue'

// Root 컴포넌트인 App.vue를 가져온다.
import App from './App.vue'

// App 컴포넌트를 기준으로 Vue 앱을 만들고,
// index.html 안의 #app 위치에 마운트한다.
createApp(App).mount('#app')
```

#### index.html

`index.html`은 Vue 앱의 기본 HTML 파일이다. 이 파일 안에는 Vue 앱이 들어갈 위치가 있고, `main.js`가 실행되면서 해당 위치에 Vue 앱을 마운트한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 150618.png>)

```html
<body>
  <!-- Vue 앱이 실제로 들어갈 자리 -->
  <div id="app"></div>

  <!-- Vue 앱의 시작 파일을 불러온다. -->
  <script type="module" src="/src/main.js"></script>
</body>
```

```text
마운트: 만들어진 Vue 앱을 HTML의 특정 위치에 연결해 화면에 보여주는 것
SPA: 하나의 페이지 안에서 필요한 내용만 바꿔가며 보여주는 웹 앱
```

Vue 앱이 SPA라고 불리는 이유는 페이지 전체를 계속 새로고침하는 방식이 아니라, 하나의 HTML 안에서 JavaScript가 화면 내용을 동적으로 바꾸기 때문이다.

#### 기타 설정 파일

Vue 프로젝트에는 Vite 설정 파일과 JavaScript 설정 파일도 포함된다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 152105.png>)

`vite.config.js`는 Vite 프로젝트 설정 파일이다. 플러그인, 빌드 옵션, 개발 서버 설정 등을 관리한다. 예를 들어 `@`를 `src` 경로의 별칭으로 사용하는 설정도 이곳에서 확인할 수 있다.

```text
컴파일 옵션: 디버깅, 최적화 등 컴파일 세부 방식을 제어하는 설정
플러그인: 기존 프로그램에 새로운 기능을 추가하는 확장 기능
```

### 3.11 패키지 관리 파일: package.json, package-lock.json, node_modules

Vue 프로젝트에서 패키지 관리는 처음에는 헷갈리기 쉽다. 특히 `package.json`, `package-lock.json`, `node_modules`가 모두 패키지와 관련되어 있기 때문에 역할을 구분해야 한다.

#### package.json

`package.json`은 프로젝트에 관한 기본 정보와 패키지 의존성을 정의하는 설계도 파일이다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 152242.png>)

이 파일에는 프로젝트 이름, 버전, 실행 가능한 스크립트 명령, 의존성 목록 등이 기록된다. `npm install`은 이 파일을 참고하여 어떤 패키지를 설치해야 하는지 판단한다.

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  },
  "dependencies": {
    "vue": "^3.5.0"
  }
}
```

위 예시에서 `scripts`는 `npm run dev` 같은 명령어로 실행할 수 있는 작업을 정의한다. `dependencies`는 프로젝트 실행에 필요한 패키지 목록을 의미한다.

```text
package.json은 집을 짓기 전에 필요한 재료 목록과 건축 계획서에 가깝다.
필요한 패키지와 허용 가능한 버전 범위를 알려준다.
```

#### package-lock.json

`package-lock.json`은 `package.json`을 바탕으로 실제 설치된 패키지들의 정확한 버전 정보를 기록하는 파일이다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 152547.png>)

`package.json`이 대략적인 설계도라면, `package-lock.json`은 실제로 어떤 버전의 패키지가 설치되었는지 확정해서 남긴 상세 내역서에 가깝다. 협업이나 배포 환경에서 동일한 패키지 구성을 재현하는 데 중요하다.

```text
package-lock.json은 실제 구매한 물건의 정확한 브랜드와 버전이 적힌 구매 내역서에 가깝다.
```

#### node_modules

`node_modules`는 `npm install`을 통해 실제로 설치된 모든 패키지가 저장되는 폴더이다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 152823.png>)

이 폴더는 프로젝트 실행에 필요한 라이브러리와 코드 파일을 실제로 담고 있다. 용량이 매우 클 수 있고, `package.json`과 `package-lock.json`만 있으면 다시 생성할 수 있으므로 일반적으로 Git으로 추적하지 않는다.

```text
node_modules는 설계도와 구매 내역서를 바탕으로 실제 자재들이 쌓여 있는 창고에 가깝다.
```

패키지 관리 관계를 정리하면 다음과 같다.

| 항목 | 비유 | 역할 |
|---|---|---|
| `package.json` | 설계도 | 필요한 패키지와 실행 명령을 정의한다. |
| `package-lock.json` | 상세 구매 내역서 | 실제 설치된 정확한 버전을 기록한다. |
| `node_modules` | 자재 창고 | 설치된 패키지 파일들이 실제로 저장된다. |

⚠️ 주의: `package.json`과 `package-lock.json`을 직접 손으로 수정하는 것보다 `npm install 패키지명` 명령을 통해 자동으로 갱신되게 하는 편이 안전하다.

### 3.12 컴포넌트 사용 3단계

Vue에서 컴포넌트를 활용하는 기본 흐름은 다음 세 단계로 정리할 수 있다.

1. 사전 준비
2. 컴포넌트 파일 생성
3. 컴포넌트 등록 및 사용

#### 1단계: 사전 준비

처음 생성된 프로젝트에는 기본 예시 컴포넌트들이 들어 있다. 강의에서는 `App.vue`를 제외한 초기 컴포넌트를 삭제하고, `App.vue` 코드를 간단하게 초기화했다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 154417.png>)

```vue
<!-- App.vue -->

<template>
  <!-- Root 컴포넌트의 기본 화면 -->
  <h1>App.vue</h1>
</template>

<script setup>
// 처음에는 별도 로직 없이 비워둘 수 있다.
</script>
```

#### 2단계: 컴포넌트 파일 생성

`components` 폴더 아래에 새로운 컴포넌트 파일을 만든다. 강의에서는 `MyComponent.vue`를 생성했다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 154458.png>)

```vue
<!-- components/MyComponent.vue -->

<template>
  <!-- 이 컴포넌트가 담당하는 화면 -->
  <div>
    <h2>MyComponent</h2>
  </div>
</template>

<script setup>
// 현재 예제에서는 별도의 로직이 없다.
</script>
```

#### 3단계: 컴포넌트 등록 및 사용

부모 컴포넌트인 `App.vue`에서 자식 컴포넌트인 `MyComponent.vue`를 import한 뒤, template에서 태그처럼 사용한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 154606.png>)

```vue
<!-- App.vue -->

<template>
  <h1>App.vue</h1>

  <!-- import한 컴포넌트를 템플릿에서 태그처럼 사용한다. -->
  <MyComponent />
</template>

<script setup>
// @는 src/ 경로를 뜻하는 별칭으로 자주 사용된다.
// 상대 경로로는 './components/MyComponent.vue'처럼 작성할 수도 있다.
import MyComponent from '@/components/MyComponent.vue'
</script>
```

여기서 `App.vue`는 부모 컴포넌트, `MyComponent.vue`는 자식 컴포넌트가 된다. 컴포넌트를 import했다는 것은 단순히 파일을 불러온 것이고, 실제 화면에 보이게 하려면 template 안에서 `<MyComponent />`처럼 사용해야 한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 154642.png>)

Vue Devtools를 사용하면 컴포넌트 관계가 제대로 형성되었는지 확인할 수 있다. 화면에 보이는 결과뿐 아니라 컴포넌트 트리에서 부모-자식 구조를 확인하는 습관을 들이면 디버깅에 도움이 된다.

⚠️ 주의: `@` 경로 별칭을 사용할 때는 Vite 설정에서 alias가 제대로 잡혀 있어야 한다. 설정을 변경했다면 개발 서버를 껐다가 다시 실행해야 반영되는 경우가 있다.

### 3.13 하위 컴포넌트 추가와 재사용성 확인

컴포넌트는 한 단계만 나누는 것이 아니라 계속 중첩될 수 있다. 강의에서는 `MyComponent.vue` 안에 다시 `MyComponentItem.vue`를 자식 컴포넌트로 등록했다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 154731.png>)

```vue
<!-- components/MyComponentItem.vue -->

<template>
  <!-- 재사용될 작은 단위의 컴포넌트 -->
  <p>MyComponentItem</p>
</template>
```

```vue
<!-- components/MyComponent.vue -->

<template>
  <div>
    <h2>MyComponent</h2>

    <!-- 같은 컴포넌트를 여러 번 사용하면 재사용성을 확인할 수 있다. -->
    <MyComponentItem />
    <MyComponentItem />
    <MyComponentItem />
  </div>
</template>

<script setup>
// MyComponent의 자식으로 사용할 컴포넌트를 가져온다.
import MyComponentItem from '@/components/MyComponentItem.vue'
</script>
```

이 구조에서는 `App.vue → MyComponent.vue → MyComponentItem.vue`로 이어지는 컴포넌트 트리가 만들어진다. 같은 컴포넌트를 여러 번 사용해도 각각 화면에 출력되므로, 반복되는 UI를 따로 컴포넌트로 분리하는 이유를 확인할 수 있다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 154811.png>)

컴포넌트 이름은 스타일 가이드를 따르는 것이 좋다. 보통 여러 단어로 구성된 PascalCase 이름을 사용하면 HTML 기본 태그와 충돌할 가능성을 줄이고, 파일 이름과 컴포넌트 이름의 관계도 명확해진다.

### 3.14 Virtual DOM: 실제 DOM 조작을 최소화하는 방식

Vue에서는 직접 DOM에 접근하는 방식을 권장하지 않는다. 예를 들어 JavaScript에서 자주 사용하는 `querySelector`, `createElement`, `addEventListener` 같은 방식으로 화면을 직접 조작하는 것은 Vue의 데이터 흐름과 충돌할 수 있다.

Vue가 직접 DOM 접근을 권장하지 않는 이유는 **성능과 코드의 예측 가능성** 때문이다. Vue는 데이터가 바뀌면 화면이 자동으로 갱신되도록 설계되어 있고, 이를 가능하게 하는 핵심 원리 중 하나가 Virtual DOM이다.

Virtual DOM은 실제 DOM의 모습을 메모리상에 가상으로 표현한 구조이다.

```text
Virtual DOM: 실제 DOM을 바로 수정하기 전에, 메모리상의 가상 DOM에서 변경 사항을 계산하는 방식
```

데이터가 변경되면 Vue는 실제 DOM을 바로 수정하지 않는다. 먼저 새로운 Virtual DOM을 만들고, 이전 Virtual DOM과 비교해서 어떤 부분이 바뀌었는지 계산한다. 이후 변경된 부분만 실제 DOM에 반영한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 155305.png>)

이 방식은 실제 DOM 조작을 최소화해 성능을 높인다. 실제 DOM을 자주 직접 수정하는 작업은 비용이 큰 편이기 때문이다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 155434.png>)

Virtual DOM 내부 렌더링 과정은 다음 흐름으로 이해할 수 있다.

1. 작성한 HTML 템플릿이 렌더 함수 코드로 변환된다.
2. 렌더 함수 코드를 바탕으로 Virtual DOM이 생성된다.
3. Virtual DOM을 기준으로 실제 DOM에 마운트된다.
4. 반응형 상태가 바뀔 때마다 새로운 Virtual DOM을 만들고 이전 것과 비교한다.
5. 바뀐 부분만 찾아 실제 DOM을 효율적으로 업데이트한다.

Virtual DOM 패턴의 장점은 세 가지로 정리할 수 있다.

| 장점 | 의미 |
|---|---|
| 효율성 | 실제 DOM 조작을 최소화하고 변경된 부분만 업데이트한다. |
| 반응성 | 데이터 변경을 감지해 UI를 자동으로 갱신한다. |
| 추상화 | 개발자는 DOM 조작보다 컴포넌트와 상태 관리에 집중할 수 있다. |

⚠️ 주의: Vue가 관리하는 화면을 직접 DOM 메서드로 수정하면 데이터와 화면이 서로 맞지 않는 상태가 생길 수 있다. 화면은 바뀐 것처럼 보이지만 Vue의 상태는 바뀌지 않았거나, 다음 렌더링 때 직접 수정한 내용이 사라질 수 있다.

### 3.15 직접 DOM 요소에 접근해야 할 때: ref와 onMounted

Vue에서도 특정 DOM 요소에 직접 접근해야 하는 경우는 있다. 예를 들어 input 요소에 포커스를 주거나, 외부 라이브러리와 연결해야 하는 경우가 그렇다. 이때는 `querySelector`를 쓰기보다 Vue의 `ref` 속성과 Lifecycle Hooks를 사용한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 162927.png>)

```vue
<template>
  <!-- template의 ref 이름과 script의 변수명이 일치해야 한다. -->
  <input ref="input">
</template>

<script setup>
// ref는 DOM 참조를 담을 때도 사용할 수 있다.
// onMounted는 컴포넌트가 화면에 마운트된 뒤 실행되는 훅이다.
import { ref, onMounted } from 'vue'

// 처음에는 아직 DOM이 연결되지 않았으므로 null로 둔다.
// 변수명 input은 template의 ref="input"과 일치해야 한다.
const input = ref(null)

onMounted(() => {
  // 컴포넌트가 마운트된 이후에는 input.value를 통해 실제 <input> 요소에 접근할 수 있다.
  console.log(input.value)
})
</script>
```

여기서 중요한 점은 DOM 요소가 처음부터 존재한다고 생각하면 안 된다는 것이다. 컴포넌트가 화면에 마운트되기 전에는 실제 DOM 요소를 참조할 수 없기 때문에 `onMounted` 안에서 접근해야 한다.

📌 핵심: Vue에서 DOM 접근이 필요할 때는 직접 선택자를 찾기보다, `ref`와 `onMounted`를 사용해 Vue의 렌더링 흐름 안에서 접근한다.

### 3.16 Composition API와 Options API

Vue 컴포넌트를 작성하는 방식에는 크게 **Composition API**와 **Options API**가 있다.

Composition API는 Vue 3에서 권장되는 방식이다. `ref`, `onMounted` 같은 API 함수를 import해서 컴포넌트의 로직을 직접 구성한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 163045.png>)

```vue
<template>
  <!-- 버튼을 클릭하면 increment 함수가 실행되고 count 값이 증가한다. -->
  <button @click="increment">{{ count }}</button>
</template>

<script setup>
import { ref, onMounted } from 'vue'

// 반응형 숫자 상태를 만든다.
const count = ref(0)

// ref로 만든 값은 script 안에서 .value로 접근한다.
function increment() {
  count.value++
}

onMounted(() => {
  console.log(`숫자 세기의 초기값은 ${count.value}`)
})
</script>
```

Options API는 Vue 2에서 많이 사용되던 방식이며, Vue 3에서도 지원된다. `data`, `methods`, `mounted` 같은 옵션 객체를 사용해 컴포넌트 로직을 나누어 작성한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 163136.png>)

```vue
<template>
  <!-- methods에 정의한 increment를 클릭 이벤트에 연결한다. -->
  <button @click="increment">{{ count }}</button>
</template>

<script>
export default {
  // data는 컴포넌트가 사용할 상태를 반환한다.
  data() {
    return { count: 0 }
  },

  // methods에는 컴포넌트에서 사용할 함수를 정의한다.
  methods: {
    increment() {
      this.count++
    }
  },

  // mounted는 컴포넌트가 마운트된 뒤 실행된다.
  mounted() {
    console.log(`숫자 세기의 초기값은 ${this.count}`)
  }
}
</script>
```

두 방식의 권장 사용 상황은 다음과 같이 정리할 수 있다.

| 작성 방식 | 권장 상황 |
|---|---|
| Composition API + SFC | 규모가 있는 앱 전체를 구축하는 경우 |
| Options API | 빌드 도구를 사용하지 않거나 복잡성이 낮은 프로젝트 |

⚠️ 주의: Composition API에서 `ref`로 만든 값은 JavaScript 코드 안에서는 `.value`로 접근해야 한다. 다만 template 안에서는 Vue가 자동으로 풀어주기 때문에 `{{ count }}`처럼 사용할 수 있다.

### 3.17 Single Root Element: 컴포넌트의 최상위 구조를 명확히 하기

모든 컴포넌트에서는 최상단 HTML 요소를 작성하는 것이 권장된다. 이를 **Single Root Element**라고 한다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 163328.png>)

좋지 않은 예시는 최상위에 여러 요소가 나란히 있는 구조이다.

```vue
<template>
  <h1>제목</h1>
  <p>내용</p>
</template>
```

권장되는 구조는 하나의 최상위 요소로 감싸는 방식이다.

```vue
<template>
  <div>
    <h1>제목</h1>
    <p>내용</p>
  </div>
</template>
```

Vue 3에서는 여러 루트 노드를 지원하지만, 가독성, 스타일링, 컴포넌트 구조의 명확성을 위해 하나의 최상위 요소로 감싸는 방식이 여전히 권장된다. 특히 부모 컴포넌트에서 자식 컴포넌트의 레이아웃을 제어할 때 구조가 분명해진다.

### 3.18 CSS scoped와 부모-자식 스타일 전파

`<style scoped>`를 사용하면 해당 컴포넌트 내부의 스타일이 현재 컴포넌트 내부 요소에게만 적용되도록 범위를 제한할 수 있다. 이를 통해 스타일이 컴포넌트 밖으로 유출되거나, 다른 컴포넌트의 스타일이 현재 컴포넌트를 침범하는 것을 줄일 수 있다.

`scoped`를 사용하지 않은 `<style>`은 전역 스타일처럼 동작할 수 있다. 예를 들어 어떤 컴포넌트에서 `div { color: red; }`를 작성하면, 다른 컴포넌트의 `div`에도 영향을 줄 수 있다.

부모-자식 관계에서는 한 가지 예외가 있다. 일반적으로 부모 컴포넌트의 scoped 스타일은 자식 컴포넌트 내부에 영향을 주지 않지만, 자식 컴포넌트의 **최상위 요소(root element)**에는 부모의 scoped 스타일이 영향을 줄 수 있다.

![alt text](<../assets/images/06_01_SFC/화면 캡처 2026-06-01 163925.png>)

```vue
<!-- App.vue -->

<template>
  <h1>App.vue</h1>
  <MyComponent />
</template>

<style scoped>
/* 부모 컴포넌트의 scoped 스타일 */
div {
  color: red;
}
</style>
```

```vue
<!-- MyComponent.vue -->

<template>
  <!-- 자식 컴포넌트의 최상위 요소이므로 부모 scoped 스타일의 영향을 받을 수 있다. -->
  <div>
    <h2>MyComponent</h2>
  </div>
</template>
```

이런 예외가 있는 이유는 부모가 자식 컴포넌트를 배치할 때 자식의 외곽 박스, 마진, 크기 같은 레이아웃을 제어할 필요가 있기 때문이다.

⚠️ 주의: `scoped`가 있다고 해서 부모와 자식의 스타일 영향이 완전히 차단된다고만 이해하면 안 된다. 자식 컴포넌트의 root element는 부모 레이아웃의 영향을 받을 수 있다.

### 3.19 Scaffolding: 프로젝트의 초기 뼈대 만들기

스캐폴딩은 새로운 프로젝트나 모듈을 시작할 때 초기 구조와 코드를 자동으로 생성하는 과정이다.

```text
Scaffolding: 새 프로젝트를 시작할 때 필요한 파일과 폴더 구조를 자동 생성하는 과정
```

건물을 지을 때 임시 뼈대를 세우는 것처럼, Vue 프로젝트에서도 `npm create vue@latest` 명령을 실행하면 필요한 기본 파일과 폴더 구조가 자동으로 생성된다. 덕분에 개발자는 초기 설정에 시간을 많이 쓰지 않고, 실제 기능 구현에 더 빨리 들어갈 수 있다.

관심사항의 분리는 단순히 파일 유형을 HTML, CSS, JS로 나누는 것과 같지 않다. 프론트엔드 앱이 복잡해질수록 파일 유형 기준의 분리만으로는 충분하지 않다. Vue SFC는 하나의 컴포넌트라는 관심사를 기준으로 화면, 로직, 스타일을 함께 관리한다는 점에서 현대적인 프론트엔드 개발 방식과 잘 맞는다.

### 3.20 패키지 관리 주의사항

패키지 관리는 Vue 프로젝트를 실행하고 협업할 때 자주 문제가 생기는 부분이다. 강의에서 다룬 주의사항은 다음과 같다.

1. `npm install`은 항상 프로젝트 루트 디렉토리에서 실행한다.  
   루트 디렉토리는 `package.json`이 있는 폴더이다.

2. `node_modules` 폴더는 직접 수정하거나 Git으로 관리하지 않는다.  
   필요한 경우 `npm install`로 다시 생성할 수 있다.

3. `package.json`과 `package-lock.json`은 직접 편집하기보다 npm 명령어로 관리한다.  
   패키지를 추가할 때는 `npm install 패키지명`을 사용하면 관련 파일이 자동으로 업데이트된다.

4. 패키지 버전 충돌이나 이상 동작이 의심되면 재설치를 고려한다.  
   `node_modules`를 삭제한 뒤 다시 `npm install`을 실행하면 설치 상태를 새로 맞출 수 있다.

⚠️ 주의: 에러가 났을 때 코드만 의심하기보다, 현재 터미널 위치가 프로젝트 루트인지, 개발 서버를 재시작해야 하는 상황인지, 패키지 설치가 끝났는지도 함께 확인해야 한다.

## 4. 적용 관점에서 다시 보기

이번 내용은 Vue 프로젝트를 처음 만들고 컴포넌트를 나누는 모든 상황에서 계속 반복된다. 문제를 풀거나 프로젝트를 구현할 때 다음 신호를 보면 이번 강의 내용을 떠올리면 된다.

먼저 `.vue` 파일을 작성해야 한다면, `template`, `script setup`, `style scoped`의 역할을 나누어 생각한다. 화면 구조는 template에, 상태와 함수는 script에, 현재 컴포넌트에 한정하고 싶은 CSS는 scoped style에 둔다.

컴포넌트를 분리해야 하는 상황에서는 “이 UI가 반복되는가?”, “이 영역이 독립적인 역할을 가지는가?”, “다른 화면에서도 재사용될 수 있는가?”를 기준으로 판단한다. 조건이 맞다면 `components` 폴더에 새 `.vue` 파일을 만들고, 부모 컴포넌트에서 import한 뒤 template에서 태그처럼 사용한다.

프로젝트 실행이 되지 않을 때는 코드보다 환경을 먼저 확인하는 것이 좋다. `npm install`을 프로젝트 루트에서 실행했는지, `package.json`이 있는 위치인지, `npm run dev`로 개발 서버를 다시 켰는지 확인한다. 특히 경로 별칭이나 설정 파일을 바꾼 뒤에는 서버 재시작이 필요할 수 있다.

DOM을 직접 조작하고 싶어지는 상황에서는 Vue의 데이터 흐름을 먼저 떠올려야 한다. 일반적인 화면 변화는 반응형 상태와 template로 처리하고, 정말 DOM 요소 참조가 필요할 때만 `ref`와 `onMounted`를 사용한다.

마지막으로 스타일 문제는 `scoped` 여부를 확인한다. 특정 컴포넌트에만 스타일을 적용하고 싶다면 `<style scoped>`를 사용하고, 부모 컴포넌트의 스타일이 자식의 root element에 영향을 줄 수 있다는 예외도 함께 기억해야 한다.

## 5. 배운 점 / 확장 포인트

### 1. 이번 강의 이전에 몰랐던 것 또는 새로 이해된 것

SFC는 HTML, CSS, JavaScript를 단순히 한 파일에 섞어 쓰는 방식이 아니라, 하나의 컴포넌트라는 관심사를 중심으로 관련 코드를 묶는 방식이라는 점이 중요하다. 또한 `package.json`, `package-lock.json`, `node_modules`는 모두 패키지와 관련되어 있지만 각각 설계도, 정확한 설치 내역, 실제 설치 파일이라는 다른 역할을 가진다.

### 2. 앞으로 이어지는 연결점

이번 강의에서 배운 컴포넌트 등록 방식은 이후 props, emit, slot, router, 상태 관리로 이어진다. 부모-자식 컴포넌트 구조를 이해해야 데이터를 아래로 전달하거나 이벤트를 위로 올리는 흐름도 자연스럽게 이해할 수 있다.

### 3. 더 파볼 만한 주제

심화해서 볼 만한 주제로는 Vue의 반응형 시스템, `ref`와 `reactive`의 차이, 컴포넌트 간 props/emit 통신, Vite alias 설정, scoped CSS의 내부 동작 방식, Virtual DOM의 diff 알고리즘이 있다.

## 6. 요약 정리

📌 핵심

- 컴포넌트는 웹 화면을 구성하는 재사용 가능한 UI 블록이다.
- SFC는 하나의 `.vue` 파일 안에 `template`, `script`, `style`을 함께 작성하는 Vue 컴포넌트 파일 형식이다.
- Vue SFC는 브라우저가 바로 실행하는 파일이 아니므로 Vite 같은 빌드 도구가 필요하다.
- NPM은 패키지를 설치하고 관리하며, `package.json`, `package-lock.json`, `node_modules`가 함께 패키지 환경을 구성한다.
- `App.vue`는 Root 컴포넌트이고, `main.js`는 Vue 앱을 만들어 `index.html`의 `#app`에 마운트한다.
- 자식 컴포넌트는 부모 컴포넌트에서 import한 뒤 template에서 태그처럼 사용한다.
- Vue는 Virtual DOM을 통해 실제 DOM 조작을 최소화하고 변경된 부분만 효율적으로 업데이트한다.
- 직접 DOM 접근이 필요한 경우에는 `querySelector`보다 `ref`와 `onMounted`를 사용하는 것이 Vue의 흐름에 맞다.
- `style scoped`는 스타일 범위를 현재 컴포넌트로 제한하지만, 자식 컴포넌트의 root element에는 부모 스타일이 영향을 줄 수 있다.

🧠 기억할 것

Vue 프로젝트를 이해할 때는 “파일이 어디에 있는가”보다 “이 파일이 어떤 역할을 하는가”를 먼저 봐야 한다. `App.vue`, `main.js`, `index.html`, `components` 폴더의 역할이 연결되면 컴포넌트 구조와 실행 흐름이 훨씬 명확해진다.
