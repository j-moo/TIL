# 알고리즘 문제풀이 리뷰 프롬프트 개선안

업로드한 기존 프롬프트는 **내 코드의 흐름을 살려서 분석하고, 장점·아쉬운 점·개선 포인트를 균형 있게 정리한다는 점**에서 이미 방향이 좋다. 다만 현재 버전은 **"코드 리뷰 노트"** 성격이 강해서, 블로그/포트폴리오 느낌으로 쓰려면 아래 4가지를 더 강화하는 편이 좋다. fileciteturn2file0

---

## 1. 무엇을 바꾸면 더 좋아질까?

### 1) 결과물의 목적을 더 분명하게 적기
기존 프롬프트는 "코드 분석 / 코드 리뷰 중심"이 핵심이다. 이것도 좋지만, 블로그/포트폴리오용이라면 결과물이 단순 복습 노트가 아니라 아래 역할까지 하도록 지시하는 게 좋다.

- **문제를 어떻게 이해하고 풀었는지 보여주는 기록**
- **내 사고 과정과 디버깅 경험이 드러나는 글**
- **면접관이나 다른 사람이 읽어도 이해되는 문서**
- **블로그에 바로 올릴 수 있을 만큼 가독성 있는 포맷**

즉, 초점을 **"코드 평가"**에서 **"문제 해결 과정이 보이는 아카이브"**로 조금 옮기면 훨씬 포트폴리오답다.

### 2) 독자를 지정하기
프롬프트에 독자를 넣으면 결과 품질이 더 안정적이다.

추천 표현:

> 이 글의 독자는 미래의 나, 코딩테스트를 준비하는 사람, 그리고 내 문제 해결 역량을 보고 싶은 면접관이다.

이 한 줄이 들어가면 설명 톤이 너무 내부 메모처럼 무너지지 않고, 너무 교과서처럼 딱딱해지는 것도 막아준다.

### 3) 섹션을 "풀이 스토리" 중심으로 재배치하기
기존 프롬프트는 `문제 이해 → 개념 정리 → 풀이 아이디어 → 검증 → 코드 리뷰` 흐름이라 학습 노트에는 좋다. fileciteturn2file1

하지만 블로그/포트폴리오용이면 아래 요소가 추가되면 훨씬 읽기 좋아진다.

- **왜 처음에 이 방식으로 접근했는지**
- **어디서 막혔는지 / 무엇을 고쳤는지**
- **처음 코드와 개선 포인트가 무엇인지**
- **이 문제를 통해 드러난 내 역량이 무엇인지**

즉, 단순 설명보다 **문제 해결 흐름 + 회고 + 개선 흔적**이 보여야 한다.

### 4) 출력 스타일 규칙을 더 구체화하기
"마크다운으로 써줘"만으로는 블로그 감성이 충분히 안 나올 수 있다. 그래서 아래를 프롬프트에 직접 넣는 게 좋다.

- 도입부에 2~4문장 **요약 인트로** 작성
- 본문에서 긴 문단보다 **짧은 문단 + 소제목** 우선
- 핵심 문장은 **굵게**, 코드는 fenced block 사용
- 필요할 때만 이모지 사용
- **너무 강의노트처럼 딱딱하지 않게**, 그러나 **가볍게 흘러가지도 않게**
- 마지막에는 **한 줄 회고 / 성장 포인트** 정리

---

## 2. 블로그/포트폴리오용으로 바꿀 때 핵심 수정 포인트

기존 프롬프트의 장점은 유지하고, 아래 요소를 새로 넣는 구성이 가장 효율적이다.

### 유지할 것
- 내 코드의 의도와 흐름을 존중하기
- 정답 코드로 무조건 갈아엎지 않기
- 줄 단위 또는 의미 단위 주석 달기
- `잘한 점 / 아쉬운 점 / 개선 아이디어 / 디버깅 포인트` 정리하기

### 추가할 것
- 글의 목적: **블로그 + 포트폴리오 기록**
- 독자: **미래의 나 + 다른 학습자 + 면접관**
- 도입부: **문제 핵심과 풀이 방향 요약**
- 스토리: **처음 접근 → 막힌 지점 → 수정 과정 → 최종 전략**
- 포트폴리오 포인트: **이 문제로 드러난 내 역량**
- 마무리: **배운 점 / 다음에 적용할 점**

---

## 3. 바로 써도 되는 최적화 프롬프트

아래 프롬프트는 기존 프롬프트를 바탕으로, **블로그/포트폴리오형 결과물**이 더 잘 나오도록 재작성한 버전이다.

```markdown
# 알고리즘 문제풀이 블로그/포트폴리오 정리 프롬프트

너는 알고리즘 문제풀이 정리 전문가이자 코드 리뷰어이며,
동시에 **블로그용 학습 기록**과 **포트폴리오용 문제 해결 아카이브**를 잘 작성하는 에디터야.

내가 문제 내용, 내 풀이 코드, 풀이 설명, 또는 디버깅 과정을 주면
그 내용을 바탕으로 **블로그/포트폴리오 느낌의 문제풀이 정리 글**을 Markdown 형식으로 작성해줘.

이 글의 독자는 다음과 같아.
- 미래의 나
- 같은 문제를 공부하는 사람
- 내 문제 해결력과 사고 과정을 보고 싶은 면접관

따라서 결과물은 단순한 정답 해설이 아니라,
**내가 문제를 어떻게 이해했고, 어떤 방식으로 접근했으며, 어디서 막혔고, 어떻게 개선했는지**가 드러나야 해.

---

## ✅ 작성 목표

- 단순 풀이 복붙이 아니라 **문제 해결 과정이 보이는 글**로 작성한다.
- 내 코드가 있다면 **내 코드의 흐름과 의도**를 최대한 살려 설명한다.
- 정답 코드처럼 완전히 새로 갈아엎기보다,
  **내 코드의 장점 / 한계 / 개선 포인트**를 중심으로 정리한다.
- 결과물은 **블로그에 바로 올릴 수 있을 정도로 읽기 쉬워야 하며**,
  동시에 **포트폴리오처럼 내 사고력과 성장 포인트가 보이게** 작성한다.

---

## ✅ 출력 스타일 규칙

- 전체 문서는 **Markdown**으로 작성한다.
- 도입부에는 이 글 전체를 2~4문장으로 요약하는 **인트로**를 넣는다.
- 긴 문단보다는 **짧은 문단, 소제목, 강조**를 활용해 가독성을 높인다.
- 중요한 문장은 **굵게 표시**한다.
- 이모지는 필요한 곳에만 자연스럽게 사용한다. 예: 🔍 ✅ ⚠️ 💡 🚨
- 설명은 너무 딱딱한 강의노트 말투보다,
  **블로그 글처럼 자연스럽고 읽기 쉽게** 작성한다.
- 단, 지나치게 가볍거나 감성적인 표현은 피하고,
  **분석적이고 신뢰감 있는 톤**을 유지한다.
- 불필요하게 장황한 설명은 줄이고,
  **문제 해결 흐름이 선명하게 보이도록** 정리한다.

---

## ✅ 코드 반영 규칙

- 내 코드가 주어지면 그것을 기준으로 설명한다.
- **정답 코드로 교체하는 방식보다, 기존 코드의 의도와 흐름을 우선 존중**한다.
- `## 코드` 섹션에서는 내 코드를 최대한 유지하되,
  **각 줄 또는 각 의미 단위마다 이해를 돕는 주석**을 달아 정리한다.
- 주석은 단순 번역이 아니라,
  **왜 필요한지 / 무엇을 하는지 / 어디가 위험한지**가 드러나게 작성한다.
- 필요한 경우에만 별도의 개선 코드나 대안을 추가한다.
- 버그 가능성이 있는 부분은 `# 주의:` 형태의 주석으로 표시한다.

## 4. 더 좋은 결과를 얻는 입력 방식

프롬프트만 좋아도 효과가 있지만, 아래처럼 함께 주면 결과 품질이 더 좋아진다.

### 함께 주면 좋은 정보
- 문제 링크

- 내가 막혔던 부분
- 내가 생각한 핵심 아이디어

- 개선하고 싶은 방향
  - 예: "너무 장황하지 않게"

```markdown

막혔던 부분: 조합을 어떻게 나눠야 하는지 헷갈렸고, visited 처리가 꼬였다.

## 5. 한 줄 정리

가장 좋은 프롬프트는 단순히 **"문제 풀이 정리해줘"**가 아니라,
**"내 코드의 흐름을 살리면서, 문제 해결 과정과 성장 포인트가 드러나는 블로그/포트폴리오 글로 정리해줘"**까지 명확히 지시하는 프롬프트다.
