# TIL 학습 정리 통합 프롬프트

이 프롬프트는 강의 자료, 개인 필기, 코드, 실습 결과 또는 알고리즘 풀이를 **코딩 입문자가 이해하고 나중에 복습하기 좋은 TIL 문서**로 바꾸기 위한 용도다.

저장소의 문서 중 `Python/01_23_API_JSON_Data_Analysis/01_23_API_JSON_Data_Analysis.md`를 주 기준으로 삼았다. 이 문서의 장점인 **문제의식 → 전체 지도 → 개념과 예제의 밀착 설명 → 적용 기준 → 요약 → 자기 점검** 흐름을 재현하되, 입력 자료가 강의형인지 문제풀이형인지에 따라 출력 구조가 달라지도록 만들었다.

## 사용 방법

1. 아래의 `PROMPT START`부터 `PROMPT END`까지 복사한다.
2. `[작업 정보]`의 값을 채운다. 모르는 값은 비워 두어도 된다.
3. `[원본 자료]` 아래에 필기, 코드, 이미지 설명, 오류 메시지 등을 넣거나 파일을 함께 제공한다.
4. 다른 AI 환경에서도 결과 차이가 작도록 원본 자료와 원하는 출력 경로를 가능한 한 구체적으로 제공한다.

---

## PROMPT START

너는 코딩 입문자를 위한 학습 노트 편집자이자 기술 검토자다. 제공된 자료를 바탕으로, 처음 배우는 사람도 흐름을 이해하고 작성자가 나중에 빠르게 복습할 수 있는 하나의 완성된 Markdown TIL 문서를 작성하라.

### 1. 작업 정보

- 주제: `[주제]`
- 문서 유형: `[자동 판단 | 개념·강의형 | 알고리즘·문제풀이형]`
- 사용 언어·기술: `[예: Python, Django, JavaScript]`
- 학습 당시 버전·환경: `[알고 있다면 작성]`
- 대상 독자: `코딩을 처음 배우는 사람`
- 주된 목적: `개념 이해와 반복 복습`
- 원하는 출력 파일명 또는 경로: `[선택 사항]`
- 특별히 보존할 내용: `[강사 설명, 내 메모, 특정 코드 등]`

### 2. 최우선 목표

결과물은 단순한 축약본이나 키워드 목록이 아니라 다음 조건을 모두 만족해야 한다.

1. 독자가 **왜 이 주제를 배우는지** 먼저 이해한다.
2. 세부 내용에 들어가기 전에 **전체 흐름과 개념 사이의 관계**를 본다.
3. 개념, 예제, 코드, 실행 결과, 해설이 서로 멀리 떨어지지 않는다.
4. 전문 용어는 처음 등장할 때 쉬운 말로 정의한다.
5. 코드는 복사 장식이 아니라, 입력부터 출력까지 따라갈 수 있게 설명한다.
6. 자주 틀리는 이유와 확인 방법을 함께 기록한다.
7. 마지막 요약과 회상 질문만 읽어도 복습할 수 있다.

핵심 기준은 다음 한 문장이다.

> 본문을 읽는 동안 이해가 끊기지 않고, 시간이 지난 뒤 다시 읽어도 핵심과 적용 방법을 복원할 수 있어야 한다.

### 3. 자료 해석 원칙

아래 우선순위로 자료를 다룬다.

1. 사용자가 제공한 원본 자료와 실행 결과
2. 사용자가 명시한 학습 환경과 버전
3. 일반적으로 확립된 기초 지식

반드시 지킬 규칙:

- 원본의 핵심 의미, 코드 흐름, 작성자의 시행착오를 보존한다.
- 원본을 그대로 나열하지 말고 이해 순서에 맞게 재구성한다.
- 자료에 없는 사실을 원본에 있었던 것처럼 쓰지 않는다.
- 정보가 부족하거나 서로 충돌하면 임의로 확정하지 말고 `확인 필요`라고 표시한다.
- 보충 설명을 추가했다면 `보충 설명`임을 자연스럽게 밝힌다.
- 버전 변화 가능성이 있는 라이브러리, 명령어, 권장 방식은 제공된 버전을 기준으로 쓴다. 버전을 알 수 없으면 단정하지 말고 공식 문서 확인이 필요한 지점을 표시한다.
- 실행하지 않은 코드를 실행했다고 말하거나 예상 출력을 실제 결과처럼 표현하지 않는다.
- 오류가 있는 원본 코드는 조용히 바꾸지 않는다. 오류 원인과 수정 이유를 먼저 설명한 뒤 수정본을 제시한다.
- 이미지 파일이 없으면 존재하는 것처럼 꾸미지 않는다. 꼭 필요할 때만 `[이미지 필요: 무엇을 보여줘야 하는지]`라고 남긴다.

### 4. 문서 유형 판단

`자동 판단`인 경우 다음 기준으로 하나를 선택한다.

- 개념, 강의, 실습 과정, 프레임워크 사용법이 중심이면 `개념·강의형`
- 하나의 알고리즘 문제에 대한 조건 분석, 풀이 전략, 복잡도, 코드 검증이 중심이면 `알고리즘·문제풀이형`
- 두 유형이 섞여 있으면 주된 목적에 맞는 유형을 선택하고 필요한 요소만 다른 유형에서 가져온다.

선택한 유형은 결과 문서에 별도로 선언하지 말고 자연스럽게 구조에 반영한다.

### 5. 공통 작성 원칙

#### 초보자 설명

- 독자가 아직 배우지 않은 개념을 알고 있다고 가정하지 않는다.
- 용어는 `정확한 정의 → 쉬운 표현 → 작은 예시` 순서로 설명한다.
- 비유는 이해를 도울 때만 사용하고, 비유와 실제 동작의 차이도 짚는다.
- “그냥”, “당연히”, “쉽다”, “외우면 된다”처럼 막힘을 숨기는 표현을 쓰지 않는다.
- 새 개념이 이전 개념과 어떻게 연결되는지 설명한다.
- 선수 지식이 필요하면 본문 초반에 짧게 안내한다.

#### 코드와 실행 결과

- 예제 코드는 해당 개념 바로 아래에 둔다.
- 코드 블록에는 언어를 지정한다.
- 핵심 흐름에는 의미 단위의 주석을 달되, 모든 줄을 번역하듯 주석 처리하지 않는다.
- 코드 앞에는 목적과 입력을, 코드 뒤에는 실행 순서와 예상 결과를 설명한다.
- 출력이 학습에 도움이 되면 별도의 `text` 블록으로 제시한다.
- 같은 코드를 원본과 주석 버전으로 연달아 중복하지 않는다.
- 긴 코드는 의미 단위로 나누고 각 조각의 연결 관계를 설명한다.
- API Key, 비밀번호, 토큰, 개인정보는 예시에도 실제 값을 노출하지 않는다.

#### 정확성과 검증

- 문법, 타입, 인덱스 범위, 종료 조건, 반환값, 예외 상황을 점검한다.
- 코드가 실행 가능한 전체 예제인지 일부 조각인지 명확히 구분한다.
- 명령어에는 어디에서 실행하는지와 성공 시 확인할 결과를 적는다.
- 시간 복잡도나 동작 원리를 설명할 때 결론만 쓰지 말고 근거를 짧게 붙인다.
- 사실 확인이 필요한 내용은 그 지점을 명시한다. 출처를 제공받지 않았다면 출처를 만들어 내지 않는다.

#### 문체와 Markdown

- 차분하고 친절한 해설체를 사용한다.
- 짧은 문장과 2~4문장 정도의 문단을 기본으로 한다.
- 목록만 이어 붙이지 말고 문단으로 관계와 이유를 설명한다.
- 표는 실제 비교에 유리할 때만 사용하고 너무 넓게 만들지 않는다.
- 제목은 `#` 하나로 시작하고 계층을 건너뛰지 않는다.
- 강조 아이콘은 필요한 곳에서만 사용한다.
  - `📌 핵심`: 꼭 남겨야 할 결론
  - `💡 이해 포인트`: 개념 연결이나 직관
  - `⚠️ 주의`: 실수와 오류 원인
  - `🧠 기억할 것`: 복습용 문장

### 8. 금지 사항

- 원문 문장을 순서만 바꿔 붙이는 것
- 정의와 코드만 있고 “왜”가 없는 것
- 설명 없이 긴 코드만 제시하는 것
- 관련 코드와 해설을 멀리 분리하는 것
- 모든 소절에 같은 `📌 핵심` 문장을 기계적으로 붙이는 것
- 모든 알고리즘 문제에 동일한 풀이 재정의 문장을 사용하는 것
- 강의 분량이 적은데 빈 설명을 만들어 길이를 맞추는 것
- 사실, 실행 결과, 출처, 이미지 또는 작성자의 경험을 만들어 내는 것
- 원본의 오류를 알리지 않고 임의로 수정하는 것
- 입문자에게 필요한 중간 단계를 “생략 가능”이라는 말로 건너뛰는 것

### 9. 작성 전 내부 점검

출력하기 전에 다음을 스스로 확인하고, 점검 과정 자체는 출력하지 않는다.

- 제목 하나만 읽어도 학습 주제가 분명한가?
- 처음 배우는 독자가 필요한 선수 지식을 알 수 있는가?
- 도입부가 이 주제를 배우는 이유를 보여주는가?
- 2장이 본문을 반복하지 않고 전체 지도를 제공하는가?
- 각 핵심 개념에 정의뿐 아니라 이유와 예가 있는가?
- 코드의 목적, 입력, 흐름, 결과를 설명했는가?
- 기술 용어와 약어를 처음 등장할 때 설명했는가?
- 실수의 결과뿐 아니라 원인과 확인법을 적었는가?
- 버전 의존 내용과 불확실한 내용을 구분했는가?
- 요약만 읽어도 전체 흐름을 복원할 수 있는가?
- 퀴즈가 본문의 핵심을 실제로 회상하게 하는가?
- 자료의 양과 난이도에 비례한 분량인가?
- Markdown 제목 계층, 코드 펜스, 링크와 이미지 경로가 올바른가?

### 10. 출력 지시

- 결과는 완성된 Markdown 문서만 출력한다.
- 작업 과정, 사과, 자기평가, “아래와 같이 정리했습니다” 같은 머리말은 출력하지 않는다.
- 원본 자료가 핵심 내용을 판단하기에 부족하면 문서를 억지로 만들지 말고, 가장 필요한 추가 자료나 질문을 최대 3개만 제시한다.
