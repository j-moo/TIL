# 멱등성 키: 재시도된 주문을 한 번만 처리하기

- 🎯 글의 목표: 응답 유실과 클라이언트 재시도 상황에서 같은 주문·재고 차감이 중복 실행되지 않도록 HTTP 계약과 DB 저장 구조를 설계한다.
- 🧩 핵심 키워드: Idempotency, Idempotency-Key, Request Fingerprint, Unique Constraint, Response Replay, `ON CONFLICT`, Retry Window
- ⭐ 중요도: ★★★★★ — 서버가 성공했어도 응답이 사라질 수 있으므로, 재시도를 막는 대신 같은 논리 요청을 안전하게 다시 받을 수 있어야 한다.
- 📝 한눈에 보는 내용: 사용자 범위·작업 종류·멱등성 키를 유일하게 저장하고 payload fingerprint를 비교한다. 최초 요청의 주문·재고·응답 기록을 한 트랜잭션으로 확정하며, 같은 요청은 저장된 응답을 재생한다.
- 🧱 선수 지식: HTTP POST·상태 코드, Spring 트랜잭션, JPA Repository, DB 유일 제약, 조건부 재고 UPDATE
- 🔗 이전 노트: [비관적 잠금과 조건부 UPDATE](../23_09_21_Pessimistic_Locking_and_Atomic_Update/09_21_Pessimistic_Locking_and_Atomic_Update.md)

> 정리 기준일: 2026-09-22. Java 21·Spring Boot 4.1·Spring Data JPA 4.1 계열과 PostgreSQL 17을 기준으로 작성했다. `Idempotency-Key` 이름과 오류 예시는 2025년 10월의 IETF draft-07을 참고했지만, 이 문서는 2026년 4월 만료된 **Internet-Draft이며 RFC 표준이 아니다**. 따라서 아래 plain UUID 헤더 형식과 보관 기간은 이 학습 API가 별도로 정한 계약이다. TIL 저장소에는 실행 애플리케이션과 PostgreSQL이 없어 Java 통합 테스트는 실행하지 않았으며 결과는 예상이다.

## 1. 들어가며: timeout은 실패를 뜻하지 않는다

클라이언트가 주문 생성 요청을 보낸 뒤 응답을 받기 전에 연결이 끊겼다고 하자.

```text
클라이언트 ── POST /orders ──▶ 서버
                              ├─ 재고 1개 차감 성공
                              ├─ 주문 생성 성공
                              └─ DB commit 성공
클라이언트 ◀──── 응답 유실 ──── X
```

클라이언트가 아는 것은 “응답을 받지 못했다”뿐이다. 서버가 요청을 받지 못했는지, 처리 중인지, 이미 commit했는지 구분할 수 없다. 같은 POST를 다시 보내면 두 번째 주문과 두 번째 재고 차감이 생길 수 있다.

RFC 9110은 같은 요청을 여러 번 적용해도 의도한 서버 효과가 한 번 적용한 것과 같은 성질을 **멱등성(idempotency)**이라고 설명한다. GET·PUT·DELETE 등은 메서드 의미가 멱등적이지만, 일반적인 POST는 그렇지 않다. 비멱등 요청을 자동 재시도하려면 애플리케이션이 같은 논리 요청임을 식별하는 수단이 필요하다.

멱등성 키는 클라이언트가 한 번의 논리 작업에 만든 식별자다. 전송을 다시 시도할 때 새 키를 만들지 않고 같은 키를 보낸다.

```http
POST /orders HTTP/1.1
Content-Type: application/json
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324

{"productId":42,"quantity":1}
```

📌 멱등성 키의 목적은 요청을 다시 보내지 못하게 하는 것이 아니다. **같은 논리 요청을 다시 보내도 업무 효과를 반복하지 않게 하는 것**이다.

## 2. 전체 흐름부터 보기

```text
인증된 사용자 ID + 작업 이름 + Idempotency-Key + 요청 fingerprint
  → DB 유일 제약으로 이 키의 최초 처리 권한 획득
  → 같은 트랜잭션에서 재고 차감·주문 생성
  → HTTP status·응답 body를 멱등성 레코드에 저장
  → commit

같은 키 재시도
  → payload fingerprint가 같음
  → 주문을 다시 만들지 않음
  → 저장한 status·응답 body 재생

같은 키 + 다른 payload
  → 키 오사용으로 거부
```

| 상황 | 서버 동작 | 이 노트의 응답 계약 |
| --- | --- | --- |
| 키 없음·형식 오류 | 업무 시작 전 거부 | 400 Bad Request |
| 처음 보는 키 | 주문·차감·응답 저장 | 201 Created |
| 같은 키·같은 payload·완료됨 | 저장 응답 재생 | 최초와 같은 201 body |
| 같은 키·다른 payload | 키 재사용 거부 | 422 Unprocessable Content |
| 같은 키의 작업이 처리 중 | 기다림 또는 처리 중 알림 | 구현 정책에 따라 409 Conflict |

여기서 “같다”는 키 문자열만 같다는 뜻이 아니다. 공격자나 다른 사용자가 우연히 같은 키를 보내도 결과가 노출되지 않도록 사용자 범위와 작업 종류를 함께 묶는다. payload가 바뀌었는지는 fingerprint로 확인한다.

## 3. API 계약을 먼저 고정한다

### 3.1 키의 생성자와 범위

이 학습 API는 다음 계약을 사용한다.

- 클라이언트가 각 **논리 주문**마다 UUID를 하나 만든다.
- 네트워크 재시도에는 같은 UUID를 사용한다.
- 새 주문에는 새 UUID를 사용한다.
- 서버는 인증 정보에서 얻은 `clientId`, 작업 이름 `CREATE_ORDER`, UUID를 복합 범위로 사용한다.
- 키는 성공 후 24시간 보관한다는 예시 정책을 사용한다.

UUID는 충돌 가능성을 매우 낮추는 식별자이지 인증 토큰이 아니다. 키를 안다고 다른 사용자의 응답을 읽을 수 없어야 하며, 로그에도 사용자 정보·요청 body와 무분별하게 결합해 남기지 않는다. UUID 규격은 RFC 9562를 기준으로 확인한다.

IETF draft-07은 `Idempotency-Key`를 Structured Field 문자열로 제안하므로 예시에 따옴표가 있다. 현재 만료된 초안이고 실제 서비스 계약도 서로 다를 수 있다. 이 노트의 Spring 예제는 구현을 단순하게 하기 위해 **따옴표 없는 UUID 텍스트 한 개**를 받는다고 문서화한다. 이를 IETF 표준 준수라고 부르지 않는다.

### 3.2 fingerprint는 키를 payload에 묶는다

키만 저장하면 다음 두 요청이 같은 작업인지 판단할 수 없다.

```text
같은 키 + { productId: 42, quantity: 1 }
같은 키 + { productId: 99, quantity: 10 }
```

두 번째 payload로 첫 번째 응답을 돌려주면 클라이언트 오류를 숨기고 보안 경계를 흐릴 수 있다. 서버는 업무에 영향을 주는 필드를 정규화한 뒤 SHA-256 같은 fingerprint를 저장한다.

원본 JSON 문자열을 그대로 hash하면 필드 순서·공백·숫자 표현만 달라도 다른 값이 될 수 있다. 반대로 일부 필드를 빠뜨리면 의미가 다른 요청을 같다고 판단할 수 있다. API 버전, 경로 매개변수, 통화·수량 등 업무 의미를 바꾸는 입력을 정해진 순서와 형식으로 포함한다.

## 4. DB 유일 제약이 최종 동시성 경계다

애플리케이션에서 `existsBy...()`를 먼저 호출하는 방식은 안전하지 않다.

```text
요청 A: 키가 없음 확인
요청 B: 키가 없음 확인
요청 A: 주문 생성
요청 B: 주문 생성
```

두 확인 사이를 보호하지 못하므로 DB의 유일 제약이 필요하다. 새 Flyway migration으로 다음 테이블을 추가한다.

```sql
-- 파일: src/main/resources/db/migration/V6__create_idempotency_records.sql
CREATE TABLE api_idempotency_records ( -- 재시도 판정과 완료 응답을 보관한다.
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, -- 내부 행 식별자다.
    client_id BIGINT NOT NULL, -- 인증된 사용자·가맹점 범위다.
    operation VARCHAR(80) NOT NULL, -- 같은 키를 구분할 API 작업 이름이다.
    idempotency_key UUID NOT NULL, -- 클라이언트가 재시도마다 유지할 UUID다.
    request_fingerprint CHAR(64) NOT NULL, -- SHA-256의 소문자 16진수 64자리다.
    state VARCHAR(20) NOT NULL, -- PROCESSING 또는 COMPLETED 상태다.
    http_status INTEGER, -- 완료 응답의 HTTP 상태다.
    response_body TEXT, -- 재생할 JSON body다. 민감 정보 저장 범위를 검토한다.
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP, -- 최초 요청 시각이다.
    completed_at TIMESTAMPTZ, -- 업무와 응답 저장을 마친 시각이다.
    expires_at TIMESTAMPTZ NOT NULL, -- 문서화된 중복 판정 보관 기한이다.

    CONSTRAINT uq_idempotency_scope -- 동시 최초 요청을 하나만 통과시킨다.
        UNIQUE (client_id, operation, idempotency_key),

    CONSTRAINT ck_idempotency_state -- 오타 상태가 저장되지 않게 한다.
        CHECK (state IN ('PROCESSING', 'COMPLETED')),

    CONSTRAINT ck_idempotency_completion -- 완료 상태는 재생 정보가 모두 있어야 한다.
        CHECK (
            (state = 'PROCESSING' AND http_status IS NULL AND response_body IS NULL AND completed_at IS NULL)
            OR
            (state = 'COMPLETED' AND http_status IS NOT NULL AND response_body IS NOT NULL AND completed_at IS NOT NULL)
        )
); -- 멱등성 레코드 테이블 정의를 끝낸다.

CREATE INDEX idx_idempotency_expiry -- 만료 정리 대상 탐색을 돕는다.
    ON api_idempotency_records (expires_at); -- 정리 batch의 조건 컬럼이다.
```

유일 범위에 client_id가 없으면 다른 사용자가 같은 UUID를 보냈을 때 응답이 섞일 수 있다. operation이 없으면 주문 생성 키가 환불 API의 키와 충돌할 수 있다. 실제 다중 tenant 서비스라면 tenant ID도 범위에 포함한다.

만료 행을 삭제하면 아주 늦은 재시도는 새 요청으로 처리될 수 있다. 보관 시간은 저장 공간만 보고 정하지 않고 클라이언트 최대 재시도 시간과 중복 주문의 업무 위험을 함께 본다. 결제·정산처럼 재실행 비용이 큰 작업은 별도의 영구 업무 키가 더 적합할 수도 있다.

## 5. 요청 모델과 fingerprint를 만든다

각 `public` 타입은 타입 이름과 같은 별도 `.java` 파일에 둔다.

```java
package com.example.orderstudy.order; // 주문 API DTO의 패키지다.

import jakarta.validation.constraints.Min; // 최소 수량을 검증한다.
import jakarta.validation.constraints.NotNull; // 상품 ID 누락을 막는다.

public record CreateOrderRequest(
        @NotNull // 주문 대상 상품은 필수다.
        Long productId,

        @Min(1) // 0·음수 주문을 업무 시작 전에 거부한다.
        int quantity
) {
}
```

```java
package com.example.orderstudy.order; // 주문 응답 DTO의 패키지다.

public record CreateOrderResponse(
        Long orderId, // 한 번만 생성된 주문의 식별자다.
        Long productId, // 주문한 상품의 식별자다.
        int quantity // 확정된 주문 수량이다.
) {
}
```

```java
package com.example.orderstudy.idempotency; // fingerprint 계산의 패키지다.

import java.nio.charset.StandardCharsets; // 같은 문자열을 UTF-8 byte로 고정한다.
import java.security.MessageDigest; // SHA-256 digest를 계산한다.
import java.security.NoSuchAlgorithmException; // 알고리즘 부재 예외를 처리한다.
import java.util.HexFormat; // byte 배열을 소문자 16진수로 바꾼다.

import org.springframework.stereotype.Component; // 재사용 가능한 Spring Bean으로 등록한다.

import com.example.orderstudy.order.CreateOrderRequest; // 주문 의미 필드를 읽는다.

@Component // Controller가 아니라 애플리케이션 계층에서 사용한다.
public class OrderRequestFingerprint {

    public String create(CreateOrderRequest request) { // 같은 의미의 요청에 같은 hash를 만든다.
        String canonical = "v1\n" // fingerprint 규칙 버전을 포함한다.
                + "productId=" + request.productId() + "\n" // 상품 ID를 고정된 이름·순서로 넣는다.
                + "quantity=" + request.quantity(); // 수량을 정수 문자열로 넣는다.

        try { // JDK가 제공하는 SHA-256 구현을 얻는다.
            MessageDigest digest = MessageDigest.getInstance("SHA-256"); // 256bit hash 알고리즘을 선택한다.
            byte[] hashed = digest.digest(canonical.getBytes(StandardCharsets.UTF_8)); // 정규 문자열을 hash한다.
            return HexFormat.of().formatHex(hashed); // DB CHAR(64)에 저장할 소문자 16진수다.
        } catch (NoSuchAlgorithmException exception) { // 표준 JDK에서 발생하면 환경 구성 오류다.
            throw new IllegalStateException("SHA-256 is not available", exception); // 업무 실패로 숨기지 않는다.
        }
    }
}
```

`v1`은 fingerprint 규칙이 바뀌었을 때의 구분값이다. API에 가격·옵션·배송지가 추가되어 주문 의미가 바뀌면 어떤 필드를 포함할지 함께 버전 관리한다. hash는 요청 내용을 숨기는 암호화 저장소가 아니므로 민감 입력 자체의 수집·로그 정책도 따로 지킨다.

## 6. 최초 처리 권한을 원자적으로 획득한다

### 6.1 상태 Entity

```java
package com.example.orderstudy.idempotency; // 멱등성 영속성 모델의 패키지다.

import java.time.OffsetDateTime; // UTC offset이 있는 완료·만료 시각을 표현한다.
import java.util.UUID; // API가 허용한 UUID 키 타입이다.

import jakarta.persistence.Column; // DB 컬럼과 필드를 연결한다.
import jakarta.persistence.Entity; // JPA Entity임을 표시한다.
import jakarta.persistence.EnumType; // 상태를 문자열로 저장하기 위한 상수다.
import jakarta.persistence.Enumerated; // enum 저장 방식을 지정한다.
import jakarta.persistence.GeneratedValue; // ID 생성을 DB에 맡긴다.
import jakarta.persistence.GenerationType; // IDENTITY 생성 전략을 사용한다.
import jakarta.persistence.Id; // 기본키 필드를 표시한다.
import jakarta.persistence.Table; // 테이블 이름을 지정한다.

@Entity // 완료 응답을 변경 감지로 기록한다.
@Table(name = "api_idempotency_records") // Flyway가 만든 테이블과 연결한다.
public class IdempotencyRecord {

    @Id // 내부 행 기본키다.
    @GeneratedValue(strategy = GenerationType.IDENTITY) // DB identity 값을 사용한다.
    private Long id;

    @Column(name = "client_id", nullable = false) // DB의 snake_case 이름까지 명시한다.
    private Long clientId;

    @Column(nullable = false, length = 80) // 작업 이름 길이를 DB와 맞춘다.
    private String operation;

    @Column(name = "idempotency_key", nullable = false) // PostgreSQL UUID 컬럼과 연결한다.
    private UUID idempotencyKey;

    @Column(name = "request_fingerprint", nullable = false, length = 64) // SHA-256 16진수 길이다.
    private String requestFingerprint;

    @Enumerated(EnumType.STRING) // enum 순서가 아니라 PROCESSING·COMPLETED 문자열을 저장한다.
    @Column(nullable = false, length = 20) // DB CHECK 제약과 맞춘다.
    private IdempotencyState state;

    @Column(name = "http_status") // PROCESSING 동안에는 null이다.
    private Integer httpStatus;

    @Column(name = "response_body", columnDefinition = "text") // 재생할 JSON 문자열의 길이를 고정하지 않는다.
    private String responseBody;

    @Column(name = "created_at", nullable = false) // 최초 claim 시각이다.
    private OffsetDateTime createdAt;

    @Column(name = "completed_at") // PROCESSING 동안에는 아직 완료되지 않았다.
    private OffsetDateTime completedAt;

    @Column(name = "expires_at", nullable = false) // 중복 판정 보관 기한이다.
    private OffsetDateTime expiresAt;

    protected IdempotencyRecord() { // JPA가 조회 결과를 만들 때 사용한다.
    }

    public void complete(int httpStatus, String responseBody, OffsetDateTime completedAt) {
        if (state != IdempotencyState.PROCESSING) { // 완료된 레코드를 다시 덮지 않는다.
            throw new IllegalStateException("Idempotency record is already completed"); // 상태 전이 오류다.
        }
        this.state = IdempotencyState.COMPLETED; // 먼저 완료 상태로 바꾼다.
        this.httpStatus = httpStatus; // 최초 HTTP 상태를 보관한다.
        this.responseBody = responseBody; // 최초 JSON body를 그대로 보관한다.
        this.completedAt = completedAt; // 완료 시각을 기록한다.
    }

    public String getRequestFingerprint() { // 재시도 payload 비교에 사용한다.
        return requestFingerprint; // 최초 fingerprint를 반환한다.
    }

    public IdempotencyState getState() { // 완료 여부를 판정한다.
        return state; // 현재 상태를 반환한다.
    }

    public int getHttpStatus() { // 완료 응답의 상태를 읽는다.
        return httpStatus; // COMPLETED에서만 호출한다.
    }

    public String getResponseBody() { // 저장된 JSON을 재생한다.
        return responseBody; // COMPLETED에서만 null이 아니다.
    }
}
```

### 6.2 PostgreSQL `ON CONFLICT DO NOTHING`으로 claim한다

```java
package com.example.orderstudy.idempotency; // 멱등성 Repository의 패키지다.

import java.time.OffsetDateTime; // 만료 시각 매개변수 타입이다.
import java.util.Optional; // 조회 부재를 명시한다.
import java.util.UUID; // 멱등성 키 타입이다.

import org.springframework.data.jpa.repository.JpaRepository; // Entity 조회·flush를 제공한다.
import org.springframework.data.jpa.repository.Modifying; // INSERT native query임을 표시한다.
import org.springframework.data.jpa.repository.Query; // native SQL을 선언한다.
import org.springframework.data.repository.query.Param; // 이름 매개변수를 연결한다.

public interface IdempotencyRecordRepository extends JpaRepository<IdempotencyRecord, Long> {

    @Modifying // SELECT가 아닌 INSERT를 실행한다.
    @Query(value = """
            INSERT INTO api_idempotency_records (
                client_id, operation, idempotency_key, request_fingerprint,
                state, created_at, expires_at
            ) VALUES (
                :clientId, :operation, :idempotencyKey, :fingerprint,
                'PROCESSING', CURRENT_TIMESTAMP, :expiresAt
            )
            ON CONFLICT (client_id, operation, idempotency_key) DO NOTHING
            """, nativeQuery = true) // 유일 범위 충돌을 예외 대신 영향 행 수 0으로 바꾼다.
    int claim(
            @Param("clientId") Long clientId, // 인증된 호출자 범위다.
            @Param("operation") String operation, // CREATE_ORDER 같은 작업 이름이다.
            @Param("idempotencyKey") UUID idempotencyKey, // 클라이언트 UUID다.
            @Param("fingerprint") String fingerprint, // 최초 payload hash다.
            @Param("expiresAt") OffsetDateTime expiresAt // 공개한 재시도 보관 기한이다.
    ); // 1이면 최초 처리 권한 획득, 0이면 이미 같은 범위의 키가 있다.

    Optional<IdempotencyRecord> findByClientIdAndOperationAndIdempotencyKey(
            Long clientId, // 다른 사용자 응답을 읽지 않게 한다.
            String operation, // 다른 API 작업과 키 공간을 분리한다.
            UUID idempotencyKey // 재시도에서 전달받은 키다.
    );
}
```

PostgreSQL의 유일 인덱스와 `ON CONFLICT`가 동시 claim의 최종 판정자다. 같은 키의 첫 트랜잭션이 아직 끝나지 않았다면 두 번째 INSERT는 충돌 결과가 정해질 때까지 기다릴 수 있다. 첫 트랜잭션이 commit하면 두 번째는 0, rollback하면 두 번째가 새 행을 넣어 1을 얻을 수 있다.

이 구현은 PostgreSQL 종속 native SQL이다. H2 문법으로 통과한 테스트만으로 운영 동작을 보장하지 않는다.

## 7. 주문·재고·응답을 한 트랜잭션으로 확정한다

### 7.1 최초 요청 실행기

```java
package com.example.orderstudy.order; // 주문 트랜잭션의 패키지다.

import java.time.Clock; // 테스트 가능한 현재 시각을 얻는다.
import java.time.OffsetDateTime; // 완료·만료 시각을 만든다.
import java.util.UUID; // 검증된 멱등성 키다.

import org.springframework.stereotype.Service; // 별도 프록시를 가진 Service Bean이다.
import org.springframework.transaction.annotation.Transactional; // claim부터 응답 저장까지 한 트랜잭션으로 묶는다.

import com.example.orderstudy.idempotency.IdempotencyRecord; // claim한 레코드를 완료 처리한다.
import com.example.orderstudy.idempotency.IdempotencyRecordRepository; // 멱등성 DB 작업을 수행한다.

@Service // 바깥 조정 Service와 분리해 @Transactional 프록시를 확실히 통과한다.
public class FirstOrderExecutionService {

    private static final String OPERATION = "CREATE_ORDER"; // DB 키 범위의 안정적인 작업 이름이다.

    private final IdempotencyRecordRepository idempotencyRepository; // claim·완료 저장소다.
    private final ProductRepository productRepository; // 원자적 재고 차감 저장소다.
    private final OrderRepository orderRepository; // 주문 Entity 저장소다.
    private final OrderResponseCodec responseCodec; // 응답 JSON 직렬화를 담당한다.
    private final Clock clock; // 테스트에서 시각을 고정할 수 있다.

    public FirstOrderExecutionService(
            IdempotencyRecordRepository idempotencyRepository,
            ProductRepository productRepository,
            OrderRepository orderRepository,
            OrderResponseCodec responseCodec,
            Clock clock
    ) {
        this.idempotencyRepository = idempotencyRepository; // 멱등성 저장소를 보관한다.
        this.productRepository = productRepository; // 상품 저장소를 보관한다.
        this.orderRepository = orderRepository; // 주문 저장소를 보관한다.
        this.responseCodec = responseCodec; // 응답 codec을 보관한다.
        this.clock = clock; // 시간 공급자를 보관한다.
    }

    @Transactional // claim·재고·주문·완료 응답이 모두 commit되거나 모두 rollback된다.
    public CreateOrderResponse execute(
            Long clientId,
            UUID idempotencyKey,
            String fingerprint,
            CreateOrderRequest request
    ) {
        OffsetDateTime now = OffsetDateTime.now(clock); // 한 요청의 기준 시각을 한 번만 읽는다.
        int claimed = idempotencyRepository.claim( // 최초 처리 권한을 DB에 요청한다.
                clientId, // 인증된 사용자 범위다.
                OPERATION, // 주문 생성 작업 범위다.
                idempotencyKey, // 재시도 식별 키다.
                fingerprint, // payload 동일성 비교값이다.
                now.plusHours(24) // 예시 보관 정책에 따른 만료 시각이다.
        );

        if (claimed == 0) { // 다른 요청이 같은 범위의 키를 이미 확정했다.
            throw new DuplicateIdempotencyKeyException(); // 현재 트랜잭션을 끝내고 바깥에서 재생한다.
        }

        IdempotencyRecord record = idempotencyRepository // 방금 native INSERT한 행을 Entity로 읽는다.
                .findByClientIdAndOperationAndIdempotencyKey(clientId, OPERATION, idempotencyKey)
                .orElseThrow(() -> new IllegalStateException("Claimed idempotency record is missing"));

        int changed = productRepository.decreaseStockIfEnough( // 이전 노트의 조건부 UPDATE를 재사용한다.
                request.productId(), // 주문 대상 상품이다.
                request.quantity() // 주문 수량만큼 차감한다.
        );
        if (changed != 1) { // 상품이 없거나 재고가 부족하면 차감은 일어나지 않았다.
            throw new StockUnavailableException(request.productId(), request.quantity()); // 전체 트랜잭션을 rollback한다.
        }

        Order saved = orderRepository.save( // 재고 차감과 같은 트랜잭션에 주문을 만든다.
                new Order(clientId, request.productId(), request.quantity()) // 인증 사용자와 주문 내용을 기록한다.
        );
        orderRepository.flush(); // 생성 ID를 응답에 사용하도록 INSERT를 실행한다.

        CreateOrderResponse response = new CreateOrderResponse( // 최초 성공 응답을 만든다.
                saved.getId(), // DB가 만든 주문 ID다.
                saved.getProductId(), // 확정된 상품 ID다.
                saved.getQuantity() // 확정된 수량이다.
        );
        String responseBody = responseCodec.write(response); // 재시도에 그대로 돌려줄 JSON을 만든다.
        record.complete( // 상태·HTTP code·body를 같은 트랜잭션에 기록한다.
                201, // 최초 응답의 HTTP 상태 코드다.
                responseBody, // 최초 응답을 재생할 JSON이다.
                OffsetDateTime.now(clock) // 요청 시작이 아니라 실제 완료 시각을 기록한다.
        );
        idempotencyRepository.flush(); // 완료 레코드의 DB 제약까지 commit 전에 확인한다.

        return response; // 프록시가 commit에 성공한 뒤 호출자에게 반환된다.
    }
}
```

`DuplicateIdempotencyKeyException`은 `RuntimeException`으로 정의한다. Spring 기본 rollback 규칙에 따라 현재 트랜잭션을 끝낸 후에만 기존 완료 레코드를 읽는다. 충돌을 잡고 같은 트랜잭션에서 계속 조회·저장하는 구조로 만들지 않는다.

재고 부족도 RuntimeException이므로 claim 행·재고·주문이 모두 rollback된다. 이 단순 설계는 **성공 응답만 재생**한다. 재고 부족 같은 업무 실패까지 같은 키로 고정해 재생하려면 실패 레코드를 별도 commit하는 정책과 어떤 오류를 보관할지 추가로 설계해야 한다.

### 7.2 바깥 조정 Service에서 최초 처리와 재생을 나눈다

```java
package com.example.orderstudy.order; // 주문 애플리케이션 조정 계층의 패키지다.

import java.util.UUID; // 파싱된 멱등성 키다.

import org.springframework.stereotype.Service; // Controller가 호출할 Bean이다.

@Service // 자체 트랜잭션 없이 두 개의 독립된 트랜잭션 Service를 조정한다.
public class IdempotentOrderService {

    private final OrderRequestFingerprint fingerprint; // 요청 의미의 hash를 만든다.
    private final FirstOrderExecutionService firstExecution; // 최초 업무 트랜잭션이다.
    private final OrderReplayService replayService; // 완료 응답 조회 트랜잭션이다.

    public IdempotentOrderService(
            OrderRequestFingerprint fingerprint,
            FirstOrderExecutionService firstExecution,
            OrderReplayService replayService
    ) {
        this.fingerprint = fingerprint; // fingerprint 계산기를 보관한다.
        this.firstExecution = firstExecution; // 최초 실행 프록시를 보관한다.
        this.replayService = replayService; // 재생 조회 프록시를 보관한다.
    }

    public IdempotentOrderResult create(
            Long clientId,
            UUID idempotencyKey,
            CreateOrderRequest request
    ) {
        String requestFingerprint = fingerprint.create(request); // DB 작업 전에 payload hash를 만든다.

        try { // 먼저 최초 처리 권한을 얻어 업무를 실행한다.
            CreateOrderResponse response = firstExecution.execute( // 별도 프록시가 트랜잭션을 시작한다.
                    clientId, idempotencyKey, requestFingerprint, request
            );
            return new IdempotentOrderResult(201, response, false); // 새로 생성한 결과임을 표시한다.
        } catch (DuplicateIdempotencyKeyException exception) { // 같은 범위의 키가 이미 commit되었다.
            return replayService.replay( // 실패한 트랜잭션이 끝난 뒤 read-only 트랜잭션으로 읽는다.
                    clientId, idempotencyKey, requestFingerprint
            );
        }
    }
}
```

자기 클래스 안의 `@Transactional` 메서드를 직접 호출하면 일반적인 proxy 방식에서 새 경계를 통과하지 않을 수 있다. 최초 실행과 replay를 별도 Bean으로 나눈 이유는 트랜잭션 경계를 코드 구조에 드러내기 위해서다.

### 7.3 저장 응답을 재생한다

```java
package com.example.orderstudy.order; // 완료 응답 재생의 패키지다.

import java.util.UUID; // 조회할 멱등성 키다.

import org.springframework.stereotype.Service; // read-only 트랜잭션 Bean이다.
import org.springframework.transaction.annotation.Transactional; // 완료 레코드 조회 경계를 만든다.

import com.example.orderstudy.idempotency.IdempotencyRecord; // 저장 상태와 body를 읽는다.
import com.example.orderstudy.idempotency.IdempotencyRecordRepository; // 완료 레코드를 조회한다.
import com.example.orderstudy.idempotency.IdempotencyState; // 완료 상태를 확인한다.

@Service // 실패한 최초 트랜잭션과 분리된 조회 경계다.
public class OrderReplayService {

    private static final String OPERATION = "CREATE_ORDER"; // 최초 실행과 같은 범위 이름이다.

    private final IdempotencyRecordRepository repository; // 기존 레코드 조회 저장소다.
    private final OrderResponseCodec responseCodec; // 저장 JSON을 DTO로 복원한다.

    public OrderReplayService(
            IdempotencyRecordRepository repository,
            OrderResponseCodec responseCodec
    ) {
        this.repository = repository; // Repository를 보관한다.
        this.responseCodec = responseCodec; // codec을 보관한다.
    }

    @Transactional(readOnly = true) // 완료 레코드를 변경하지 않고 읽는다.
    public IdempotentOrderResult replay(
            Long clientId,
            UUID idempotencyKey,
            String requestFingerprint
    ) {
        IdempotencyRecord record = repository // 사용자·작업·키가 모두 같은 행만 찾는다.
                .findByClientIdAndOperationAndIdempotencyKey(clientId, OPERATION, idempotencyKey)
                .orElseThrow(IdempotencyStateException::new); // 충돌 판정 뒤 행이 없으면 비정상 상태다.

        if (!record.getRequestFingerprint().equals(requestFingerprint)) { // 같은 키의 payload가 달라졌다.
            throw new IdempotencyKeyReuseException(); // 422로 변환할 클라이언트 오류다.
        }
        if (record.getState() != IdempotencyState.COMPLETED) { // 별도 claim 설계에서는 처리 중일 수 있다.
            throw new IdempotencyRequestInProgressException(); // 409로 변환할 진행 중 상태다.
        }

        CreateOrderResponse response = responseCodec.read(record.getResponseBody()); // 최초 JSON을 복원한다.
        return new IdempotentOrderResult(record.getHttpStatus(), response, true); // 업무를 반복하지 않고 재생한다.
    }
}
```

```java
package com.example.orderstudy.order; // Controller에 전달할 내부 결과의 패키지다.

public record IdempotentOrderResult(
        int httpStatus, // 최초 처리에서 저장한 상태 코드다.
        CreateOrderResponse body, // 최초 또는 재생된 응답 body다.
        boolean replayed // 관찰·테스트용 재생 여부다.
) {
}
```

실제 `OrderResponseCodec`은 애플리케이션의 `ObjectMapper`로 DTO를 JSON에 쓰고 읽되 직렬화 실패를 RuntimeException으로 감싸 전체 트랜잭션을 rollback한다. Java 직렬화 객체나 임의 클래스명을 DB에 저장하지 않는다. DTO schema가 바뀌어도 보관 기간 동안 과거 JSON을 읽을 수 있는지 version 정책을 둔다.

## 8. 동시 재시도는 어떻게 하나만 성공하는가?

이 노트의 claim·업무·완료는 한 트랜잭션이다.

```text
요청 A: INSERT claim 성공 → 재고 차감 → 주문 생성 → COMPLETED → commit
요청 B: 같은 INSERT 시도 → 유일 인덱스 충돌 결과를 기다림
        → A commit 확인 → DO NOTHING, 영향 행 수 0
        → 별도 조회에서 A의 완료 응답 재생
```

A가 중간에 rollback하면 claim 행도 사라진다. 기다리던 B는 INSERT에 성공해 최초 처리자가 될 수 있다. PostgreSQL `ON CONFLICT DO NOTHING`과 유일 제약이 이 경합을 판정한다.

단점은 A가 오래 걸리면 B도 DB에서 기다릴 수 있다는 것이다. DB·HTTP timeout을 정하고 주문 트랜잭션을 짧게 유지한다. 외부 결제 API를 이 트랜잭션 안에서 호출하지 않는다.

처리 중 요청에 즉시 409를 주고 싶다면 claim을 먼저 별도 트랜잭션으로 commit하는 설계가 필요하다. 그러면 서버 crash 뒤 남은 PROCESSING 행을 누가, 언제, 어떤 증거로 재개하거나 실패시킬지 lease·heartbeat·복구 작업까지 설계해야 한다. 상태만 먼저 저장하고 복구 정책을 생략하면 요청이 영원히 처리 중으로 남는다.

## 9. 통합 테스트로 한 주문만 생겼는지 확인한다

다음 테스트는 PostgreSQL Testcontainers 등 `ON CONFLICT`를 실제 지원하는 환경을 전제로 한다. 같은 키·같은 payload를 두 worker가 동시에 보내도 두 응답의 orderId가 같고, 주문은 한 건이며 재고도 한 번만 줄어야 한다.

```java
package com.example.orderstudy.order; // 운영 코드와 같은 패키지 구조의 통합 테스트다.

import static org.assertj.core.api.Assertions.assertThat; // 결과와 DB 상태를 검증한다.

import java.util.UUID; // 테스트마다 새 멱등성 키를 만든다.
import java.util.concurrent.CountDownLatch; // 두 worker의 출발을 맞춘다.
import java.util.concurrent.ExecutorService; // 별도 thread에서 요청을 실행한다.
import java.util.concurrent.Executors; // 고정 thread pool을 만든다.
import java.util.concurrent.Future; // 비동기 결과를 회수한다.

import org.junit.jupiter.api.Test; // JUnit 테스트 메서드다.
import org.springframework.beans.factory.annotation.Autowired; // 실제 Bean을 생성자에 주입한다.
import org.springframework.boot.test.context.SpringBootTest; // Repository·트랜잭션 프록시를 함께 올린다.

@SpringBootTest // 대역이 아닌 실제 DB 통합 경로를 사용한다.
class OrderIdempotencyIntegrationTest {

    private final IdempotentOrderService orderService; // 동시 호출할 애플리케이션 Service다.
    private final ProductRepository productRepository; // 준비와 최종 재고 확인에 사용한다.
    private final OrderRepository orderRepository; // 실제 주문 행 수를 확인한다.

    @Autowired // Spring이 테스트 의존성을 주입한다.
    OrderIdempotencyIntegrationTest(
            IdempotentOrderService orderService,
            ProductRepository productRepository,
            OrderRepository orderRepository
    ) {
        this.orderService = orderService; // Service 프록시를 보관한다.
        this.productRepository = productRepository; // 상품 저장소를 보관한다.
        this.orderRepository = orderRepository; // 주문 저장소를 보관한다.
    }

    @Test // 같은 논리 요청이 동시에 도착해도 업무 효과가 한 번인지 검증한다.
    void concurrentRetryCreatesOnlyOneOrder() throws Exception {
        Product product = productRepository.saveAndFlush(new Product("한정판", 10)); // commit된 초기 재고를 만든다.
        CreateOrderRequest request = new CreateOrderRequest(product.getId(), 2); // 두 worker가 같은 payload를 사용한다.
        UUID key = UUID.randomUUID(); // 한 논리 주문을 나타내는 키 하나다.
        Long clientId = 7L; // 같은 인증 사용자 범위를 사용한다.

        CountDownLatch ready = new CountDownLatch(2); // 두 worker의 준비 완료를 기다린다.
        CountDownLatch start = new CountDownLatch(1); // 동시에 시작시키는 문이다.
        ExecutorService executor = Executors.newFixedThreadPool(2); // 두 요청용 thread를 만든다.

        try { // 성공·실패와 관계없이 executor를 종료한다.
            Future<IdempotentOrderResult> first = executor.submit(() -> { // 첫 번째 전송을 등록한다.
                ready.countDown(); // 시작 대기 지점에 도착했음을 알린다.
                start.await(); // 두 요청이 모두 준비될 때까지 기다린다.
                return orderService.create(clientId, key, request); // 같은 키·payload로 주문한다.
            });
            Future<IdempotentOrderResult> retry = executor.submit(() -> { // 재시도 전송을 등록한다.
                ready.countDown(); // 두 번째 worker도 준비되었음을 알린다.
                start.await(); // 첫 worker와 같은 신호에 출발한다.
                return orderService.create(clientId, key, request); // 네트워크 재시도를 흉내 낸다.
            });

            ready.await(); // 두 worker가 모두 start 문 앞에 올 때까지 기다린다.
            start.countDown(); // 두 요청을 가능한 한 비슷한 시점에 출발시킨다.

            IdempotentOrderResult firstResult = first.get(); // 예상 밖 예외는 테스트 실패로 전파된다.
            IdempotentOrderResult retryResult = retry.get(); // 기다리거나 재생된 결과를 회수한다.

            Product current = productRepository.findById(product.getId()).orElseThrow(); // commit된 최신 재고를 읽는다.
            assertThat(firstResult.body().orderId()).isEqualTo(retryResult.body().orderId()); // 같은 주문을 응답해야 한다.
            assertThat(orderRepository.countByClientId(clientId)).isEqualTo(1); // 주문 업무 효과는 한 번이다.
            assertThat(current.getStock()).isEqualTo(8); // 수량 2가 한 번만 차감된다.
            assertThat(firstResult.replayed() || retryResult.replayed()).isTrue(); // 둘 중 하나는 완료 응답 재생이다.
        } finally {
            executor.shutdownNow(); // worker thread를 반드시 정리한다.
        }
    }
}
```

테스트 메서드 자체에 `@Transactional`을 붙이지 않는다. 부모의 미commit 데이터가 worker 트랜잭션에 보이지 않을 수 있기 때문이다. thread 수만큼 DB connection을 사용할 수 있는지도 확인한다.

추가 테스트에는 다음을 포함한다.

1. 같은 키를 순차 재시도해도 같은 orderId와 저장 body를 반환한다.
2. 같은 키에 quantity를 바꾸면 422 후보 예외가 발생하고 새 주문이 생기지 않는다.
3. 다른 clientId가 같은 UUID를 사용하면 서로 독립적으로 처리된다.
4. 재고 부족으로 최초 트랜잭션이 rollback되면 claim·주문·차감이 남지 않는다.
5. 응답 직렬화 실패 시 주문과 재고까지 rollback된다.
6. 보관 기한 안의 재시도는 완료 응답을 재생한다.

이 문서에서는 테스트 코드를 실행하지 않았다. PostgreSQL의 실제 동시 INSERT, timeout과 rollback을 검증할 수 있는 프로젝트에서 실행해야 한다.

## 10. “정확히 한 번”이라고 과장하지 않는다

이 설계가 보장하는 범위는 다음처럼 제한된다.

- 같은 DB 안의 claim, 재고 차감, 주문 생성, 응답 저장이 한 트랜잭션이다.
- 유일 범위와 보관 기간 안에서 같은 키의 **commit된 DB 업무 효과**를 중복하지 않는다.
- 완료 응답을 잃은 클라이언트가 같은 키로 결과를 회수할 수 있다.

하지만 외부 결제사가 승인한 직후 애플리케이션이 crash하고 DB가 rollback될 수 있다. 재시도하면 결제를 다시 호출할 위험이 있다. DB 트랜잭션은 다른 시스템까지 원자적으로 묶지 않는다.

외부 효과에는 외부 API가 제공하는 멱등성 키를 함께 전달하고, Transactional Outbox·상태 머신·보상 작업 등을 검토한다. 메시지 broker도 중복 전달할 수 있으므로 consumer 측 deduplication이 별도로 필요하다.

또한 같은 사용자가 새 키를 만들어 같은 주문을 두 번 요청하면 서버는 서로 다른 논리 작업으로 본다. “장바구니 한 번만 결제” 같은 업무 유일성은 order token이나 cart version 같은 별도 business key로 보호한다.

## 12. 핵심 정리와 다음 학습

1. timeout은 서버 업무 실패가 아니라 결과를 모르는 상태일 수 있다.
2. 멱등성 키는 한 논리 요청의 재전송을 식별하며 새 업무에는 새 키를 사용한다.
3. 사용자·tenant·작업 종류를 키 범위에 포함해 데이터 누출과 잘못된 충돌을 막는다.
4. 같은 키의 다른 payload는 fingerprint로 찾아 거부한다.
5. 애플리케이션 사전 조회가 아니라 DB 유일 제약이 동시 최초 요청을 판정한다.
6. claim·업무 변경·응답 저장을 한 트랜잭션에 두면 commit 결과와 재생 결과가 어긋나지 않는다.
7. 완료된 재시도는 업무를 반복하지 않고 최초 상태와 body를 재생한다.
8. 보관 기한, 처리 중 대기, 실패 저장과 timeout은 API 계약의 일부다.
9. 한 DB의 중복 방지는 외부 결제·메시지까지 정확히 한 번 실행됨을 보장하지 않는다.

🧠 기억할 것: **멱등성은 같은 요청을 알아보는 키, 같은 의미인지 확인하는 fingerprint, 최초 처리자를 정하는 유일 제약, 결과를 되돌려 주는 응답 기록이 함께 있어야 한다.**

다음 확장 주제인 [Transactional Outbox와 이벤트 발행 일관성](../25_09_23_Transactional_Outbox_and_Event_Publishing/09_23_Transactional_Outbox_and_Event_Publishing.md)에서는 주문 DB commit과 메시지 broker 발행 사이에서 한쪽만 성공하는 문제를 outbox 테이블, relay와 consumer 중복 처리로 연결한다.

5. 최초 요청의 주문은 저장했지만 응답 body 기록이 rollback되면 어떤 불일치가 생기는가?
6. 이 노트의 같은 트랜잭션 claim 방식에서 최초 요청이 rollback되면 기다리던 재시도는 어떻게 될 수 있는가?
7. DB 멱등성 레코드가 있어도 외부 결제가 두 번 실행될 수 있는 이유는 무엇인가?

<details>
<summary>정답과 해설</summary>

1. 서버가 첫 요청을 이미 commit했다면 새 키는 새 논리 주문으로 인식되어 주문과 차감이 중복될 수 있다. 같은 논리 요청에는 같은 키를 사용한다.
2. 두 요청이 모두 “없음”을 읽은 뒤 각각 INSERT할 수 있다. DB 유일 제약이나 같은 수준의 원자적 claim이 최종 판정을 해야 한다.
3. 다른 업무 요청에 과거 응답을 재생하거나 변경된 주문을 조용히 무시할 수 있기 때문이다. 키 오사용을 명시적 오류로 드러낸다.
4. 다른 사용자나 API 작업이 우연히 같은 UUID를 사용할 때 충돌하거나 기존 응답이 노출되는 것을 막기 위해서다.
5. 재시도는 완료 결과를 찾지 못해 주문을 다시 만들 수 있다. 업무 효과와 재생 정보는 함께 commit되어야 한다.
6. claim도 함께 rollback된다. PostgreSQL 충돌 판정 뒤 재시도 INSERT가 성공해 새 최초 처리자가 될 수 있다.
7. 외부 시스템 호출은 로컬 DB 트랜잭션에 참여하지 않는다. 외부 성공 뒤 DB rollback이 발생하면 재시도가 외부 호출을 반복할 수 있다.

- [IETF Idempotency-Key draft-07](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-07): 키·fingerprint·재생·오류 처리 제안 — 만료된 작업 문서
- [RFC 9562 — UUID](https://www.rfc-editor.org/rfc/rfc9562.html): UUID 형식과 생성 고려사항
- [PostgreSQL 17 — INSERT](https://www.postgresql.org/docs/17/sql-insert.html): 유일 충돌과 `ON CONFLICT DO NOTHING`
- [PostgreSQL 17 — Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html): 복합 UNIQUE 제약
- [PostgreSQL 17 — Transaction Isolation](https://www.postgresql.org/docs/17/transaction-iso.html): 동시 `ON CONFLICT`의 Read Committed 동작
- [Spring Framework — `@Transactional`](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html): 기본 rollback과 트랜잭션 설정
- [Spring Framework — Transaction Propagation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html): 논리·물리 트랜잭션과 독립 경계
